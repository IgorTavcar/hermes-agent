Multimodal I/O — Images & Audio

Hermes has explicit, first-class code for all four text↔media directions: Text→Image (an image_generate tool over a pluggable provider registry), Image→Text (native vision attachment with a vision_analyze fallback, chosen per model), Text→Audio (a text_to_speech tool with ~12 built-in providers plus sentence-streaming PCM), and Audio→Text (a transcription stack the harness invokes on inbound voice notes — deliberately not a model tool). This page maps each stack to its actual code, and marks precisely where core support ends and skills/plugins take over.

The design split worth noticing. Generation directions (image, speech) are agent tools the model calls; understanding directions (vision, transcription) are harness capabilities applied to inbound media before or around the model. STT in particular has no registry entry at all — the dispatcher tools/transcription_tools.py:2987 is reached only from the gateway, voice mode, wake word, the dashboard, and plugins.

Inbound: platform adapters download photos and voice notes into cache/images / cache/audio (gateway/platforms/base.py:854, gateway/platforms/base.py:1005), then _prepare_inbound_message_text classifies attachments (gateway/run.py:17860, image test at gateway/run.py:2967, STT-eligibility test at gateway/run.py:2990) and enriches the message. Outbound: the model's replies can carry MEDIA: path tags parsed by extract_media (gateway/platforms/base.py:4884), and the gateway can auto-speak replies as voice notes.

Text → Image: image_generate

One unified tool covers text-to-image and image-to-image: passing image_url / reference_image_urls routes to the provider's edit endpoint (schema tools/image_generation_tool.py:1453; params prompt, aspect_ratio, image_url, reference_image_urls, upscale). The tool description is rebuilt per turn from the active provider's capabilities() — the model is told whether editing is available and how many reference images the backend accepts (tools/image_generation_tool.py:1931).

Providers implement the ImageGenProvider ABC (name, is_available, list_models, capabilities, generate — agent/image_gen_provider.py:64) and register through the plugin hook register_image_gen_provider (hermes_cli/plugins.py:2318). Selection is image_gen.provider in config (cli-config.yaml.example:1418). Ephemeral provider URLs (xAI, OpenAI) are materialized into $HERMES_HOME/cache/images/ so channel delivery outlives the URL (agent/image_gen_provider.py:278).

Two hardening details transfer well: _confine_source_images blocks a sandboxed agent from feeding credential files or arbitrary host paths into the edit endpoint (tools/image_generation_tool.py:1817), and the result post-processor emits an agent_visible_image path when the terminal backend's filesystem differs from the host's (tools/image_generation_tool.py:1095). The same ABC/registry pattern repeats for video (video_generate, tools/video_generation_tool.py:595) and powers the desktop pet's sprite generation (agent/pet/generate/imagegen.py:1). Creative skills (comfyui, meme-generation, pixel-art…) sit on top of the tool, not beside it.

Image → Text: native attachment vs. pre-description

Every image that reaches the agent goes through one routing decision: decide_image_input_mode() returns "native" (attach pixels as content parts) or "text" (pre-describe with a vision model) (agent/image_routing.py:468). Config is agent.image_input_mode: auto|native|text; in auto it attaches natively when the model reports supports_vision (resolution order: explicit model config → provider model config → the models.dev catalog, agent/image_routing.py:180) and falls back to text otherwise. Native parts are OpenAI-style base64 image_url data URLs built by build_native_content_parts (agent/image_routing.py:735), with magic-byte MIME sniffing and Pillow transcode-to-PNG for formats Anthropic rejects (AVIF/HEIC/BMP/TIFF, agent/image_routing.py:598).

The vision_analyze tool is the workhorse of the text path and also a standalone tool the model can call on any image path/URL, with an optional region crop (tools/vision_tools.py:1713). It has two internal modes: a native fast path that returns a {"_multimodal": true, "content": […image parts…]} envelope so the main model sees the pixels in the tool result (gated by a provider allowlist, tools/vision_tools.py:967), and a legacy path that asks the auxiliary vision model (auxiliary.vision.model) to describe the image (tools/vision_tools.py:1299). Supporting machinery: progressive resize to a 4 MB embed target (tools/vision_tools.py:796), SVG rasterization through a four-tool fallback chain (tools/vision_tools.py:277), a bounded CPU pool for encode/resize added after a video-frame fan-out starved the event loop (tools/vision_tools.py:181), and a 50 MB download cap.

Security boundary. All media ingestion funnels through resolve_image_source (tools/image_source.py:49 ff.): SSRF checks on URLs, a media-cache-roots allowlist for host paths, and container-exec confinement — the fix for GHSA-gpxw-6wxv-w3qq, where a prompt-injected vision_analyze('/etc/passwd') could read host files.

Dialect translation. The transports rewrite image_url parts per dialect: Anthropic {"type":"image","source":…} blocks (agent/anthropic_adapter.py:1849), Gemini inline_data (agent/gemini_native_adapter.py:284), Bedrock Converse image blocks (agent/bedrock_adapter.py:544), Codex Responses input_image items — including inside function_call_output (agent/codex_responses_adapter.py:960). For models that can't take images at all, _prepare_messages_for_non_vision_model swaps image parts for cached vision_analyze descriptions (run_agent.py:7249), multimodal tool results downgrade to their text_summary (run_agent.py:7281), and on a provider size rejection the loop re-encodes in-flight images below 4 MB and retries (agent/conversation_compression.py:4078).

Producers. Beyond channel photos (Telegram/Discord/WhatsApp/Slack/Matrix/Signal/WeChat/QQ… download into the image cache; Telegram even runs sticker vision, plugins/platforms/telegram/adapter.py:10137), image parts come from browser_vision screenshots (tools/browser_tool.py:2260), computer-use screen captures with their own aux-vision routing gate (tools/computer_use/vision_routing.py:164), MCP image content blocks (tools/mcp_tool.py:1864), ACP resource links (acp_adapter/server.py:494), the OpenAI-compatible inbound API (gateway/platforms/api_server.py:551), and the dashboard's image-upload endpoint (hermes_cli/web_server.py:2505). In gateway text mode, _enrich_message_with_vision prepends a 2–4-sentence description per image (gateway/run.py:24296).

Text → Audio: text_to_speech and streaming TTS

The text_to_speech tool (params text, output_path, speed, instructions, provider — tools/tts_tool.py:4451, entry tools/tts_tool.py:3487) dispatches across BUILTIN_TTS_PROVIDERS (tools/tts_tool.py:771) with documented precedence built-in > command-type > plugin (agent/tts_provider.py:12). Streaming. A parallel stack turns LLM text deltas into PCM while the reply is still generating: StreamingTTSProvider implementations for ElevenLabs/OpenAI/Gemini/xAI chunk text at sentence boundaries and emit int16 mono PCM (tools/tts_streaming.py:131), the gateway's StreamingTTSConsumer bridges the synchronous agent thread into an asyncio drain (gateway/streaming_tts_consumer.py:55), and adapters opt in via a five-method contract (supports_streaming_tts … abort_streaming_tts, gateway/platforms/base.py:4557) — with a barge-in latch so user speech interrupts playback.

Voice replies on channels. /voice toggles per-chat auto-TTS (gateway/slash_commands.py:3244, persisted state gateway/run.py:7245). When _should_send_voice_reply agrees (gateway/run.py:21779), _send_voice_reply synthesizes and hands the file to adapter.send_voice() (gateway/run.py:21859) — as Ogg/Opus on Telegram/WhatsApp/Signal/Matrix/Feishu (the platforms that render true voice bubbles, tools/tts_tool.py:796; ffmpeg conversion tools/tts_tool.py:1403), e.g. Telegram's sendVoice with a duration probe (plugins/platforms/telegram/adapter.py:7547). Discord goes further with live voice-channel playback through a 48 kHz mixer with an ambient "thinking" bed and ducking (plugins/platforms/discord/voice_mixer.py:1). The dashboard/desktop exposes POST /api/audio/speak and a websocket PCM stream (hermes_cli/web_server.py:5181).

Audio → Text: transcription as a harness capability

STT lives in tools/transcription_tools.py but is never registered as a model tool. The public API is transcribe_audio(file_path, model, source) (tools/transcription_tools.py:3153) plus transcribe_audio_local_fallback — recover with local whisper when the configured cloud provider fails (tools/transcription_tools.py:3226). The dispatcher walks built-in → command-type → plugin (tools/transcription_tools.py:2987). The default provider is local: faster-whisper with the base model, Silero VAD, confidence gating on no_speech_prob/logprob, and idle model unload (tools/transcription_tools.py:1897).

Preprocessing handles the messy formats messaging platforms actually send: WeChat/QQ .silk voice codec → WAV via pilk (tools/transcription_tools.py:1531), iOS .caf → WAV, generic ffmpeg transcode, a 25 MB cap, and an ffmpeg silenceremove trim before paying for cloud STT (tools/transcription_tools.py:2820).

The gateway voice-note pipeline. Only genuine voice messages qualify (MessageType.VOICE or audio/* voice notes — gateway/run.py:2990); _enrich_message_with_transcription transcribes in a worker thread, falls back to local whisper, and injects the transcript as a quoted line, optionally echoing 🎙️ "…" back to the chat (gateway/run.py:24367; gates stt.enabled / stt.echo_transcripts, gateway/config.py:959). Audio file attachments are deliberately excluded: the model gets the cached path plus an instruction to "transcribe or process it yourself" via its own tools (gateway/run.py:18042).

Live voice. The same transcribe_audio core powers Discord voice-channel listening (plugins/platforms/discord/adapter.py:4929), CLI voice mode with a whisper-hallucination filter (tools/voice_mode.py:1249), TUI continuous VAD capture (hermes_cli/voice.py:432), wake-word activation ("hey Hermes" via openWakeWord, tools/wake_word.py:847), and the dashboard's POST /api/audio/transcribe (hermes_cli/web_server.py:4974).

The shared media plane

  • Inbound caching with content sniffing — cache_image_from_bytes/url verify magic bytes so an HTML error page can't be cached as a .jpg (gateway/platforms/base.py:837); audio extensions are corrected by a real container sniffer that distinguishes M4A vs MP4 ftyp brands and MP3 vs ADTS sync words (tools/audio_container.py:1). Size guards cap inbound media before download completes (gateway/platforms/base.py:758).
  • Outbound delivery with path safety — the model attaches files via MEDIA:<path> tags; validate_media_delivery_path enforces allowed roots, recency, and deny-lists before anything leaves the machine (gateway/platforms/base.py:1684), with per-platform how-to-attach guidance injected into the system prompt (agent/prompt_builder.py:817).
  • The multimodal tool-result envelope — any tool can return {"_multimodal": true, "content": […], "text_summary": …}; the registry enforces the shape (tools/registry.py:1084) and every consumer (display, logging, compression, non-vision models) knows to fall back to text_summary (agent/tool_dispatch_helpers.py:349).
  • ffmpeg as the universal shim — one discovery helper (tools/transcription_tools.py:231) serves STT transcodes, silence trimming, TTS→Opus conversion for voice bubbles, and Discord playback.
  • Relay media plane — for the experimental Relay connector, generated images and voice notes upload to /relay/media and connector attachments download to local temp files so vision/file tools always see a local path (gateway/relay/media.py:71).

What is explicitly not in core

  • OCR. No tesseract/easyocr/paddleocr anywhere. Scanned-PDF handling is prompt-driven: read_file's extraction-coverage warning literally instructs the model to run pdftoppm -jpeg -r 150 … and inspect each page with vision_analyze (tools/read_extract.py:297, tools/file_tools.py:2654). Dedicated OCR lives in the optional skills/productivity/ocr-and-documents skill (marker-pdf).
  • No Replicate/Stability/Together image backends — only a forward-looking comment (hermes_cli/tools_config.py:3947). No Deepgram or gTTS either; those names appear only as examples in the provider-ABC docstrings.
  • No in-tree TTS or STT plugins. Both ABCs and registries are wired end-to-end, but plugins/tts/ and plugins/transcription/ don't exist — the extension points are documented and empty (agent/tts_provider.py:32).
  • No music/audio generation in core — only optional skills (audiocraft MusicGen/AudioGen; Suno prompting).
  • SMS/Twilio has no media path at all — no MMS in or out; likewise a2a, ntfy, irc and other minimal adapters.
