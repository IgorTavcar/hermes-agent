Hermes Agent — Fresh Engineering Wiki

Hermes Agent is a self-improving, multi-platform AI agent harness from Nous Research (MIT-licensed). It wraps any chat model in everything it needs to act in the world — a terminal, a filesystem, web and code execution, memory, and a gateway onto messaging platforms — and drives every user message to completion through one provider-agnostic turn loop. This wiki is a from-the-code reference: how Hermes is built, what makes it work, and which ideas transfer to any agent harness. Every claim is a path:line citation into this repository at commit 42a4c91c4.

What Hermes is

The entire system is a set of thin drivers around one agent core: the AIAgent class (run_agent.py:412) and its single production turn loop, run_conversation (agent/conversation_loop.py:1704). The CLI, the TUI, the multi-platform gateway daemon, the cron scheduler, the ACP adapter and the batch runner all feed the same loop — they differ only in how messages get in and how replies flow out. There is no second code path.

It is provider-agnostic by design, speaking to ~40 backends through four API dialects (OpenAI ChatCompletion, Anthropic Messages, OpenAI Responses/Codex, Bedrock Converse) — including subscription-OAuth backends like ChatGPT Plus and Claude Pro/Max — with provider differences quarantined inside per-dialect transports so the loop body stays uniform. And it is genuinely self-improving: it creates skills from experience, patches them during use, nudges itself to persist knowledge, and searches its own past conversations.

The core is deliberately simple, the edges deliberately paranoid. The loop head is a plain synchronous while (api_call_count < max_iterations and iteration_budget.remaining > 0) (agent/conversation_loop.py:1922). Almost everything else in the repo is scaffolding to feed, protect, persist and observe that loop — and almost every non-obvious choice traces back to protecting the context window, surviving rate limits, or making stateless infra behave statefully. See Transferables.

A message, end to end

A bird's-eye view of how a single chat message flows through the system, from platform SDK to reply:

graph TD;
  U[user message on Telegram/Discord/...]-->AD[platform adapter: MessageEvent + session key];
  AD-->GD[gateway busy guard / pending FIFO];
  GD-->RH[GatewayRunner._handle_message: reset vars, profile, hooks, auth];
  RH-->SS[SessionStore.get_or_create + turn lease];
  SS-->TR[TurnRunner.run_sync on thread pool];
  TR-->RC[run_conversation = inner loop];
  RC-->L{budget loop};
  L-->K[build api_kwargs + cache marks];
  K-->T[transport: convert + stream];
  T-->N[normalize to uniform shape];
  N-->B{tool calls?};
  B-->|yes|FL[flush to SQLite -> execute batch];
  FL-->L;
  B-->|no|F[final response];
  F-->FIN[finalize: persist, nudges, background review fork];
  RC-->STR[live stream events -> user];
  FIN-->OUT[deliver reply];
