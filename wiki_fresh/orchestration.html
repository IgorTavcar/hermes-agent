Orchestration & Subagents

How Hermes runs many agents: the one model-facing spawn tool (delegate_task), the OS-process worker fleet behind the Kanban board, agent-to-agent protocols, and the harness's own background forks — measured along five axes: steerability, context isolation, configurability, observability, and inter-agent communication. The headline finding: Hermes has no dynamic workflow engine — the model never writes orchestration code; it declares intent (a task, a batch, a dependency graph) and a validated kernel executes it.

The stance. Everywhere the model participates in orchestration it emits data — a goal, a task list, a {tasks, parents} graph — and a kernel validates and executes it. Control flow (loops, conditionals, retries, scheduling) always lives in harness code. This trades expressiveness for governability: spawns can be paused globally (tools/delegate_tool.py:194), capped per turn, and halted by an ESTOP that by policy never kills in-flight work (agent/estop.py:12).

The Kanban DAG: the real workflow engine

The closest thing to a workflow engine is a task board. It is a genuine dependency-graph executor: link_tasks creates edges with cycle rejection (hermes_cli/kanban_db.py:3829, hermes_cli/kanban_db.py:3860); a child promotes to ready only when every parent is done (_parents_satisfied, hermes_cli/kanban_db.py:4606, inside recompute_ready hermes_cli/kanban_db.py:4510); block kinds are typed — dependency blocks auto-promote rather than entering the human "blocked" bucket (hermes_cli/kanban_db.py:125).

Execution: a gateway watcher ticks dispatch_once every 60 s under a machine-global lockfile (gateway/kanban_watchers.py:1182, hermes_cli/kanban_db.py:9808); each ready node spawns a full agent OS process via subprocess.Popen pinned to a profile — which carries model, provider, reasoning effort, toolsets and system prompt per node (hermes_cli/kanban_db.py:10709). Workers are supervised for real: PID-based crash detection, stale-claim reclaim, SIGTERM→SIGKILL on max_runtime_seconds (hermes_cli/kanban_db.py:4971), and a memory-derived concurrency default of 512 MiB per worker clamped to 2–8 (hermes_cli/kanban_db.py:9664).

What it cannot do: no conditional branching, no loops, no typed data between nodes. Handoff is prose — completion summaries and comments, which the tool descriptions call "the deliberate handoff channel between tasks" (tools/kanban_tools.py:1101) — plus the swarm "blackboard", structured JSON comments on the root task (hermes_cli/kanban_swarm.py:337).

Dynamic workflows — the direct answer

There is no Workflow-script facility. Nothing lets the model author and execute an orchestration program in the Claude-Code sense (a script composing agent() / pipeline() / parallel()). Two hard boundaries enforce this:

  • The execute_code sandbox RPC — the obvious place to hang model-written orchestration — is hard-gated to exactly seven data tools: SANDBOX_ALLOWED_TOOLS = {web_search, web_extract, read_file, write_file, search_files, patch, terminal} (tools/code_execution_tool.py:63), 50 calls per execution (tools/code_execution_tool.py:75), dispatched through the same guarded handler the LLM uses (tools/code_execution_tool.py:652). No delegate_task, no cronjob, no kanban, no MCP behind the RPC. The only leak is terminal — a script could shell out to hermes chat -q, but that routes through the normal approval stack with no result plumbing: shelling out, not orchestration.
  • No graph structure accepts control flow: Kanban edges are pure "wait for all parents".

What exists instead is declarative graph emission. kanban_decompose prompts an auxiliary LLM for {"tasks": [{title, body, assignee, parents: [indices]}]} with the execution semantics spelled out in the prompt — parents are data dependencies, parentless tasks run in parallel (hermes_cli/kanban_decompose.py:52). The kernel then validates with a Kahn's-algorithm cycle check over the whole sibling graph and writes the entire decomposition in one atomic transaction (hermes_cli/kanban_db.py:7339). It runs automatically each dispatcher tick, gated by kanban.auto_decompose re-read every tick so flipping the flag halts runaway fan-out without a restart (gateway/kanban_watchers.py:1600). A running orchestrator agent can also build graphs itself — kanban_create's description says outright: "used by orchestrator workers to fan out — decompose work into child tasks, link them into a pipeline, then complete your own task" (tools/kanban_tools.py:2137).

Model emits data, kernel executes. Claude Code hands the model a Turing-complete orchestration script; Hermes hands it a JSON graph a scheduler executes. Less expressive — no conditionals, no loops, no map-reduce composition — but trivially validatable, pausable, rate-limitable, and resumable, because the "workflow state" is rows in SQLite rather than a running program.

delegate_task anatomy

The one model-facing spawn tool (schema tools/delegate_tool.py:4730, registered tools/delegate_tool.py:4906, toolset delegation toolsets.py:299, entry tools/delegate_tool.py:3597). Params: goal, context, tasks[] for batch fan-out, role (leaf|orchestrator), per-task output_schema, and the control plane action=list|steer|stop. Two params are accepted and ignored: background is deprecated (tools/delegate_tool.py:4816) — the harness decides sync-vs-background itself, forcing background=(not _is_subagent) so top-level delegations never block the chat and orchestrator children stay synchronous to synthesize (run_agent.py:8242) — and a model-supplied max_iterations is discarded in favor of config (tools/delegate_tool.py:3689).

Background results return as a new turn: a completion event on the shared process_registry.completion_queue (tools/async_delegation.py:1220), injected by the gateway's delegation watcher (gateway/run.py:25485), backed by a durable async_delegations ledger with crash recovery and delivery retry — 48 h replay, 8 attempts (tools/async_delegation.py:142, tools/async_delegation.py:335). Guardrails: 50 spawns per turn (agent/tool_guardrails.py:483, hermes_cli/config_defaults.py:656), and multiple delegate_task calls in one assistant message are truncated to the concurrency cap (run_agent.py:4883).

Plugins get the same machinery through SubagentLifecycleService — contract objects and HMAC handles instead of raw agents, on its own hardcoded 8-worker executor (agent/subagent_lifecycle.py:187, agent/subagent_lifecycle.py:165).

Steerability: main loop vs children vs workers

One delivery primitive serves everything: AIAgent.steer() (run_agent.py:3381) stashes text that is appended into the last tool-result message at the next iteration boundary (agent/agent_runtime_helpers.py:4223) — never inserting a message, so role alternation and the prompt cache survive.

  • Steer races are first-class. Acceptance closes under the registry lock; a steer that misses the last delivery boundary is drained into the completion entry as missed_steer — reported, never silently dropped (tools/delegate_tool.py:242, tools/delegate_tool.py:3151).
  • Subagents shield the main loop. With live children, the gateway demotes interrupt mode to queue so a casual chat follow-up can't destroy hours of delegated work; /stop still forces it (gateway/run.py:9744, gateway/run.py:10112).
  • Kill switches by blast radius: per-child stop; per-session interrupt_for_session on /new (tools/async_delegation.py:1531); process-wide interrupt_all on shutdown (tools/async_delegation.py:1502); a global spawn-pause toggle from the TUI (tools/delegate_tool.py:194, RPC tui_gateway/methods_session.py:3223); and ESTOP, which pauses new cron/kanban/gateway work but never kills in-flight (agent/estop.py:12).
  • Gap: the TUI /agents overlay has kill and pause keys but no steer key — the subagent.steer RPC has no UI caller (ui-tui/src/components/agentsOverlay.tsx:684).

Context isolation & workspaces

Children are built by _build_child_agent (tools/delegate_tool.py:1578) with a fresh conversation, never the parent transcript: an ephemeral system prompt of goal + context only (tools/delegate_tool.py:1173), skip_context_files, skip_memory, no clarify callback. Toolsets are inherited and intersected, never expanded — "subagent must not gain tools the parent lacks" (tools/delegate_tool.py:1660) — and DELEGATE_BLOCKED_TOOLS = {delegate_task, clarify, memory, send_message, cronjob} strips recursion, user interaction, shared-memory writes, and outbound side effects (tools/delegate_tool.py:50, tools/delegate_tool.py:1278); role="orchestrator" re-adds only delegation, one level deep by default.

  • State: own SQLite session with its own DB handle on the parent's file and parent_session_id lineage (tools/delegate_tool.py:1900); child sessions are hidden from pickers/search (tools/session_search_tool.py:46) and cascade-delete with the parent (hermes_state.py:301).
  • Workspace: opt-in git-worktree isolation puts each child in .worktrees/subagent-<id> on its own branch, with {commits, dirty, pruned} reported in the result (tools/subagent_worktree.py:120, flag tools/delegate_tool.py:887) — local backend + git only, off by default. Otherwise children share the parent's working copy and container (tools/delegate_tool.py:2704).
  • The one deliberate leak: a "subagent modified files the parent previously read" reminder built from the file-write registry, appended to the summary (tools/delegate_tool.py:3171).
  • The opposite trade: the background-review fork deliberately shares the parent's session id and cached system prompt for warm prefix cache, with persistence hard-disabled so it cannot corrupt the session (agent/background_review.py:1062).

Kanban adds genuine per-node configuration: each task's assignee is a profile carrying model, provider, reasoning effort, toolsets and prompt (hermes_cli/kanban_db.py:10709).

The big absences. The model can configure almost nothing per spawn — no model, no effort, no toolsets, no timeout (schema has no such params; toolsets=None is forced at tools/delegate_tool.py:3847). And there is no token/cost budget anywhere: per-child cost_usd is measured and rolled up, but never enforced — caps are iteration count, optional wall-clock, and concurrency only.

Observability

  • Live transcripts as files — one append-only, redacted log per child under cache/delegation/live/ (tools/delegation_live_log.py:112), whose path is handed back to the parent model with an explicit tail -f hint (tools/delegate_tool.py:4304) — the model can watch its own children with the terminal tool.
  • Structured progress events — subagent.spawn_requested/start/tool/thinking/text/complete carrying subagent_id, parent_id, depth, model (tools/delegate_tool.py:1338), rendered as the TUI /agents spawn tree and desktop panels.
  • Durable ledger — the async_delegations table with delivery claims and crash recovery means completions survive process restarts and land as a new turn (tools/async_delegation.py:142).
  • Cost attribution — per-child tokens/api_calls/duration/cost plus a tool trace in every result, rolled into the parent session's spend (tools/delegate_tool.py:3403).
  • Hooks — subagent_start / subagent_stop with a sanitized tool-call history (tools/delegate_tool.py:2055, tools/delegate_tool.py:3454).
  • Gap — the parent model is blind mid-run by design (context protection): no child events enter its context until the completion message, unless it polls action="list" or tails the live log itself.

Inter-agent communication

  • Parent↔child: goal + context down; one summary up, optionally validated against a per-task JSON Schema with exactly one bounded correction retry (tools/delegation_output_schema.py:1, driven at tools/delegate_tool.py:2925) — the repo's only typed inter-agent contract. Mid-run: parent→child steer only; children cannot ask questions (clarify blocked).
  • Sibling↔sibling: absent by design. Ownership checks restrict control to one's own descendants; shared state is only the filesystem, the shared container, and (for kanban) the board.
  • LLM-free handoffs: kanban comments/blackboard, cron's context_from file injection, and teams_pipeline's dataclasses between stages. Nothing routes child A's output directly into child B's input inside a delegation batch — that composition exists only via the Kanban DAG.
  • Cross-instance: the A2A plugin is a real agent-to-agent protocol — outbound a2a_discover/call/orchestrate with capability-based fan-out to peers in all|first|best modes (plugins/platforms/a2a/tools.py:396), an inbound JSON-RPC server with Agent Card (plugins/platforms/a2a/adapter.py:338), ping-pong loop protection (plugins/platforms/a2a/protocol.py:454), and Hermes→Hermes forwarding across local profiles by subprocess (plugins/platforms/a2a/adapter.py:850).
  • Adjacent: send_message targets chat platforms, not agent sessions, and is blocked for children (tools/send_message_tool.py:208); delivery mirroring writes a record into the target session's transcript — one-directional, text-only (gateway/mirror.py:25); ACP session forking deep-copies history into a new editor session (acp_adapter/session.py:253).

Consolidated absences

  • No model-authored orchestration programs; no conditionals, loops, or typed data-flow in any graph structure.
  • No per-spawn model/effort/toolset selection by the model; no token or cost budgets (iterations + optional wall-clock + concurrency only).
  • No redirect for subagents; no queueing of follow-ups to a child; no sibling messaging or shared mailbox.
  • Cooperative-only cancellation for in-process children — a truly wedged thread can only be stall-finalized, not killed; real kills exist only at the OS-process tier.
  • Worktree isolation off by default and git/local-only; children otherwise share the parent's working copy and container.
  • No cron job dependencies or ordering (context_from is a stale read, not a barrier); no plugin-registered pipeline stages or middleware — hooks are a fixed event set, mostly observer-only.
