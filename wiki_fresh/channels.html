Messaging Channels

One gateway process fronts every chat platform. Each channel is a platform adapter — a subclass of BasePlatformAdapter that normalizes inbound platform updates into a MessageEvent and sends replies back out. This page covers the quickest, cleanest setup for Telegram, WhatsApp (both the unofficial Baileys bridge and the official Meta Cloud API), and Twilio SMS, with the real config keys, plus a briefer tour of Discord, Slack and Signal.

How a channel plugs into the gateway

Adapters subclass BasePlatformAdapter and register through a plugin's register(ctx) → ctx.register_platform(...) (hermes_cli/plugins.py:2774), which builds a PlatformEntry in the PlatformRegistry (gateway/platform_registry.py:62). Heavy SDKs (python-telegram-bot, discord.py, slack_bolt) are lazy-loaded — a deferred loader per platform imports the SDK only when the registry is queried (hermes_cli/plugins.py:4437). At startup GatewayRunner._create_adapter() checks the registry first, then falls through to a built-in if/elif chain (gateway/run.py:15560).

Enablement is env-driven — the mere presence of a token enables the channel (gateway/config.py:1910 ff.): Telegram on TELEGRAM_BOT_TOKEN, WhatsApp/Baileys on WHATSAPP_ENABLED, WhatsApp Cloud on the phone-id + access-token pair, SMS/Twilio on TWILIO_ACCOUNT_SID. YAML config in ~/.hermes/config.yaml is bridged into these env vars by each plugin's apply_yaml_config hook.

Authorization & pairing — one shared gate

GatewayRunner._is_user_authorized() (gateway/authz_mixin.py:386) applies one ordered policy across every channel: chat-scoped group allowlists → {PLATFORM}_ALLOW_BOTS → per-platform allow-all → the pairing store → env allowlists {PLATFORM}_ALLOWED_USERS + GATEWAY_ALLOWED_USERS → default deny. The global escape hatch is GATEWAY_ALLOW_ALL_USERS.

The zero-config path is DM pairing: leave the allowlist unset, and an unknown DM gets a pairing code the operator approves with hermes pairing approve <platform> <code> — approval also writes the user into the platform's allowlist env var (gateway/pairing.py:1).

Cross-cutting message handling

  • Chunking: truncate_message() splits at natural boundaries, preserves/re-opens code fences, and appends (1/3) indicators; a len_fn lets Telegram measure in UTF-16 units (gateway/platforms/base.py:7188).
  • Typing: a _keep_typing() heartbeat refreshes every 2 s (gateway/platforms/base.py:5104).
  • Voice memos: gateway-side and provider-agnostic — _enrich_message_with_transcription() transcribes inbound audio and prepends it as quoted lines, optionally echoing 🎙️ "…" back to the chat (gateway/run.py:24367).
  • Cross-platform continuity: sessions are keyed per platform — there is no automatic shared session across platforms. The three bridges are /handoff <platform> (moves a live session keeping its id), the send_message tool with target="<platform>:<chat_id>", and delivery mirroring into the target session's transcript (gateway/mirror.py:25).

Telegram

The most feature-complete adapter (~10.9k lines): TelegramAdapter over python-telegram-bot 22.8 (plugins/platforms/telegram/adapter.py:638). Inbound is long polling by default, or webhook when TELEGRAM_WEBHOOK_URL is set — and webhook mode refuses to start without TELEGRAM_WEBHOOK_SECRET (plugins/platforms/telegram/adapter.py:4640). Outbound sends MarkdownV2 with an automatic plain-text fallback when Telegram reports a parse error (plugins/platforms/telegram/adapter.py:5255); the 4096-char limit is measured in UTF-16 code units. Voice memos route through the gateway STT pipeline; photos are cached locally so vision tools survive Telegram's ~1h ephemeral URLs.

Quickest setup.
  1. Automatic (recommended): hermes setup → Telegram → choice [1] does QR-based managed-bot onboarding through a Nous-hosted service and auto-detects your user id (hermes_cli/telegram_managed_bot.py:21). Manual: /newbot in @BotFather for the token; message @userinfobot for your numeric id.
  2. Write ~/.hermes/.env: TELEGRAM_BOT_TOKEN=…, TELEGRAM_ALLOWED_USERS=<your id>, TELEGRAM_HOME_CHANNEL=<your id> (cron/notification target). Or leave ALLOWED_USERS unset and use pairing.
  3. For groups: disable BotFather privacy mode and re-add the bot.
  4. hermes gateway → expect [telegram] Connected to Telegram (polling mode).
  5. Webhook mode (cloud/sleep-when-idle): add TELEGRAM_WEBHOOK_URL and TELEGRAM_WEBHOOK_SECRET="$(openssl rand -hex 32)".

WhatsApp via Baileys bridge (unofficial, personal accounts)

WhatsAppAdapter does not speak the WhatsApp protocol — it manages a Node.js sidecar (Baileys @whiskeysockets/baileys) and talks HTTP to 127.0.0.1:<bridge_port> (plugins/platforms/whatsapp/adapter.py:381, bridge at scripts/whatsapp-bridge/bridge.js:1). Inbound is 1-second HTTP polling of the local bridge's /messages (plugins/platforms/whatsapp/adapter.py:1326); outbound is one POST /send per chunk. Pairing is by QR against WhatsApp's Linked Devices; the bridge serializes all sends to avoid cross-chat contamination.

Quickest setup.
  1. Prereq: Node.js 18+.
  2. hermes whatsapp — choose mode (separate bot number vs personal self-chat), enter WHATSAPP_ALLOWED_USERS (country-code phone numbers, no +; * = anyone), then scan the terminal QR: WhatsApp → Settings → Linked Devices → Link a Device (hermes_cli/main.py:3257). Only after creds.json exists does it write WHATSAPP_ENABLED=true — a deliberate choice so an aborted wizard doesn't cost a 30 s gateway timeout.
  3. Alternative: pair from the web dashboard (streams QR frames).
  4. hermes gateway.
Unofficial API — ban risk. Use a dedicated number.

WhatsApp Business Cloud API (official Meta)

WhatsAppCloudAdapter is built-in and talks raw HTTPS to the Meta Graph API via httpx, with an aiohttp webhook server for inbound (gateway/platforms/whatsapp_cloud.py:203). Inbound is a webhook: a GET verify handshake plus a POST handler that validates the X-Hub-Signature-256 HMAC over the raw bytes and refuses with 503 when WHATSAPP_CLOUD_APP_SECRET is unset — the #1 "inbound doesn't work" cause (gateway/platforms/whatsapp_cloud.py:1457). Typing + read receipt ship in one call (Meta couples them), and interactive button/list replies are supported. Note: free-form sends only within Meta's 24-hour window; groups not supported in v1.

Quickest setup.
  1. Meta side: create an app → WhatsApp → API Setup → generate access token.
  2. hermes whatsapp-cloud — six validated prompts (hermes_cli/setup_whatsapp_cloud.py:232): WHATSAPP_CLOUD_PHONE_NUMBER_ID (Meta's 15–17 digit id, not the phone number — the #1 trap), ACCESS_TOKEN (EAA…), APP_SECRET (32 hex), and an auto-generated VERIFY_TOKEN.
  3. Expose HTTPS: cloudflared tunnel --url http://localhost:8090.
  4. hermes gateway, then verify locally with a curl of the hub.challenge handshake before touching Meta.
  5. In Meta's dashboard set the callback URL <tunnel>/whatsapp/webhook + verify token, subscribe to the messages field, and add your phone to the recipient list.

Twilio SMS

SmsAdapter uses no Twilio SDK — raw REST over aiohttp with HTTP Basic auth (plugins/platforms/sms/adapter.py:81). Inbound is a webhook (Twilio POSTs form-encoded); the handler validates the X-Twilio-Signature HMAC-SHA1 (trying both with-port and without-port URL variants, since Twilio may sign either) and refuses to start without SMS_WEBHOOK_URL unless SMS_INSECURE_NO_SIGNATURE=true (plugins/platforms/sms/adapter.py:322). Replies go out via the Twilio REST Messages.json API, not inline TwiML. Markdown is stripped (SMS renders it literally), the limit is 1600 chars (~10 segments), phone numbers are redacted in all logs, and MMS/media is not implemented.

Quickest setup.
  1. Twilio Console: copy Account SID (AC…), Auth Token, and an SMS-capable number in E.164.
  2. uv pip install -e ".[sms]" (installs aiohttp).
  3. ~/.hermes/.env: TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_PHONE_NUMBER=+1…, and SMS_WEBHOOK_URL=https://your-host/webhooks/twilio (required), plus SMS_ALLOWED_USERS.
  4. Expose the port: cloudflared tunnel --url http://localhost:8080.
  5. Twilio Console → your number → Messaging → "A message comes in" → Webhook POST to <public>/webhooks/twilio. This URL must byte-match SMS_WEBHOOK_URL or every request fails signature validation.
  6. hermes gateway.
Known bug (found during this survey). The SMS adapter's out-of-process sender (_standalone_send, used by cron deliver=sms and send_message without a live gateway) calls _strip_markdown_for_sms(), which uses re.sub but the module never imports re — so those paths raise NameError and return an error (plugins/platforms/sms/adapter.py:437). The live-adapter path is unaffected because it uses helpers.strip_markdown instead. Worth a one-line import re fix.
