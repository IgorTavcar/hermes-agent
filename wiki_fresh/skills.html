Self-Adaptive Skills

The marketing claim — "creates skills from experience, improves them during use, nudges itself to persist knowledge, searches its own past conversations, builds a deepening model of who you are" — maps to real, specific machinery. This page documents the workflows that transform work-over-time into skills: the counter that decides a task was complex, the background fork that writes skills without touching the live conversation, the ownership guards that keep the agent from mutating what it doesn't own, and the weekly curator that consolidates the library.

The design intent is stated in the review module's own docstring: "After every turn, run_conversation may fire off a daemon thread that replays the conversation snapshot in a forked AIAgent and asks itself 'should any skill/memory be saved or updated?'. Writes go straight to the memory + skill stores. Main conversation and prompt cache are never touched." (agent/background_review.py:1).

Skill format & storage

Three shipped trees plus one runtime tree: skills/ (82 bundled SKILL.md files), optional-skills/ (117, installed on demand), and the user tree ~/.hermes/skills/ (hermes_constants.py:1515). The format is agentskills.io-compatible — YAML frontmatter + Markdown body, with an assets//references//templates//scripts/ layout (tools/skills_tool.py:28; allowed subdirs whitelisted at tools/skill_manager_tool.py:520).

A hard validator enforces frontmatter shape and — on create only — a description ≤ 60 characters (tools/skill_manager_tool.py:566). That 60-char limit is the single highest-leverage constraint in the system: it gates creation, is repeated in three separate prompts, has its own linter rule, and its violation silently truncates the description so the skill never routes (agent/learn_prompt.py:44). A 12-rule advisory linter runs after every create (tools/skill_linter.py:1). Seeding never clobbers user edits: a bundled skill that changed and whose user copy diverged is skipped (tools/skills_sync.py:13).

How skills reach the model's context — three tiers

  1. Always-on index in the system prompt. A ## Skills (mandatory) block lists every skill's name + 60-char description and instructs: scan before replying, load with skill_view(name) if even partially relevant, patch it if it has issues, and offer to save one after difficult tasks (agent/prompt_builder.py:2101). The self-improvement instruction is baked into the always-loaded index itself.
  2. Full body via skill_view. Loading a skill bumps both view and use telemetry — actively loading a skill to act on it counts as use, and the curator's stale timer keys off last_used_at (tools/skills_tool.py:2135).
  3. Support files on demand via skill_view(name, file_path="references/x.md").

The index sits in the volatile prompt band, ahead of memory, precisely because skills are runtime-mutable — a stable-band placement would bust the cached prefix on every self-edit (agent/system_prompt.py:765). There is no embedding or semantic router: matching is the model reading descriptions plus deterministic frontmatter filters (platform gating, tool-dependency gating, disabled lists).

Autonomous skill creation — the trigger

"This task was complex" is operationalized as ≥N tool iterations since the last skill_manage call. The counter _iters_since_skill increments once per tool-calling iteration (agent/conversation_loop.py:1988), resets when skill_manage is actually used (agent/tool_executor.py:667), and is checked at turn end against skills.creation_nudge_interval (default 10 in code, 15 in the example config) (agent/turn_finalizer.py:770). The spawn gate additionally requires a real final response, no interrupt, not a cron session, not a subagent, and the feature enabled (run_agent.py:1832).

The prompt (_SKILL_REVIEW_PROMPT, agent/background_review.py:259) is emphatic and specific — a few load-bearing excerpts:

"Be ACTIVE — most sessions produce at least one skill update… A pass that does nothing is a missed learning opportunity, not a neutral outcome."

"Target shape of the library: CLASS-LEVEL skills, each with a rich SKILL.md and a references/ directory… Not a long flat list of narrow one-session-one-skill entries."

Preference order, earliest that fits: (1) update a currently-loaded skill, (2) update an existing umbrella, (3) add a support file, (4) create a new class-level umbrella. "If the proposed name only makes sense for today's task, it's wrong."

And a negative half — the anti-sediment rules — that refuses to capture environment-dependent failures, negative claims about tools ("browser tools do not work" harden into refusals the agent cites against itself for months), transient errors, one-off narratives, and unresolved failures written up as reliable workflows (agent/background_review.py:332).

A content-filter scar worth knowing. The original skill-guidance wording ("After completing a complex task (5+ tool calls)…") tripped Anthropic's server-side filter on subscription OAuth credentials, surfacing as a billing-shaped HTTP 400. The reword is described in the code as "empirically validated, not understood" (agent/prompt_builder.py:203).

What the review fork actually is

_run_review_in_thread (agent/background_review.py:860) builds a forked AIAgent with a stack of invariants, each fixing a real bug:

PropertyWhy
max_iterations=16, tool whitelist {memory, skills}bounded cost; other tools denied at runtime
skip_memory=Truethe fork must not touch external memory providers (three leak sites)
_persist_disabled=True, _session_db=Nonethe curator-takeover root cause: otherwise the harness prompt is written into the user's real session and re-read next turn as a standing instruction, making the agent "become" the curator
cached system prompt inherited (same model)prefix-cache hit — cited ~26% end-to-end cost reduction
compression_enabled=Falsesharing session_id means a compression race would fork the parent
dangerous-command approvals auto-deniedprevents an input() deadlock against the TUI

Same-model reviews replay the full snapshot; a routed cheaper model replays a compact digest instead. Writes land on disk, provenance is stamped in .usage.json, an audit entry lands in .curator_ledger.jsonl, the skills prompt cache is cleared so the just-written skill is visible next turn, and the user sees 💾 Self-improvement review: <actions>.

Skill self-improvement during use

There is no critique loop and no semver bumping — self-improvement is instruction plus telemetry:

  • The system prompt's SKILLS_GUIDANCE: "When using a skill and finding it outdated, incomplete, or wrong, patch it immediately with skill_manage(action='patch') — don't wait to be asked. Skills that aren't maintained become liabilities." (agent/prompt_builder.py:212). The tool schema declares patch the preferred action; edit is for major overhauls only.
  • Foreground path: the live agent calls skill_manage(action='patch', old_string, new_string) on the skill it just used — a unique-match requirement guards it (tools/skill_manager_tool.py:1069).
  • Autonomous path: the end-of-turn fork re-reads the loaded skill with skill_view, then patches — only if the skill passes the ownership guards below.
  • "Versioning" is a reuse-after-patch signal in telemetry: bump_patch increments patch_generation, and a subsequent successful use flips reuse_after_patch true, evidencing the improvement stuck (tools/skill_usage.py:864). Recoverability comes from the per-mutation ledger and pre-run tarball snapshots, not frontmatter versions.

The ownership guards — how the agent can only improve what it owns

The autonomous half prefers UPDATE over CREATE, made safe by five guards (tools/skill_manager_tool.py:301):

  1. Ownership guard — no-op for foreground agents; for the fork it refuses, in order: pinned, external-dir, protected builtin, hub-installed, bundled, and finally not-curator-managed. A missing telemetry record and an explicit created_by: null resolve identically — otherwise "allowed exactly once" would be a race with the guard's own bookkeeping. The refusal names the escape hatch: hermes curator adopt <name>.
  2. Read-before-write guard — the fork may only patch a path it actually skill_view'd this turn, never content inferred from the transcript (tools/skill_manager_tool.py:424).
  3. Consolidation-delete guard — during a review/curator pass, delete requires a non-empty absorbed_into=<umbrella>; a past fail-open pass once archived whole clusters of active skills (tools/skill_manager_tool.py:463).
  4. Delete → archive, never rmtree, during autonomous passes (recoverable .archive/).
  5. Org-mirror guard — org-shared skills are editable (edits go to a personal mirror and reach the org via hermes sync propose) but not deletable. The docstring is the clearest statement of the whole philosophy: blocking every write "broke the learning loop exactly where it matters most" (tools/skill_manager_tool.py:699).

Provenance is the mechanism underneath: a ContextVar set once per turn marks writes as assistant_tool vs background_review, so the curator only ever consolidates skills the agent autonomously created — a user-directed create gets created_by: null and belongs to the user (tools/skill_provenance.py:3).

Memory nudges

_turns_since_memory increments per user turn, hydrates from persisted history on resume so a restart doesn't reset the clock, and at memory.nudge_interval (default 10) arms should_review_memory (agent/turn_context.py:703). The nudge is not injected into the conversation — the prologue explicitly preserves the original user message; the flag rides through to the finalizer, which spawns the same fork.

The prompt (_MEMORY_REVIEW_PROMPT) is short: save persona/preferences/personal details and expectations about how the agent should behave (agent/background_review.py:248). Memory is two Markdown files, not SQLite: ~/.hermes/memories/MEMORY.md (agent notes) and USER.md (user profile), delimited by §, bounded by character limits (tools/memory_tool.py:53). The load-bearing design is the frozen snapshot: files are injected at session start; mid-session writes update disk immediately (durable) but do not change the system prompt, preserving the prefix cache for the whole session (tools/memory_tool.py:11). Guidance draws a sharp line: reusable procedures belong in a skill, task progress belongs in session search, and memories must be declarative facts ("User prefers concise responses" ✓) not imperatives ("Always respond concisely" ✗).

Session search / cross-session recall

Transcripts live in the SQLite state DB with an FTS5 external-content index plus a trigram index for CJK/substring search (hermes_state_common.py:483). The agent-facing tool makes no LLM calls — every shape returns actual DB rows (tools/session_search_tool.py:1128): DISCOVERY (FTS with adaptive hydration of only the top hit), SCROLL (a window around a message), READ (a whole session), BROWSE (recent). Notable behaviors: cron sessions demoted below interactive results to fix "recall blindness" where a high-volume cron corpus starved user sessions under bare BM25; lineage dedup so compression continuations don't return the same conversation N times; and an explicit anti-hallucination clause forbidding "no prior correspondence" conclusions from search alone when a direct source was given.

The "LLM summarization" lives adjacent, not in the search path: LLM-generated session titles (agent/title_generator.py:74) that are themselves searchable, plus compaction summaries written into the message stream and therefore FTS-indexed. SESSION_SEARCH_GUIDANCE tells the model to recall before asking the user to repeat themselves.

Honcho dialectic user modeling

An optional external provider (plugins/memory/honcho/__init__.py:262) selected by memory.provider. Per turn: on_turn_start → prefetch_all (base context + a dialectic supplement, each on its own cadence) → the recalled text is composed into the API copy of the user message only, wrapped in a <memory-context> block marked "recalled memory context, NOT new user input", and stamped as api_content so it never enters the clean transcript → sync_all + queue_prefetch_all on a serialized background worker so a wedged provider can't stall the turn.

The dialectic itself runs up to three peer.chat() passes — a cold/warm opening question, a self-audit ("what gaps remain?"), and a reconciliation ("do these cohere?") — bailing early on strong signal (plugins/memory/honcho/__init__.py:1170). It renders up to five blocks — Session Summary, User Representation, User Peer Card, AI Self-Representation, AI Identity Card — the literal "deepening model of who you are". The background review fork is built with skip_memory=True precisely so it never writes the harness prompt into the user's real Honcho namespace.

The curator — the slower library-level loop

Not a cron daemon — it is polled at CLI startup and in the gateway housekeeping loop (agent/curator.py:1). It runs when curator.enabled ∧ not paused ∧ last_run_at older than interval_hours (default 7 days), with an idle gate. Two passes:

  • Pass 1 — deterministic, no LLM. Walks usage: active → stale after 30 days idle, → archived after 90, reactivating on re-use. Skips pinned, cron-referenced, and young-unused skills ("a use=0 skill is absence of evidence, not evidence of staleness") (agent/curator.py:305).
  • Pass 2 — LLM consolidation, OFF by default (curator.consolidate: False). When on, it forks an agent with the CURATOR_REVIEW_PROMPT (agent/curator.py:432) to build umbrella skills — cluster prefix-related skills, merge into or create umbrellas, demote narrow siblings to references/. "One broad umbrella skill with labeled subsections beats five narrow siblings for discoverability." It requires a structured YAML summary listing every archived skill, reconciled against what actually happened on disk, with a pre-run tarball snapshot as a safety net.

The adopt CLI is the documented escape hatch the refusals point at, and its own docstring explains why adoption can never be automatic: "a high patch count proves the agent MAINTAINS a skill, not that it AUTHORED it" (hermes_cli/curator.py:344). The plan skill is a protected builtin, exempt on every path.

Honest caveats for the reader

  • Nudges are counters, not prompt injections — the live conversation never sees them.
  • LLM consolidation is off by default — out of the box a curator run does only the deterministic prune; the dramatic curator prompt runs only when opted in.
  • No embeddings anywhere in skill routing — 60-char descriptions + frontmatter filters. FTS5 is keyword/BM25/trigram, not vector.
  • "LLM summarization" for session search = LLM-generated session titles + indexed compaction summaries; the search tool makes no LLM calls.
  • Skill "versioning" is telemetry + ledger + tarball snapshots, not semver frontmatter.
  • hermes_cli/curator.py curates skills, not memory; memory consolidation is forced by the char limit and done by the model in-band.
