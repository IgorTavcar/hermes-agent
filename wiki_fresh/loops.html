Inner & Outer Loops

The heart of Hermes is two loops: an outer loop that owns a session — intake, queueing, steering, interrupts, nudges, cron wakeups, idle lifecycle — and an inner loop that owns a turn — one LLM call plus one tool batch, repeated under an iteration budget until the model produces plain text. This page walks both in algorithmic detail, with the actual loop bodies and the ordering invariants that make them safe.

The loop stack

There are really four nested control layers, plus a retry sub-loop:

Outer loop: intake and the three-level busy guard

Every inbound message crosses three gates before it can start a turn:

  1. Adapter guard (synchronous). If the session already has an entry in _active_sessions, the message goes to the busy handler instead of the runner (gateway/platforms/base.py:6151). Photo bursts merge, text may debounce, otherwise the message lands in the per-session pending slot (gateway/platforms/base.py:6182). For an idle session the guard is installed before the task spawn to close the race — the code cites grammY's sequentialize pattern (gateway/platforms/base.py:6190).
  2. Runner busy handler. _handle_active_session_busy_message (gateway/run.py:9945) decides steer vs redirect vs interrupt vs queue (next section).
  3. Turn lease. SessionTurnLeaseRegistry holds an asyncio.Lock per resolved session_id — not routing key — so two routing keys mapped to one session serialize; timeout raises and the caller must not enter the load/run/flush region: fail closed (gateway/turn_lease.py:191).

Queueing is a single head slot with album-merge semantics plus an overflow FIFO behind it (gateway/run.py:9852). The historical bug is documented inline: the old overwrite path silently mashed two user messages into one turn (gateway/run.py:9853).

Outer loop: steer / redirect / interrupt

The busy handler resolves an effective mode from display.busy_input_mode ∈ {interrupt, queue, steer} (default interrupt, gateway/run.py:9369) and then applies two safety demotions: interrupt is demoted to queue when subagents are active — an interrupt cascades into children and would destroy minutes of work — and when compression is in flight (gateway/run.py:10112, gateway/run.py:10123).

VerbSemanticsWhere
steer(text)Appends guidance to the last tool result at the next iteration boundary. Never kills anything.run_agent.py:3381, applied at gateway/run.py:10162
redirect(text)Aborts only the in-flight model request (never a running tool — it degrades to steer while tools execute, run_agent.py:3457) and re-anchors the turn on the new text.run_agent.py:3417, applied at gateway/run.py:10180
interrupt(text)Kills the model request and fans the interrupt out to all tool worker threads and children.run_agent.py:3180

The queue-unless-consumed invariant: if not steered and not redirected: queue it — a successful steer must never also be replayed as a next-turn user message (gateway/run.py:10200). A separate 200 ms poller inside the run task peeks (never pops) pending interrupts, so a message is never lost if the agent finishes first (gateway/run.py:28437).

Outer loop proper: the recursive turn chain

The outer loop is tail recursion bounded by depth, not a while. After a turn returns, the runner drains follow-ups in priority order — pending queue, then result["interrupt_message"] (unless it is a control interrupt like "Stop requested", gateway/run.py:3356), then leftover /steer text — and recurses with _interrupt_depth + 1, capped at _MAX_INTERRUPT_DEPTH = 3 (gateway/run.py:25773, recursion at gateway/run.py:29307).

There is a second, adapter-level drain for follow-ups that land after the runner returned: it spawns a fresh task rather than awaiting recursively, because the old await chain grew one C-stack frame per follow-up and segfaulted around 2000 (gateway/platforms/base.py:6765). Crucially it .clear()s the guard Event but never deletes the _active_sessions entry — deleting would admit a second concurrent agent on the same session key (gateway/platforms/base.py:6768).

Outer loop: nudges (the learning-loop trigger)

Two counters drive the self-improvement machinery (detailed on Self-Adaptive Skills):

  • Memory nudge — turn-counted. _turns_since_memory increments per user turn; at memory.nudge_interval (default 10) it arms should_review_memory (agent/turn_context.py:704). The counter is hydrated from persisted history on session resume so a restart doesn't reset the clock (agent/turn_context.py:655).
  • Skill nudge — iteration-counted. _iters_since_skill increments once per API call inside the inner loop (agent/conversation_loop.py:1989) and is evaluated at turn end (agent/turn_finalizer.py:771). Both counters reset whenever the corresponding tool is actually used (agent/tool_executor.py:667).

When either fires, the finalizer forks a background review agent after delivery (agent/turn_finalizer.py:791) — a daemon thread with tools restricted to memory + skills. A still-running review from the previous turn is cancelled at the top of the next turn so two forks never make concurrent API calls on the same credentials (agent/conversation_loop.py:1780).

Nudges are not prompt injections. The turn prologue explicitly preserves the original user message (agent/turn_context.py:700); the nudge is a boolean flag that spawns an out-of-band fork. The live conversation never sees it.

Outer loop: scheduled cron wakeups

The ticker is a daemon-thread loop inside the gateway process (cron/scheduler_provider.py:559) with a 60 s interval, exponential backoff on consecutive failures, and — deliberately — except BaseException, so a SystemExit escaping a provider SDK cannot silently kill scheduling. Each tick() (cron/scheduler.py:6730): reap dead-owner executions → collect due jobs → sweep stale in-flight claims → advance next_run_at first, under the file lock (at-most-once semantics, cron/scheduler.py:6901) → partition workdir-mutating jobs onto a sequential pool → claim at execution start, not submit time (cron/scheduler.py:6935) → run.

A cron turn runs run_conversation on a single-worker pool with a copied contextvar context so the ticker thread can watchdog it on idle seconds — not wall clock — and hard-interrupt on inactivity (cron/scheduler.py:5639). Cron sets skip_background_review=True: review forks cost ~30K tokens per event and cron has no human in the loop (agent/turn_finalizer.py:788). A global ESTOP file pauses all new dispatch without killing in-flight work (agent/estop.py:1).

Outer loop: idle behavior & session lifecycle

  • Per-turn inactivity watchdog — a thread (so it survives event-loop starvation) polling seconds_since_activity; timeout default 1800 s of idle time, so a busy turn can legally run for hours (gateway/run.py:3320). Activity is stamped at every meaningful point: API call start, stream chunk received, tool start, tool results posted, backoff heartbeats (run_agent.py:3918).
  • Session reset/expiry — mode ∈ {none, idle, daily, both}; both paths refuse to expire a session that still has live background processes (gateway/session.py:2424, gateway/session.py:2326).
  • Scale-to-zero — when idle (no in-flight turn, no inbound, no background work), the gateway goes dormant and self-suspends via the Fly Machines socket, because the Fly proxy judges idleness on inbound connections only and cannot see an in-flight turn (gateway/scale_to_zero.py:1). Wakeups deliver a synthetic internal MessageEvent, or a self-POST for stateless adapters (gateway/wake.py:1).
  • Other outer loops — /loop recurring in-session wakeups that fire only while the session is idle (hermes_cli/loops.py:1), and the Ralph-style kanban goal loop (hermes_cli/goals.py:2189).

Inner loop: header, budget, and steer drain

Entry is run_conversation at agent/conversation_loop.py:1704. The prologue (build_turn_context, agent/turn_context.py:431) does everything once-per-turn: sanitize, hydrate nudge counters, restore-or-build the system prompt, run preflight compression, fire the pre_llm_call hook, prefetch external memory, and allocate a fresh IterationBudget. Then the loop head, verbatim:

while (api_call_count < agent.max_iterations and agent.iteration_budget.remaining > 0) or agent._budget_grace_call:
    _redirect_text = agent._drain_pending_redirect()
    ...
    agent._checkpoint_mgr.new_turn()
    if agent._interrupt_requested:
        interrupted = True; break
    api_call_count += 1
    agent._touch_activity(f"starting API call #{api_call_count}")
    ...budget consume or break...

(agent/conversation_loop.py:1922.) The budget (agent/iteration_budget.py:17) is a lock-guarded counter with consume()/refund(); the gateway raises max_iterations to 500 (gateway/run.py:2042), and each subagent gets an independent budget (default 50), so total iterations across a delegation tree can exceed the parent cap.

A steer that arrived during the previous API call is drained before request assembly and appended to the last role:"tool" message so the model sees it on this iteration; on a first iteration with no tool message, it is put back rather than breaking role alternation (agent/conversation_loop.py:2005).

Inner loop: request assembly

  1. Sanitize tool-call arguments with a prefix cursor so already-validated history isn't re-parsed every iteration (agent/conversation_loop.py:2062).
  2. Drop legacy ghost interrupt-scaffold rows (agent/conversation_loop.py:2081).
  3. Repair role alternation (tool → user, user → user tails) and recompute the flush cursor (agent/conversation_loop.py:2109).
  4. Build api_messages by structural clone — never msg.copy() — so in-place transforms can't corrupt the durable transcript (agent/conversation_loop.py:2118).
  5. Pre-API compression gate (below), then per-provider prompt-cache re-decoration and _build_api_kwargs (agent/conversation_loop.py:2807), then a whole-payload surrogate sanitization chokepoint (agent/conversation_loop.py:2832).

Inner loop: retry sub-loop and the API call

Each iteration runs while retry_count < max_retries (default 3, agent/conversation_loop.py:2741) with a fresh TurnRetryState holding ~16 one-shot recovery guards plus four restart signals (agent/turn_retry_state.py:33). Streaming is the default; the call is dispatched through middleware to either the interruptible streaming transport or relay_llm.execute (agent/conversation_loop.py:3019).

The trickiest ordering guarantee is the redirect-crossing window: _model_request_active is set and cleared under the same lock redirect() observes, so a response and a redirect that cross on different threads cause the now-stale response to be discarded, never silently delivered (agent/conversation_loop.py:3056). Inside a stream, the chunk loop touches activity per chunk, checks the interrupt flag, and closes the stream on the owning thread — abandoning a half-read SSE response would permanently leak the pooled connection (agent/chat_completion_helpers.py:4038).

Backoff sleeps in 200 ms slices so interrupts land immediately and 30 s activity touches keep the watchdog fed (agent/conversation_loop.py:6415). After the retry loop, every restart signal — redirected, compressed, rebuilt-on-fallback, length-continuation — rewinds api_call_count and refunds the budget, so a rebuilt request never costs an iteration (agent/conversation_loop.py:6452).

Inner loop: compaction triggers & token accounting

Post-response, usage is normalized into canonical buckets and fed to context_compressor.update_from_response (agent/conversation_loop.py:4028). Three compaction trigger sites share one compression_attempts counter (cap 3):

  1. Turn-prologue preflight — with a "defer to real usage" guard so a noisy rough estimate doesn't trigger compaction the provider's own prompt count would refute (agent/turn_context.py:860).
  2. Pre-API mid-turn preflight — because a single turn can balloon on tool results while the post-response gate only sees lagging counts (agent/conversation_loop.py:2557). A lock-skip refunds the attempt: a defer is not evidence about compressibility.
  3. Post-tool-batch gate — on real prompt tokens only (reasoning tokens inflate completion counts and caused premature compaction), with a sentinel for "compaction just ran, no reading yet" and a schema-inclusive rough estimate as last resort (agent/conversation_loop.py:7305).

When over threshold but blocked, a deterministic LLM-free prune of old tool results runs instead (agent/context_compressor.py:3691). The compression budget rearms only on provider-confirmed recovery — a real prompt count below threshold on the request immediately after compaction (agent/conversation_loop.py:4021). The decision threshold is (context_length − max_tokens) × threshold_percent (default 0.50), with an 85% ratio fallback so small-context models can ever compact (agent/context_compressor.py:2768).

Inner loop: response handling

The branch is simply if assistant_message.tool_calls: (agent/conversation_loop.py:6820).

Tool-call path runs a validation ladder — duplicate-id uniquify, fuzzy name repair, mixed-batch partial erroring, 3-strike all-invalid handling, JSON arg validation, truncation detection, invalid-JSON recovery injected as tool-role results (never user messages: role alternation) — then the two invariants: the assistant message is appended and flushed to SQLite before any tool executes (a destructive tool can restart Hermes; resume logic must see the exact tool-call block that ran, agent/conversation_loop.py:7161), and a flush failure aborts the turn rather than executing from process-local state. Batches consisting only of execute_code refund their iteration (agent/conversation_loop.py:7288).

Final-response path is an ordered ladder of continuation gates, each able to set final_response = None and continue: codex intermediate-ack continuation (cap 2), length-continuation joining, dropped-tool-call re-prompt (cap 3, agent/conversation_loop.py:7926), scaffolding strip, verify-on-stop nudge, pre_verify hook nudge, kanban terminal-tool nudge — then terminate (agent/conversation_loop.py:8156). An empty-response recovery ladder runs first: partial-stream salvage → cached housekeeping content → post-tool nudge → thinking prefill → bounded empty retries with a deterministic-empty detector → fallback provider (agent/conversation_loop.py:7473).

The outer except classifies errors by walking traceback module names: a deterministic local-processing bug would fail identically every iteration and only burn budget, so it stops immediately; API errors retry. Either way, orphaned tool_call_ids get error results filled in (agent/conversation_loop.py:8180).

Inner loop: finalization

finalize_turn (agent/turn_finalizer.py:120): if a verification gate withheld an answer and the budget then ran out, that exact answer is reused rather than paying for another fallible call; otherwise budget exhaustion triggers one extra toolless API call asking for a summary (agent/turn_finalizer.py:192). Then: persist, return leftover steer as pending_steer, clear interrupts, evaluate the skill nudge, sync external memory, spawn the background review, fire on_session_end, and return the result dict (final_response, exit reason, token buckets, cost, flags).

Tool execution layer

Dispatch selection (run_agent.py:8170): a single call runs sequential; a batch is planned into segments — maximal contiguous parallel-safe runs separated by sequential barriers, preserving the model's emission order exactly (agent/tool_dispatch_helpers.py:117). Path-scoped tools carry reader/writer reservations: reader↔reader overlap commutes, any writer overlap closes the run; search_files reserves its root as a reader so a search after a write into that subtree is ordered behind it.

  • Concurrent executor (agent/tool_executor.py:1048): up to 8 workers on a DaemonThreadPoolExecutor — daemon because a wedged non-daemon worker would block interpreter exit forever (agent/tool_executor.py:1458). A start-order gate serializes dispatch by submit order even though execution is parallel, so approval prompts appear in order; on gate timeout it proceeds out of order rather than starving (agent/tool_executor.py:1200).
  • Deadlines: 420 s batch default, with human-approval wait time excluded from the deadline (agent/tool_executor.py:1526). On abandon: shutdown(wait=False, cancel_futures=True) — wedged workers are left detached rather than deadlocking the batch (agent/tool_executor.py:1622).
  • Results: pre-allocated slots appended in original call order — wall-clock completion order never leaks into the transcript (agent/tool_executor.py:1172). Every tool_call_id gets exactly one result on every path: success, error, skip, cancel, timeout, interpreter shutdown.
  • Untrusted-output framing: results from high-risk tools (web, browser, MCP) are wrapped in semantic delimiters marking them as data, not instructions — the single-chokepoint defense against indirect prompt injection (agent/tool_dispatch_helpers.py:534).
  • Steer injection happens after the whole batch and after budget enforcement, so a steer marker can never be truncated by output budgeting (agent/tool_executor.py:1855).
