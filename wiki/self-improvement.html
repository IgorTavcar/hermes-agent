The Closed Learning Loop: How Hermes Adapts Over Time

Most agents are stateless between sessions: every conversation starts from the same blank system prompt. Hermes is designed around the opposite premise — that the artifacts of one conversation should change the prompt of the next. This page traces each adaptation mechanism concretely: what fires it, what it reads and writes, where the result persists, and exactly how that persisted state re-enters a future prompt. Some of these form a genuinely closed loop today; others are real but human-in-the-loop, and a couple are honestly aspirational. We mark which is which.

Key insight. A "learning loop" is only closed when the output of one turn is written to durable storage and then automatically read back into a later prompt without a human re-typing it. Hermes has several mechanisms that meet that bar (memory writes, skill creation, frozen-snapshot recall) and several that assist a human-driven loop (session search, insights reporting). The honest distinction is the whole point of this page.

What a closed loop means here

Every mechanism below is an instance of the same three-stage pattern. It is worth holding this template in mind, because the differences between the mechanisms are entirely in where each stage lives.

Trigger
What causes the adaptation to run — a turn counter crossing a threshold, a tool call, a compression event, or an explicit user command.
Read / write
What state the mechanism consults and what durable artifact it produces (a Markdown file, a SQLite row, a skill directory, a remote representation).
Persistence
Where the artifact lives across sessions, and crucially, whether it survives a process restart with no human involvement.
Feedback
The closing move: how the persisted artifact is re-injected into a future system prompt or recalled mid-conversation.

Two architectural facts shape every mechanism. First, memory is read into the system prompt as a frozen snapshot at session start: mid-session writes hit disk immediately and durably, but the in-context copy is not rebuilt until the next session, which preserves the model provider's prefix cache for the whole conversation (tools/memory_tool.py:11). Second, the heavier adaptation work (deciding what to remember, whether to write a skill) is deferred to a background fork that runs after the user's answer is delivered, so introspection never competes with the task for the model's attention (run_agent.py:11268).

Curated memory and self-nudges

The built-in memory provider is always present and cannot be removed; at most one external provider runs alongside it (agent/memory_provider.py:1, agent/memory_manager.py:104). It backs two bounded Markdown files in the profile's memories/ directory:

FileHoldsDefault bound
MEMORY.mdThe agent's own notes — environment facts, project conventions, tool quirks, things learned2200 chars
USER.mdWhat the agent knows about you — preferences, communication style, expectations, workflow habits1375 chars

The stores are deliberately bounded and curated rather than append-only logs (tools/memory_tool.py:5, tools/memory_tool.py:116). A write that would exceed the char limit is rejected with an explanatory error, forcing the model to consolidate rather than accumulate (tools/memory_tool.py:254). Entries are separated by a section-sign delimiter and edited by short unique-substring matching — there are no IDs to track, so the model adds, replaces, removes, or reads by content (tools/memory_tool.py:57). Character limits are used instead of token limits precisely because char counts are model-independent.

Trigger: the periodic nudge

Memory is not written only when the user says "remember this." A turn counter (_turns_since_memory) increments every user turn; when it reaches the configurable nudge interval (default 10), a memory review is flagged for that turn (run_agent.py:8308, run_agent.py:1203). A parallel counter, _iters_since_skill, tracks tool-calling iterations and flags a skill review at its own interval (run_agent.py:11252). Both intervals are config-driven and can be set to 0 to disable. The counters reset when the relevant tool is actually used, so an agent that just wrote a memory is not nagged again immediately (run_agent.py:7682).

Persistence and feedback

Writes are durable the instant they happen — the file on disk is updated immediately. But the copy the model is reasoning over is the frozen snapshot from session start, so the new entry does not become active context until the next session rebuilds the system prompt (tools/memory_tool.py:11). This is the closing edge of the loop: a preference saved to USER.md on Monday is part of the identity slot of Tuesday's first prompt, with no human re-statement. The system prompt itself is cached per session and only rebuilt after compression or a fresh session, which is what keeps the prefix cache stable (run_agent.py:8336).

The pre-compression flush

There is a second, event-driven write path. Before context compression, a session reset, or CLI exit, flush_memories() gives the model exactly one turn — with only the memory tool exposed — to persist anything worth keeping before the raw transcript is discarded (run_agent.py:6972). The injected flush prompt explicitly prioritizes "user preferences, corrections, and recurring patterns over task-specific details," and all flush artifacts are stripped from the message list afterward so they never pollute the transcript (run_agent.py:6999). This is a real closed-loop edge: information about to be lost to compression is salvaged into durable memory automatically.

The background review fork

The nudge counters do not interrupt the conversation. Instead, after the response is delivered and only if the turn was not interrupted, Hermes spawns a daemon thread that forks a full second agent to do the introspection (run_agent.py:11268, run_agent.py:2358). This is the engine that drives both curated-memory writes and autonomous skill creation, so it is worth understanding in detail.

The fork is a complete AIAgent with the same model and provider, capped at 8 iterations, running in quiet mode with stdout/stderr redirected to /dev/null so it produces no visible output (run_agent.py:2388). It shares the parent's memory and skill stores by reference, and its own nudge intervals are zeroed so it cannot recurse (run_agent.py:2395). The parent's conversation snapshot is passed as conversation_history, and one of three review prompts is appended as the next user turn (run_agent.py:2401).

The prompts are concrete and skeptical. The memory prompt asks whether the user revealed persona, preferences, or behavioral expectations; the skill prompt asks whether a non-trivial approach was used that required trial and error or course correction; the combined prompt asks both. All three end with the same escape hatch: "If nothing is worth saving, just say 'Nothing to save.' and stop" (run_agent.py:2323, run_agent.py:2344). After the fork runs, the parent scans the fork's tool results for successful create/update/add actions and surfaces a compact one-line summary (for example, 💾 User profile updated) so the user sees that learning happened without seeing the deliberation (run_agent.py:2408).

Surprising design. Hermes uses a second, hidden instance of itself to decide what the first instance should learn. The introspection runs on the user's own model with the full conversation as context, but writes to shared storage on a background thread — so the cost is a few extra tokens after the answer is already on screen, not added latency to the reply.

Autonomous skill creation

Skills are Hermes's procedural memory — narrow, actionable "how to do this specific kind of task" knowledge — as distinct from the broad declarative facts in MEMORY.md and USER.md (tools/skill_manager_tool.py:10). A skill is a directory with a SKILL.md (YAML frontmatter plus a body) and optional references/, templates/, scripts/, and assets/ subdirectories (tools/skill_manager_tool.py:22).

Trigger and write

The skill-review branch of the background fork fires when _iters_since_skill crosses the skill nudge interval — that is, after a turn that took many tool iterations, which is a proxy for "this was a hard, multi-step task" (run_agent.py:11252). The fork is handed the skill review prompt and the conversation; if it judges the approach reusable, it calls skill_manage(action='create') to write a new skill into ~/.hermes/skills/ (tools/skill_manager_tool.py:6). If a relevant skill already exists, the prompt directs it to update that one instead (run_agent.py:2334).

Caveat. Agent-created skills get the same security scrutiny as community installs. Every write is scanned by the skills guard; a "dangerous" or "ask" verdict blocks the skill outright and returns the scan report rather than silently writing it (tools/skill_manager_tool.py:56). Autonomous authorship does not mean unaudited authorship.

Persistence and feedback

The new skill lives on disk in the local skills directory, the single source of truth for user skills (tools/skill_manager_tool.py:81). On the next session, the prompt builder scans every SKILL.md and folds its name and one-line description into a compact, cached skill index in the system prompt (agent/prompt_builder.py:583). That index carries a mandatory instruction: scan the listed skills before replying and load any that are even partially relevant with skill_view(name) (agent/prompt_builder.py:777). So a skill the agent wrote for itself yesterday becomes a discoverable, loadable capability today — a closed loop whose currency is procedural knowledge rather than facts.

Skills that self-improve during use

The previous mechanism creates skills after the fact. This one improves them in the moment they are used, and it is one of the cleaner closed loops in the system. The skill index header that ships in every system prompt contains two standing instructions beyond "load relevant skills" (agent/prompt_builder.py:789):

If a skill has issues, fix it with skill_manage(action='patch').
After difficult/iterative tasks, offer to save as a skill.
If a skill you loaded was missing steps, had wrong commands, or needed
pitfalls you discovered, update it before finishing.

Because this guidance is in the prompt of the primary agent (not the background fork), the agent is directed to correct a skill while still inside the task that exposed the flaw. The patch action does a targeted find-and-replace inside SKILL.md or any supporting file, so the agent can surgically fix a wrong command or add a newly discovered pitfall without rewriting the whole skill (tools/skill_manager_tool.py:17). The next agent that loads that skill reads the corrected version straight from disk — no re-derivation of the fix required.

Key insight. This is the tightest loop in Hermes: the artifact being read (the skill) and the artifact being written (the patched skill) are the same file, and the write happens during the very task that revealed the defect. A wrong command discovered at 2pm is gone for every future invocation by 2:05pm, persisted on disk, with the human only optionally in the loop.

FTS5 session search and cross-session recall

Memory and skills capture distilled knowledge. Session search provides recall over the raw history: every past conversation transcript is stored in SQLite and made searchable through an FTS5 full-text index (tools/session_search_tool.py:1). This is recall, not background learning — it fires when the model decides it needs it.

Flow

The session_search tool has two modes. With no query it lists recent sessions (titles, previews, timestamps) at zero LLM cost. With a query it runs the FTS5 search, groups the top matches into unique sessions, and then — rather than dumping raw transcripts into the main context — summarizes each matching session with a cheap auxiliary model and returns focused recaps (tools/session_search_tool.py:297, tools/session_search_tool.py:175). Several details make this robust:

  • Match-centered truncation. Each session is truncated to ~100k chars around a window chosen to maximize coverage of the query's actual hit positions, biased 25% before / 75% after each match (tools/session_search_tool.py:90).
  • Lineage resolution. Child sessions created by compression or delegation are walked back to their root parent, and the current conversation's lineage is excluded — the agent already has that context (tools/session_search_tool.py:356).
  • Parallel summarization with graceful fallback. Sessions are summarized concurrently; if the summarizer is unavailable, the matched session falls back to a raw preview rather than being silently dropped (tools/session_search_tool.py:468).

Feedback into the prompt

The tool description tells the model to search proactively on cues like "we did this before," "remember when," or "last time," and even when it suspects it solved a similar problem before (tools/session_search_tool.py:511). The returned summaries enter the working context as a tool result. This makes the loop pull-based and conversational: recall happens because the model reached for it, not because a counter expired. It is a genuine cross-session capability — the search spans all prior sessions — but it closes the loop only when the model elects to query.

SOUL, USER.md, and the insights model

The model the agent holds of itself and of you spans three artifacts, each filling a different slot.

SOUL.md
The agent's identity, loaded as slot #1 of the system prompt when present (agent/prompt_builder.py:893, run_agent.py:3349). On first run a default template is seeded into HERMES_HOME (hermes_cli/default_soul.py:3). It is user-authored persona, not auto-learned — editing it changes who the agent is for every future session.
USER.md
The agent's model of you, written by the curated-memory loop described above and re-injected as the frozen snapshot on each session start. This is the auto-learned half of the self/user model.
Insights
An analytical model of your usage, not your identity. InsightsEngine queries the session database to produce token consumption, cost estimates, tool-usage patterns, and activity trends, surfaced via the /insights command (agent/insights.py:1, agent/insights.py:93).
Worth being precise here. SOUL.md and USER.md feed directly back into future prompts and are part of the closed loop. The insights engine is a reporting layer — it reads the database and renders a report for the human; nothing it computes is automatically written back into the agent's prompt. It informs your decisions about the agent, which is valuable, but it is not a self-improvement loop in the strict sense.

Honcho dialectic user modeling

The optional Honcho plugin is the most sophisticated user-modeling backend, slotting in as the single allowed external memory provider (plugins/memory/honcho/__init__.py:1). Where USER.md is a bounded local file, Honcho maintains an AI-native, server-side representation of each peer and reasons over it dialectically. It runs in one of three recall modes — context (auto-inject only), tools (model queries explicitly), or hybrid (plugins/memory/honcho/__init__.py:478).

Five tools, two layers of recall

The plugin exposes honcho_profile (read/write a peer card), honcho_search (semantic excerpts, no synthesis), honcho_reasoning (synthesized dialectic answer at a chosen depth), honcho_context (raw session snapshot), and honcho_conclude (persist or delete a conclusion) (plugins/memory/honcho/__init__.py:34). Recall assembles two layers each turn: a cached base context (user representation + peer card, refreshed on a configurable cadence) and a dialectic supplement produced by the reasoning engine (plugins/memory/honcho/__init__.py:506).

The dialectic itself

"Dialectic" here is literal: _run_dialectic_depth runs up to three conditional .chat() passes against the user's representation (plugins/memory/honcho/__init__.py:769). Pass 0 is a cold-start or session-scoped query ("Who is this person?"); pass 1 is a self-audit that hunts for gaps in pass 0; pass 2 is a reconciliation pass that resolves contradictions between the prior two into a final synthesis (plugins/memory/honcho/__init__.py:710). A signal-sufficiency heuristic bails early when a pass already returned a structured, substantive answer, capping cost (plugins/memory/honcho/__init__.py:749).

How it closes the loop

Completed turns are recorded into Honcho on a background thread, chunked to fit the API's message limit, and writes to the built-in USER.md are mirrored as Honcho conclusions so the two stores stay consistent (plugins/memory/honcho/__init__.py:860, plugins/memory/honcho/__init__.py:891). On the next session the base context and a pre-warmed dialectic query ("What should I know about this user?") are fetched at init, so the model arrives with a synthesized profile already in context (plugins/memory/honcho/__init__.py:394). Notably, Honcho is fully disabled in cron and subagent contexts to avoid corrupting the user representation with non-conversational system prompts (plugins/memory/honcho/__init__.py:272).

Dependency and cost caveat. Honcho is an optional, separately configured plugin (API key or self-hosted base URL) and is inactive unless installed and enabled (plugins/memory/honcho/__init__.py:228). Its dialectic passes are real LLM calls with real cost; the cadence, depth, and reasoning-level caps exist precisely to bound that spend. The closed loop it provides is strongest where it is configured — out of the box, the built-in memory loop is what runs.

The full learning loop

After the answer is delivered, nudge counters may spawn the background review fork, which writes durable artifacts. Those artifacts re-enter the system prompt at the start of the next session.

Honest ledger: real loop vs aspiration

Not every mechanism on this page closes the loop to the same degree. The table below states, per mechanism, whether the persisted output re-enters a future prompt automatically (a real closed loop), whether it assists a human-driven loop, or whether it remains aspirational.

MechanismTriggerCloses automatically?Notes
Curated memory + nudgeTurn counter (default 10)YesWrite to disk durable immediately; re-injected as frozen snapshot next session (run_agent.py:8308).
Pre-compression flushCompression / reset / exitYesOne-turn save salvages soon-to-be-lost context into durable memory (run_agent.py:6972).
Autonomous skill creationTool-iteration counterYesBackground fork writes skill; appears in next session's skill index (run_agent.py:11252). Security-scanned (tools/skill_manager_tool.py:56).
Skills self-improving in useDefect found while skill is loadedYesTightest loop: patch the same file mid-task; next load reads the fix (agent/prompt_builder.py:789).
FTS5 session recallModel elects to searchPartialGenuine cross-session recall, but pull-based — closes only when the model queries (tools/session_search_tool.py:511).
SOUL.md identityUser edits the filePartialFeeds every future prompt, but human-authored, not auto-learned (agent/prompt_builder.py:893).
Insights engine/insights commandNoReporting layer — informs the human, not written back into the prompt (agent/insights.py:1).

The real closed loop, stated plainly. Four mechanisms close the loop with no human required: curated-memory nudges, the pre-compression flush, autonomous skill creation, and in-use skill self-improvement. All four share the same backbone — a turn/iteration counter or a compression event triggers a write to a durable on-disk artifact, which is read back into a later prompt as either the frozen memory snapshot or the skill index. Session search and SOUL.md are real and valuable but human- or model-initiated; the insights engine is reporting, not adaptation. Honcho is a genuine closed loop when you choose to wire it in.

The aspirational edge is honesty about quality, not existence. The loops described here move artifacts mechanically and reliably; whether the agent's judgment about what to remember, what to skillify, and how to patch a skill improves over time depends on the underlying model's discrimination, not on any guarantee in the harness. Hermes builds the closed circuit; the model decides what to send around it.
