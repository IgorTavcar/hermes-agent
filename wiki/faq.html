Research Answers & FAQ

Three headline questions drove this research: can you point Hermes at your Anthropic Claude Code Max/20x, OpenAI ChatGPT/Codex, or xAI Grok subscription instead of paying per-token for an API key? The short version is that all three are technically wired into Hermes, but only one of them is something the provider actually permits. Below, each headline question gets a verdict badge, a crisp answer, a concrete “how to,” and a Terms-of-Service caveat — followed by a broader FAQ on Copilot, Qwen/Gemini, Nous, how to escape per-token billing, the legal/risk picture, and the single safest path.

Q1 — Anthropic Claude Code (Pro / Max 5x / Max 20x) subscription vs API key

Partial — works, but violates Anthropic ToS

Technically yes, policy-wise no. Hermes has a fully built-out path to drive a Claude Pro/Max subscription: it accepts CLAUDE_CODE_OAUTH_TOKEN / claude setup-token output / the Claude Code credential file, ships its own native PKCE login (“Authorize Hermes with your Claude Pro/Max subscription”), and will happily make subscription-backed inference calls. But it only works by impersonating Anthropic’s first-party Claude Code client. Per Anthropic’s own Legal & Compliance docs, OAuth/subscription credentials are “intended exclusively” for native Anthropic applications, and Anthropic began technically blocking and suspending exactly these spoofing harnesses starting January 2026. The only unambiguously legitimate Anthropic option is a pay-as-you-go Console API key (sk-ant-api…).

Key insight. “Hermes accepts the credential” and “Anthropic permits the usage” are two different statements. Hermes’ acceptance is implemented through first-party-client impersonation that Anthropic explicitly disallows and is actively enforcing against — so the credential works while the usage is forbidden.

How to

Legitimate (recommended) — Console pay-as-you-go API key. Get an sk-ant-api… key from console.anthropic.com, then export ANTHROPIC_API_KEY=sk-ant-api... (or put it in Hermes’ .env). Hermes routes this via the x-api-key header — the non-OAuth branch in agent/anthropic_adapter.py:292-296 — with no Claude Code spoofing. Clean, supported, billed per-token under the Commercial Terms.

Subscription (technically works, but violates ToS — not recommended). Any of: (a) export CLAUDE_CODE_OAUTH_TOKEN=$(claude setup-token); (b) export ANTHROPIC_TOKEN=<oauth token>; (c) simply having ~/.claude/.credentials.json from a claude login (Hermes auto-reads and refreshes it); or (d) Hermes’ own login that opens claude.ai/oauth/authorize and stores creds in ~/.hermes/.anthropic_oauth.json. All four make Hermes send subscription-backed requests disguised as Claude Code.

ToS caveat. Anthropic’s Legal & Compliance doc states OAuth/subscription auth is “intended exclusively” for native Anthropic apps and that Anthropic “does not permit third-party developers to … route requests through Free, Pro, or Max plan credentials.” Enforcement is active, not theoretical: since January 2026 Anthropic has blocked subscription-token support in OpenCode, Roo, Goose, Cursor, Manus, and Pi, and reportedly suspended accounts “without prior notice” (The Register, 2026-02-20). Your token can be revoked or your subscription account banned.

Why it only works via impersonation

A plain Authorization: Bearer sk-ant-oat01-… to the Messages API returns 401 "OAuth authentication is currently not supported" (badlogic/pi-mono #2751). To be accepted, Hermes mimics the first-party fingerprint inside agent/anthropic_adapter.py:281-291: Bearer auth plus a spoofed user-agent: claude-cli/{version}, x-app: cli, and the anthropic-beta: claude-code-20250219,oauth-2025-04-20 headers. The token-resolution chain lives in agent/anthropic_adapter.py:552-580 (env + Claude Code credential file), with a shell-out to claude setup-token at agent/anthropic_adapter.py:596-633 and the Hermes-native PKCE flow (client_id 9d1c250a-…, prompt at agent/anthropic_adapter.py:682) at agent/anthropic_adapter.py:640-755. The request transforms at agent/anthropic_adapter.py:1281-1318 prepend a “You are Claude Code” system prompt and prefix tool names with mcp_.

An admission in the code. The brand-string rewrites at agent/anthropic_adapter.py:1292 (Hermes Agent→Claude Code, Nous Research→Anthropic) carry the literal comment “to avoid Anthropic’s server-side content filters.” The integration is knowingly adversarial to Anthropic’s gating, not a sanctioned interop. Verified directly in the working tree.

One nuance worth flagging: Anthropic’s June 15, 2026 Agent SDK subscription credit (Pro $20 / Max 5x $100 / Max 20x $200) is the only Anthropic-blessed way to spend a subscription on agent usage — but it flows through the native Agent SDK authenticating to your own plan. It is not a license for a third-party harness like Hermes to spoof Claude Code.

Q2 — OpenAI ChatGPT / Codex subscription vs API key

Yes — subscription is the primary supported path

Yes — you can drive OpenAI Codex models in Hermes with just your ChatGPT subscription (Plus/Pro/Team/Business/Enterprise/Edu), with no OpenAI API key. Hermes ships a first-class openai-codex provider (auth_type oauth_external) that runs OpenAI’s own “Sign in with ChatGPT” device-code + PKCE flow and routes inference through https://chatgpt.com/backend-api/codex — the same subscription-billed endpoint the official Codex CLI uses. The access token is the credential; there is no API-key path for Codex models in Hermes at all. This is OpenAI-endorsed for personal use (Romain Huet, OpenAI, ~March 2026: “use Codex and their ChatGPT subscription wherever they like”), and the Codex CLI is Apache-2.0 with permissive ToS.

Key insight. For OpenAI’s own models, the subscription route is the primary supported path in Hermes, not an afterthought. There is no generic openai API-key provider in the registry — pay-per-token access to OpenAI models is only reachable indirectly via OpenRouter or Vercel AI Gateway.

How to

Option A — let Hermes run the OAuth (no API key, no Codex CLI needed). Run hermes auth (or hermes login) and pick “OpenAI Codex.” This triggers _codex_device_code_login() (hermes_cli/auth.py:2910), which POSTs to https://auth.openai.com/api/accounts/deviceauth/usercode with client_id app_EMoamEEZ73f0CkXaXp7hrann, shows you https://auth.openai.com/codex/device plus a user code, polls for the authorization code, and PKCE-exchanges it at https://auth.openai.com/oauth/token. Tokens land in Hermes’ own store ~/.hermes/auth.json (auth_mode chatgpt) and auto-refresh.

Option B — reuse an existing Codex CLI login. Sign in to the official Codex CLI so ~/.codex/auth.json exists; Hermes imports/migrates those tokens automatically via _import_codex_cli_tokens (hermes_cli/auth.py:1494). At runtime resolve_codex_runtime_credentials() (hermes_cli/auth.py:1528) returns the access token as api_key against the backend base, mapped to api_mode codex_responses (hermes_cli/runtime_provider.py:769). Optional env vars: HERMES_CODEX_BASE_URL, CODEX_HOME, HERMES_CODEX_REFRESH_TIMEOUT_SECONDS.

What this is not: an OpenAI Platform API key (sk-…). If you specifically want pay-per-token API access to OpenAI models, route them through OpenRouter (OPENROUTER_API_KEY) or Vercel AI Gateway (AI_GATEWAY_API_KEY) — that is metered billing on a different account.

ToS caveat. Honest single-user reuse of your own ChatGPT subscription is the endorsed/tolerated zone. Multi-account pooling, shared-service deployment, or reselling access is a clear violation and ban risk — an OpenAI maintainer (etraut-openai, Discussion #8338) explicitly declined to bless the multi-user/commercial “bring your own subscription” model. The chatgpt.com/backend-api/codex endpoint is also undocumented/“semi-official” and can change without notice, and subscription Codex is rate-limited per rolling ~5-hour window.
A verified gap. Hermes sets no originator header (first-party clients default to codex_cli_rs) and no chatgpt-account-id header on Codex requests — the default_headers branches in run_agent.py:958-1041 only add custom headers for OpenRouter/Copilot/Kimi/Qwen, never for the Codex backend. Codex requests go out as a bare Authorization: Bearer <token>. There are public reports of third-party OAuth Codex calls hitting 429 "quota exceeded" where first-party clients do not; if OpenAI starts enforcing originator-based gating, Hermes’ Codex requests could begin failing until that header is added.

Q3 — xAI Grok CLI / subscription vs API key

Integrated No subscription / no Grok-CLI path

xAI/Grok is integrated in Hermes, but only as a plain API-key provider against api.x.ai/v1. There is no xAI OAuth, no device-code/login flow, and no integration with xAI’s own “Grok Build” CLI or SuperGrok subscription. In the registry, xAI is auth_type="api_key", base https://api.x.ai/v1, env XAI_API_KEY, override XAI_BASE_URL (hermes_cli/auth.py:218-225, verified directly). A targeted grep for any xai/grok-tied oauth/device/login/PKCE dispatch returned nothing; tools/xai_http.py is a 13-line User-Agent helper with no auth logic. A consumer SuperGrok/X subscription cannot be used as programmatic credentials — that requires a separate console.x.ai pay-per-token account.

Key insight. xAI’s own end-to-end CLI agent (“Grok Build,” a ~May-2026 subscription-gated product) is a separate xAI product that Hermes does not bundle, wrap, or authenticate against in any way. So “is there a subscription path in Hermes?” is simply no — API key only.

How to

  1. Create a developer API key at https://console.x.ai/ (xAI’s pay-per-token API account — not a SuperGrok/X chat subscription). The signup URL Hermes surfaces is this developer console (hermes_cli/config.py:849-852).
  2. export XAI_API_KEY=xai-... (or save it via Hermes’ .env). XAI_API_KEY is the sole env var for this provider.
  3. Optionally export XAI_BASE_URL=https://api.x.ai/v1 (already the default).
  4. Select an xAI/Grok model — aliases grok, x-ai, x.ai all resolve to xai (hermes_cli/auth.py:931, hermes_cli/providers.py:185-187). Defaults include grok-4.20-reasoning and grok-4-1-fast-reasoning (hermes_cli/models.py:147-150).

Alternative path: you can reach grok-code-fast-1 via OpenRouter (Hermes’ default fall-through) using OPENROUTER_API_KEY instead of an xAI key — it appears in Hermes’ OpenRouter model list (hermes_cli/models.py:125).

ToS caveat. Using a consumer SuperGrok/X login as programmatic API credentials would violate xAI ToS — and it is technically impossible in Hermes anyway, since the code provides no mechanism to consume a Grok chat-subscription session. Only a console.x.ai pay-per-token XAI_API_KEY (or OpenRouter) is accepted.
Quirk. At runtime xAI is routed through Hermes’ Codex Responses API adapter — hermes_cli/runtime_provider.py:933-934 sets api_mode="codex_responses" for provider=="xai". This affects request format only; auth remains a plain XAI_API_KEY bearer and implies no OAuth/subscription linkage to Codex.

GitHub Copilot subscription

Yes — subscription works via GitHub device-code OAuth

Despite being registered as auth_type="api_key" (hermes_cli/auth.py:125-132), the copilot provider ships a real GitHub device-code OAuth flow, so a GitHub Copilot subscription works as a model backend. copilot_device_code_login() (hermes_cli/copilot_auth.py:155-275) runs the GitHub OAuth device flow with client_id Ov23li8tweQw6odWQebz (the same one used by opencode and the Copilot CLI), scope read:user, and saves the resulting gho_ token via save_env_value("COPILOT_GITHUB_TOKEN", token). Token resolution checks COPILOT_GITHUB_TOKEN → GH_TOKEN → GITHUB_TOKEN then falls back to gh auth token (hermes_cli/copilot_auth.py:67-150). Supported token prefixes are gho_ (OAuth), github_pat_ (fine-grained PAT with Copilot Requests permission), and ghu_ — classic ghp_ PATs are rejected.

A second variant, copilot-acp (auth_type="external_process", base acp://copilot, hermes_cli/auth.py:133-139), holds no token at all — it shells out to the Copilot CLI (copilot --acp --stdio) and delegates auth entirely to whatever that process is logged into (agent/copilot_acp_client.py:256-347).

Caveat. Copilot requests carry editor-spoofing headers (Editor-Version: vscode/…, Copilot-Integration-Id: vscode-chat, hermes_cli/copilot_auth.py:280-299). As with Anthropic, driving a Copilot subscription from a non-official client relies on presenting first-party-editor identity; treat GitHub’s acceptable-use terms as the binding constraint.

Qwen & Gemini OAuth

Qwen — subscription via Qwen CLI session   Gemini — API key only

Qwen-OAuth

Qwen is a real subscription/OAuth provider (oauth_external, base https://portal.qwen.ai/v1, hermes_cli/auth.py:119-124), but it does not mint its own tokens. Instead it reads and refreshes the Qwen CLI’s credential file ~/.qwen/oauth_creds.json (hermes_cli/auth.py:1088-1109); if it is missing, Hermes errors with “Run ‘qwen auth qwen-oauth’ first.” Refresh POSTs grant_type=refresh_token with client_id f0304373b74a44d2b584a3fb70ca9e56 to https://chat.qwen.ai/api/v1/oauth2/token and writes the rotated pair back to the Qwen CLI file (hermes_cli/auth.py:1131-1200). So Qwen piggybacks on an existing Qwen CLI login rather than running its own device flow.

Gemini

Gemini is plain api_key — OpenAI-compatible base https://generativelanguage.googleapis.com/v1beta/openai, env GOOGLE_API_KEY / GEMINI_API_KEY (hermes_cli/auth.py:140-147). There is no OAuth and no Google subscription login; a Google AI Studio API key is the only credential.

Nous Portal subscription

Yes — the canonical first-party subscription provider

Nous is the one provider where subscription auth is fully native and uncontested. It is registered as oauth_device_code (hermes_cli/auth.py:104-112) with client_id hermes-cli, scope inference:mint_agent_key, and portal https://portal.nousresearch.com. The device-code login opens the portal verification URL, and at runtime Hermes refreshes the OAuth access token then mints a short-lived inference key via _mint_agent_key() (hermes_cli/auth.py:1749-1779) — a POST to {portal}/api/oauth/agent-key with a default 1800s TTL, cached and reused until near expiry (hermes_cli/auth.py:1839-1843). The minted agent key (not the OAuth token) is what hits inference-api.nousresearch.com/v1.

A separate nous_subscription.py layer maps the Nous subscription to managed tool features — web search, image generation, TTS (including the “xAI TTS” label at hermes_cli/nous_subscription.py:146), browser, and modal execution — gated on Nous auth status (hermes_cli/nous_subscription.py:41-71).

Key insight. Because hermes-cli is the registered OAuth client for the Nous portal, there is no impersonation and no ToS gray area here — this is the provider the harness was designed around.

Is any of this against ToS / risky?

Yes for two of the providers, and the risk is concrete, not hypothetical.

Anthropic (high risk)
Routing a Pro/Max subscription through Hermes violates the Consumer Terms of Service. Anthropic has blocked subscription-token support in OpenCode, Roo, Goose, Cursor, Manus, and Pi since January 2026, and reportedly suspended accounts “without prior notice.” The path only functions via first-party impersonation, which the code itself describes as dodging Anthropic’s content filters (agent/anthropic_adapter.py:1292). Real risk of token revocation or account ban.
OpenAI Codex (conditional)
Honest single-user reuse of your own ChatGPT subscription is endorsed. Multi-account pooling, shared deployment, or reselling is a clear ToS violation and ban risk. The undocumented backend endpoint can also change or gate non-official clients at any time.
GitHub Copilot (low–moderate)
Works through GitHub’s device-code OAuth, but presents editor-spoofing identity headers. Treat GitHub’s acceptable-use terms for Copilot as binding; personal single-user use is the safe zone.
xAI / Grok (none in Hermes)
No subscription mechanism exists to misuse — Hermes only accepts a pay-per-token API key. The only way to violate xAI ToS would be to attempt credential sharing, which the code provides no path for.
Nous, Qwen, Gemini, and all API-key providers (clean)
Nous is first-party. Qwen reuses an existing sanctioned CLI login. Gemini and the rest are ordinary API keys billed per-token. No gray area.
Bottom line on risk. The dangerous moves are (1) pointing Hermes at a Claude Pro/Max subscription, and (2) pooling or reselling any subscription (Codex especially). Both can cost you the account, not just the request.

What’s the safest, fully-supported path?

If your priority is “nothing that risks an account suspension or relies on impersonation,” here is the ranked guidance.

  1. Nous Portal subscription — the cleanest subscription option. Native OAuth, first-party client, short-lived minted keys. No ToS gray area (hermes_cli/auth.py:104-112).
  2. Anthropic Console API key (sk-ant-api…) — the only legitimate way to use Claude models in Hermes. Routed via x-api-key with no spoofing (agent/anthropic_adapter.py:292-296), billed per-token under the Commercial Terms.
  3. OpenAI Codex via your own ChatGPT subscription — fully supported in Hermes and endorsed by OpenAI for personal single-user use. Stay single-user; do not pool or share.
  4. Any plain API-key provider (Gemini, xAI, DeepSeek, Kimi, Z.AI, MiniMax, OpenRouter, AI Gateway, …) — ordinary metered billing, no policy entanglement.
The one thing to avoid. Do not drive an Anthropic Claude Pro/Max subscription through Hermes on an account you care about. It works mechanically, but it depends on impersonating Claude Code, violates Anthropic’s Consumer Terms, and is the exact pattern Anthropic has been blocking and suspending since January 2026. For Anthropic models, use a Console API key.
Quick decision rule. Want a subscription and zero risk? Use Nous. Want Claude models the legitimate way? Buy a Console API key. Want OpenAI models on a subscription? Sign in with your own ChatGPT account and keep it single-user. Want Grok? It’s API key only.
