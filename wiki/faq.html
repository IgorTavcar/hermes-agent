Research Answers & FAQ

Three headline questions drove this research: can you point Hermes at your Anthropic Claude Code Max/20x, OpenAI ChatGPT/Codex, or xAI Grok subscription instead of paying per-token for an API key? The short version is that all three are technically wired into Hermes, but only one of them is something the provider actually permits. Below, each headline question gets a verdict badge, a crisp answer, a concrete “how to,” and a Terms-of-Service caveat — followed by a broader FAQ on Copilot, Qwen/Gemini, Nous, how to escape per-token billing, the legal/risk picture, and the single safest path.

Q1 — Anthropic Claude Code (Pro / Max 5x / Max 20x) subscription vs API key

Partial — works, but violates Anthropic ToS

Technically yes, policy-wise no. Hermes has a fully built-out path to drive a Claude Pro/Max subscription: it accepts CLAUDE_CODE_OAUTH_TOKEN / claude setup-token output / the Claude Code credential file, ships its own native PKCE login (“Authorize Hermes with your Claude Pro/Max subscription”), and will happily make subscription-backed inference calls. But it only works by impersonating Anthropic’s first-party Claude Code client. Per Anthropic’s own Legal & Compliance docs, OAuth/subscription credentials are “intended exclusively” for native Anthropic applications, and Anthropic began technically blocking and suspending exactly these spoofing harnesses starting January 2026. The only unambiguously legitimate Anthropic option is a pay-as-you-go Console API key (sk-ant-api…).

Key insight. “Hermes accepts the credential” and “Anthropic permits the usage” are two different statements. Hermes’ acceptance is implemented through first-party-client impersonation that Anthropic explicitly disallows and is actively enforcing against — so the credential works while the usage is forbidden.

How to

Legitimate (recommended) — Console pay-as-you-go API key. Get an sk-ant-api… key from console.anthropic.com, then export ANTHROPIC_API_KEY=sk-ant-api... (or put it in Hermes’ .env). Hermes routes this via the x-api-key header — the non-OAuth else branch in agent/anthropic_adapter.py:811-815 — with no Claude Code spoofing. Clean, supported, billed per-token under the Commercial Terms.

Subscription (technically works, but violates ToS — not recommended). Any of: (a) export CLAUDE_CODE_OAUTH_TOKEN=$(claude setup-token); (b) export ANTHROPIC_TOKEN=<oauth token>; (c) simply having ~/.claude/.credentials.json from a claude login (Hermes auto-reads and refreshes it); or (d) Hermes’ own login that opens claude.ai/oauth/authorize and stores creds in ~/.hermes/.anthropic_oauth.json. All four make Hermes send subscription-backed requests disguised as Claude Code.

ToS caveat. Anthropic’s Legal & Compliance doc states OAuth/subscription auth is “intended exclusively” for native Anthropic apps and that Anthropic “does not permit third-party developers to … route requests through Free, Pro, or Max plan credentials.” Enforcement is active, not theoretical: since January 2026 Anthropic has blocked subscription-token support in OpenCode, Roo, Goose, Cursor, Manus, and Pi, and reportedly suspended accounts “without prior notice” (The Register, 2026-02-20). Your token can be revoked or your subscription account banned.

Why it only works via impersonation

A plain Authorization: Bearer sk-ant-oat01-… to the Messages API returns 401 "OAuth authentication is currently not supported" (badlogic/pi-mono #2751). To be accepted, Hermes mimics the first-party fingerprint in the OAuth branch of build_anthropic_client at agent/anthropic_adapter.py:800-810: Bearer auth plus a spoofed user-agent: claude-cli/{version}, x-app: cli, and the anthropic-beta: claude-code-20250219,oauth-2025-04-20 headers. The token-resolution chain lives in agent/anthropic_adapter.py:1159-1200 (env + Claude Code credential file), with a shell-out to claude setup-token at agent/anthropic_adapter.py:1203-1243 and the Hermes-native PKCE flow (client_id 9d1c250a-…, prompt “Authorize Hermes with your Claude Pro/Max subscription.” at agent/anthropic_adapter.py:1294) at agent/anthropic_adapter.py:1270-1378. The request transforms at agent/anthropic_adapter.py:2328-2369 prepend a “You are Claude Code” system prompt (the _CLAUDE_CODE_SYSTEM_PREFIX constant at agent/anthropic_adapter.py:374) and prefix tool names with mcp_.

An admission in the code. The brand-string rewrites at agent/anthropic_adapter.py:2343-2346 (Hermes Agent→Claude Code, Nous Research→Anthropic) carry the literal comment “to avoid Anthropic’s server-side content filters” (agent/anthropic_adapter.py:2338-2339). The integration is knowingly adversarial to Anthropic’s gating, not a sanctioned interop. Verified directly in the working tree.

One nuance worth flagging: Anthropic’s June 15, 2026 Agent SDK subscription credit (Pro $20 / Max 5x $100 / Max 20x $200) is the only Anthropic-blessed way to spend a subscription on agent usage — but it flows through the native Agent SDK authenticating to your own plan. It is not a license for a third-party harness like Hermes to spoof Claude Code.

Q2 — OpenAI ChatGPT / Codex subscription vs API key

Yes — subscription is the primary supported path

Yes — you can drive OpenAI Codex models in Hermes with just your ChatGPT subscription (Plus/Pro/Team/Business/Enterprise/Edu), with no OpenAI API key. Hermes ships a first-class openai-codex provider (auth_type oauth_external) that runs OpenAI’s own “Sign in with ChatGPT” device-code + PKCE flow and routes inference through https://chatgpt.com/backend-api/codex — the same subscription-billed endpoint the official Codex CLI uses. The access token is the credential; there is no API-key path for Codex models in Hermes at all. This is OpenAI-endorsed for personal use (Romain Huet, OpenAI, ~March 2026: “use Codex and their ChatGPT subscription wherever they like”), and the Codex CLI is Apache-2.0 with permissive ToS.

Key insight. For OpenAI’s own models, the subscription route is the primary supported path in Hermes, not an afterthought. There is no generic openai API-key provider in the registry — pay-per-token access to OpenAI models is only reachable indirectly via OpenRouter or Vercel AI Gateway.

How to

Option A — let Hermes run the OAuth (no API key, no Codex CLI needed). Run hermes auth (or hermes login) and pick “OpenAI Codex.” This triggers _codex_device_code_login() (hermes_cli/auth.py:6925), which POSTs to https://auth.openai.com/api/accounts/deviceauth/usercode with client_id app_EMoamEEZ73f0CkXaXp7hrann, shows you https://auth.openai.com/codex/device plus a user code, polls for the authorization code, and PKCE-exchanges it at https://auth.openai.com/oauth/token. Tokens land in Hermes’ own store ~/.hermes/auth.json (auth_mode chatgpt) and auto-refresh.

Option B — reuse an existing Codex CLI login. Sign in to the official Codex CLI so ~/.codex/auth.json exists; Hermes imports/migrates those tokens automatically via _import_codex_cli_tokens (hermes_cli/auth.py:3676). At runtime resolve_codex_runtime_credentials() (hermes_cli/auth.py:3710) returns the access token as api_key against the backend base, mapped to api_mode codex_responses (hermes_cli/runtime_provider.py:309-311). Optional env vars: HERMES_CODEX_BASE_URL, CODEX_HOME, HERMES_CODEX_REFRESH_TIMEOUT_SECONDS.

What this is not: an OpenAI Platform API key (sk-…). If you specifically want pay-per-token API access to OpenAI models, route them through OpenRouter (OPENROUTER_API_KEY) or Vercel AI Gateway (AI_GATEWAY_API_KEY) — that is metered billing on a different account.

ToS caveat. Honest single-user reuse of your own ChatGPT subscription is the endorsed/tolerated zone. Multi-account pooling, shared-service deployment, or reselling access is a clear violation and ban risk — an OpenAI maintainer (etraut-openai, Discussion #8338) explicitly declined to bless the multi-user/commercial “bring your own subscription” model. The chatgpt.com/backend-api/codex endpoint is also undocumented/“semi-official” and can change without notice, and subscription Codex is rate-limited per rolling ~5-hour window.
Codex requests are now fingerprinted as first-party. The post-merge tree closes the gap an earlier read flagged: the chatgpt.com branch of the default_headers dispatch in run_agent.py:3857-3861 now attaches _codex_cloudflare_headers() (agent/auxiliary_client.py:503-539), which pins originator: codex_cli_rs and a matching User-Agent: codex_cli_rs/0.0.0 (Hermes Agent), and extracts a ChatGPT-Account-ID header out of the OAuth JWT’s chatgpt_account_id claim. The code comment is explicit that this is to dodge the Cloudflare layer that serves a 403 cf-mitigated: challenge to non-residential IPs (VPS / server-hosted agents) that don’t advertise an allowed first-party originator. So Codex requests now carry Codex-CLI identity, not a bare bearer — another instance of first-party-client fingerprinting, this time aimed at edge anti-abuse rather than auth.

Q3 — xAI Grok CLI / subscription vs API key

Integrated Subscription OAuth now exists (post-merge)

This is the answer the upstream merge changed most. xAI/Grok is still available as a plain API-key provider against api.x.ai/v1, but the merged tree also adds a real xAI OAuth provider, xai-oauth (registry name “xAI Grok OAuth (SuperGrok / Premium+)”, hermes_cli/auth.py:191-196). It runs a genuine browser-loopback PKCE flow — _xai_oauth_loopback_login() (hermes_cli/auth.py:6721), issuer https://auth.x.ai, client_id b1a00492-073a-47ea-816f-4c329264a828, scope openid profile email offline_access grok-cli:access api:access (hermes_cli/auth.py:99-105) — and at runtime resolve_xai_oauth_runtime_credentials() (hermes_cli/auth.py:4189) uses the refreshed OAuth access token as the credential. So a SuperGrok / Premium+ subscription can now drive Grok in Hermes via OAuth, not only via a pay-per-token key. The plain API-key path is unchanged: in the registry, xai is auth_type="api_key", base https://api.x.ai/v1, env XAI_API_KEY, override XAI_BASE_URL (hermes_cli/auth.py:349-356, verified directly).

Key insight (revised). The pre-merge fork had no xAI subscription path at all — API key only. The merge added a first-class xai-oauth provider that authenticates a SuperGrok / Premium+ subscription through xAI’s own grok-cli:access-scoped OAuth, alongside the still-present plain XAI_API_KEY route. So “is there a subscription path in Hermes?” is now yes.

How to

Option A — API key (pay-per-token).

  1. Create a developer API key at https://console.x.ai/ (xAI’s pay-per-token API account — not a SuperGrok/X chat subscription). The signup URL Hermes surfaces is this developer console (hermes_cli/config.py:2600-2607).
  2. export XAI_API_KEY=xai-... (or save it via Hermes’ .env). XAI_API_KEY is the sole env var for the plain-key xai provider.
  3. Optionally export XAI_BASE_URL=https://api.x.ai/v1 (already the default).
  4. Select an xAI/Grok model — aliases grok, x-ai, x.ai all resolve to xai (hermes_cli/auth.py:1504, hermes_cli/providers.py:251-253). The curated direct list is headed by grok-4.3, with grok-4.20-0309-reasoning / -non-reasoning variants (hermes_cli/models.py:110-115); the older grok-4.20-reasoning / grok-4-1-fast-reasoning / grok-code-fast-1 names were retired by xAI on 2026-05-15 and now map to grok-4.3 (hermes_cli/xai_retirement.py:23-32).

Option B — SuperGrok / Premium+ subscription OAuth. Run hermes auth add xai-oauth (aliases grok-oauth, x-ai-oauth, xai-grok-oauth, hermes_cli/providers.py:254-257). Hermes opens the browser-loopback PKCE flow against auth.x.ai; the refreshed access token is then used directly at runtime (hermes_cli/auth.py:4189). No XAI_API_KEY is needed on this path.

Alternative path: you can also reach x-ai/grok-4.3 via OpenRouter (Hermes’ default fall-through) using OPENROUTER_API_KEY instead of an xAI key — it appears in Hermes’ OpenRouter model list (hermes_cli/models.py:50).

ToS caveat. Unlike the pre-merge fork, Hermes now does provide a mechanism to consume a SuperGrok / Premium+ session — but it does so through xAI’s own grok-cli:access-scoped OAuth client, not by scraping a chat-session cookie, so this is xAI’s sanctioned CLI-agent auth surface rather than a spoof. Honest single-user reuse of your own subscription is the intended zone; sharing or pooling the OAuth credential would violate xAI ToS. The plain console.x.ai pay-per-token XAI_API_KEY (or OpenRouter) remains the other accepted route.
Quirk. At runtime both xAI paths are routed through Hermes’ Codex Responses API adapter — hermes_cli/runtime_provider.py:338-339 sets api_mode="codex_responses" for provider=="xai", and hermes_cli/runtime_provider.py:312-314 does the same for xai-oauth. This affects request format only; auth remains either a plain XAI_API_KEY bearer or the xAI OAuth token, and implies no linkage to OpenAI Codex.

GitHub Copilot subscription

Yes — subscription works via GitHub device-code OAuth

Despite being registered as auth_type="api_key" (hermes_cli/auth.py:217-224), the copilot provider ships a real GitHub device-code OAuth flow, so a GitHub Copilot subscription works as a model backend. copilot_device_code_login() (hermes_cli/copilot_auth.py:155-275) runs the GitHub OAuth device flow with client_id Ov23li8tweQw6odWQebz (the same one used by opencode and the Copilot CLI), scope read:user, and returns the resulting gho_ token (the caller persists it as COPILOT_GITHUB_TOKEN). Token resolution checks COPILOT_GITHUB_TOKEN → GH_TOKEN → GITHUB_TOKEN then falls back to gh auth token (resolve_copilot_token(), hermes_cli/copilot_auth.py:67-96). Supported token prefixes are gho_ (OAuth), github_pat_ (fine-grained PAT with Copilot Requests permission), and ghu_ — classic ghp_ PATs are rejected (hermes_cli/copilot_auth.py:35-36).

A second variant, copilot-acp (auth_type="external_process", base acp://copilot, hermes_cli/auth.py:225-231), holds no token at all — it shells out to the Copilot CLI (copilot --acp --stdio, args resolved at agent/copilot_acp_client.py:64-67) via subprocess.Popen in CopilotACPClient._run_prompt (agent/copilot_acp_client.py:438-462) and delegates auth entirely to whatever that process is logged into.

Caveat. Copilot requests carry editor-spoofing headers (Editor-Version: vscode/1.104.1, Copilot-Integration-Id: vscode-chat) built by copilot_request_headers() (hermes_cli/copilot_auth.py:382-388). As with Anthropic, driving a Copilot subscription from a non-official client relies on presenting first-party-editor identity; treat GitHub’s acceptable-use terms as the binding constraint.

Qwen & Gemini OAuth

Qwen — subscription via Qwen CLI session   Gemini — API key only

Qwen-OAuth

Qwen is a real subscription/OAuth provider (oauth_external, base https://portal.qwen.ai/v1, hermes_cli/auth.py:197-202), but it does not mint its own tokens. Instead it reads and refreshes the Qwen CLI’s credential file ~/.qwen/oauth_creds.json (hermes_cli/auth.py:1933-1959); if it is missing, Hermes errors with “Run ‘qwen auth qwen-oauth’ first” (hermes_cli/auth.py:1941). Refresh POSTs grant_type=refresh_token with client_id f0304373b74a44d2b584a3fb70ca9e56 to https://chat.qwen.ai/api/v1/oauth2/token and writes the rotated pair back to the Qwen CLI file (_refresh_qwen_cli_tokens(), hermes_cli/auth.py:2001-2070). So Qwen piggybacks on an existing Qwen CLI login rather than running its own device flow.

Gemini

The plain gemini provider is api_key — base https://generativelanguage.googleapis.com/v1beta, env GOOGLE_API_KEY / GEMINI_API_KEY (hermes_cli/auth.py:232-239); a Google AI Studio API key is its only credential. (The merge also added a separate google-gemini-cli OAuth provider, hermes_cli/auth.py:203-208, that reuses a Gemini-CLI login — but the plain key path above is the simplest.)

Nous Portal subscription

Yes — the canonical first-party subscription provider

Nous is the one provider where subscription auth is fully native and uncontested. It is registered as oauth_device_code (hermes_cli/auth.py:168-176) with client_id hermes-cli, scope inference:invoke (the NOUS_INFERENCE_INVOKE_SCOPE constant, hermes_cli/auth.py:73), and portal https://portal.nousresearch.com. The device-code login (_nous_device_code_login(), hermes_cli/auth.py:7502) opens the portal verification URL. The minting-via-separate-POST model the pre-merge fork used is gone: the merged tree instead treats the OAuth access token itself as an inference:invoke-scoped JWT and uses it directly as the inference credential. At runtime resolve_nous_runtime_credentials() (hermes_cli/auth.py:5268) refreshes that JWT, validates its inference:invoke scope, and returns it with source="invoke_jwt"; _set_nous_agent_key_from_invoke_jwt() (hermes_cli/auth.py:1855) derives the TTL straight from the JWT’s exp claim and reuses the token until it nears expiry. That invoke JWT is what hits inference-api.nousresearch.com/v1.

A separate nous_subscription.py layer maps the Nous subscription to managed tool features — web search, image generation, TTS (including the “xAI TTS” label at hermes_cli/nous_subscription.py:212), browser, and modal execution — gated on Nous auth status (get_nous_subscription_features(), with nous_auth_present at hermes_cli/nous_subscription.py:350).

Key insight. Because hermes-cli is the registered OAuth client for the Nous portal, there is no impersonation and no ToS gray area here — this is the provider the harness was designed around.

Which providers let me avoid per-token API billing?

Several providers in Hermes can be funded by a subscription rather than metered API tokens — Nous, OpenAI Codex, GitHub Copilot, Qwen-OAuth, and (added by the upstream merge) xAI xai-oauth. Only some of them are clean.

Is any of this against ToS / risky?

Yes for two of the providers, and the risk is concrete, not hypothetical.

Anthropic (high risk)
Routing a Pro/Max subscription through Hermes violates the Consumer Terms of Service. Anthropic has blocked subscription-token support in OpenCode, Roo, Goose, Cursor, Manus, and Pi since January 2026, and reportedly suspended accounts “without prior notice.” The path only functions via first-party impersonation, which the code itself describes as dodging Anthropic’s content filters (agent/anthropic_adapter.py:2338-2347). Real risk of token revocation or account ban.
OpenAI Codex (conditional)
Honest single-user reuse of your own ChatGPT subscription is endorsed. Multi-account pooling, shared deployment, or reselling is a clear ToS violation and ban risk. The undocumented backend endpoint can also change or gate non-official clients at any time.
GitHub Copilot (low–moderate)
Works through GitHub’s device-code OAuth, but presents editor-spoofing identity headers. Treat GitHub’s acceptable-use terms for Copilot as binding; personal single-user use is the safe zone.
xAI / Grok (low)
The merge added a real xai-oauth subscription path, but it authenticates through xAI’s own grok-cli:access OAuth client rather than by spoofing a chat session — so honest single-user reuse of your SuperGrok / Premium+ subscription sits in xAI’s intended zone. The risk is the usual one: sharing or pooling the OAuth credential (or a console.x.ai API key) would violate xAI ToS.
Nous, Qwen, Gemini, and all API-key providers (clean)
Nous is first-party. Qwen reuses an existing sanctioned CLI login. Gemini and the rest are ordinary API keys billed per-token. No gray area.
Bottom line on risk. The dangerous moves are (1) pointing Hermes at a Claude Pro/Max subscription, and (2) pooling or reselling any subscription (Codex especially). Both can cost you the account, not just the request.

What’s the safest, fully-supported path?

If your priority is “nothing that risks an account suspension or relies on impersonation,” here is the ranked guidance.

  1. Nous Portal subscription — the cleanest subscription option. Native OAuth, first-party client, the access token is the short-lived inference JWT. No ToS gray area (hermes_cli/auth.py:168-176).
  2. Anthropic Console API key (sk-ant-api…) — the only legitimate way to use Claude models in Hermes. Routed via x-api-key with no spoofing (agent/anthropic_adapter.py:811-815), billed per-token under the Commercial Terms.
  3. OpenAI Codex via your own ChatGPT subscription — fully supported in Hermes and endorsed by OpenAI for personal single-user use. Stay single-user; do not pool or share.
  4. xAI Grok via your own SuperGrok / Premium+ subscription — the new xai-oauth path uses xAI’s own grok-cli:access OAuth, so single-user reuse is in the sanctioned zone.
  5. Any plain API-key provider (Gemini, xAI, DeepSeek, Kimi, Z.AI, MiniMax, OpenRouter, AI Gateway, …) — ordinary metered billing, no policy entanglement.
The one thing to avoid. Do not drive an Anthropic Claude Pro/Max subscription through Hermes on an account you care about. It works mechanically, but it depends on impersonating Claude Code, violates Anthropic’s Consumer Terms, and is the exact pattern Anthropic has been blocking and suspending since January 2026. For Anthropic models, use a Console API key.
Quick decision rule. Want a subscription and zero risk? Use Nous. Want Claude models the legitimate way? Buy a Console API key. Want OpenAI models on a subscription? Sign in with your own ChatGPT account and keep it single-user. Want Grok on a subscription? The new xai-oauth path takes your own SuperGrok / Premium+ login (or use a console.x.ai API key).
