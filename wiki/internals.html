Surprising Internals: Fresh Engineering in Hermes

Hermes Agent is full of “huh, that’s clever” engineering where the non-obvious win is almost always one of three things: protecting the LLM’s context window, surviving real-world rate limits, or making stateless cloud backends behave like stateful shells. This page walks the standouts — what the mechanism is, and why it’s a genuinely good idea — starting with the headline feature, Programmatic Tool Calling, and working out through context compaction, credential rotation, six terminal backends, prompt caching, and the extensibility surface.

Programmatic Tool Calling: collapse N tool calls into one zero-context turn

The headline win. Instead of the model making ten separate tool calls — each round-tripping its full result back into the context window — the LLM writes a single Python script. That script imports an auto-generated hermes_tools.py stub module and calls real Hermes tools (web_search, read_file, terminal, patch, …) as ordinary Python functions. The agent spends one inference turn; the script may make up to 50 tool calls internally, and only the script’s stdout returns to the model — intermediate tool results never enter the context window tools/code_execution_tool.py:24-26.

Surprise. The entire purpose of execute_code is that intermediate tool outputs never touch the LLM’s attention. A 50-call pipeline — search, fetch, parse, filter, reduce, loop — costs exactly one inference turn, because the filtering and looping happen in Python outside the context window. This is “programmatic tool calling” done right.

One stub API, two interchangeable transports

What makes this engineering-interesting rather than merely a sandbox is that the same generated stub API runs over two completely different transports, chosen by whether the terminal backend is local or remote tools/code_execution_tool.py:8-26.

TransportMechanismWhy
Local (UDS)Parent opens an AF_UNIX socket, spawns the child, and runs an RPC listener thread. The stub’s _call() sends newline-delimited JSON over the socket and blocks for the reply tools/code_execution_tool.py:207-242; server loop at tools/code_execution_tool.py:307-413.Fast, in-process dispatch for the common case.
Remote (file-RPC)For Docker/SSH/Modal/Daytona the stub writes req_NNNNNN files atomically (write .tmp, then os.rename) and polls for res_NNNNNN, with adaptive backoff 50ms→250ms tools/code_execution_tool.py:256-294. A parent-side thread ls-es the remote RPC dir via env.execute() and dispatches through the same handle_function_call tools/code_execution_tool.py:564-696.No socket reaches into a sandbox; atomic file rename is the lowest-common-denominator IPC.

The remote path carries two battle-scar details. Responses are written base64-encoded specifically because “Modal doesn’t reliably deliver stdin to chained commands” tools/code_execution_tool.py:564-696. And on macOS the local socket is forced into /tmp because /var/folders/… paths blow past the 104-byte AF_UNIX path limit tools/code_execution_tool.py:955-959 — the kind of bug you only fix after hitting it.

The schema is prompt engineering too

The tool’s schema text is itself a small piece of prompt engineering. It tells the model exactly when to reach for this tool — “3+ tool calls with processing logic”, “filter/reduce large tool outputs before they enter your context”, branching, looping — and when not to (single call, needs the full result, interactive) tools/code_execution_tool.py:1357-1376. The generated stub even ships convenience helpers baked in — json_parse with strict=False, shell_quote, and a retry with exponential backoff — so LLM-authored scripts avoid the usual pitfalls tools/code_execution_tool.py:84-162.

Quiet correctness detail. Dispatched tool handlers have their stdout/stderr redirected to /dev/null during the RPC call, so a tool’s internal status prints don’t corrupt the CLI spinner tools/code_execution_tool.py:307-413.

Sandbox security: credential-stripped child env + head/tail output cap

The child process running LLM-authored code gets a deliberately minimal environment. The constructor walks os.environ and applies three rules: (1) always pass skill-declared passthrough vars, (2) drop anything whose name contains KEY|TOKEN|SECRET|PASSWORD|CREDENTIAL|PASSWD|AUTH, and (3) only allow known-safe prefixes (PATH, HOME, LANG, HERMES_, …) tools/code_execution_tool.py:994-1021.

Surprise. The script can call web_search and terminal, but it can never see the API keys that power them. The rationale is explicit in the code: “prevent credential exfiltration from LLM-generated scripts. The child accesses tools via RPC, not direct API.” The parent holds the keys and dispatches on the child’s behalf, so capability and credential are cleanly separated tools/code_execution_tool.py:994-1021.

The env is otherwise hand-curated: it injects only TZ (popping the internal HERMES_TIMEZONE) and can redirect HOME for per-profile isolation tools/code_execution_tool.py:1029-1043.

A 50KB cap that protects the answer

The stdout cap is not a naive head-only truncation. It splits the 50KB budget head+tail: 40% keeps the start, and 60% keeps a rolling deque of the end tools/code_execution_tool.py:1063-1089.

Key insight. A script’s final print() — usually the actual answer — lives at the end of stdout. A head-only cap would discard precisely the thing the model needs when a noisy middle blows the budget. The 40/60 head+tail split guarantees the answer survives. Stderr, where errors appear early, stays head-only.

Live context compaction: hash dedup, informative summaries, tool-pair repair

ContextCompressor is far smarter than the typical “summarize the middle” compactor. Before any LLM call, _prune_old_tool_results runs three cheap, structural passes that cost no inference at all agent/context_compressor.py:405-466.

Pass 1 — content-hash dedup

Walking backward, it MD5-hashes each tool result over 200 chars. The first (newest) occurrence is kept in full; older identical results are replaced with a back-reference, [Duplicate tool output — same content as a more recent call] agent/context_compressor.py:405-466.

Surprise. Reading the same file five times used to cost five full copies in context. After dedup it costs one full copy plus four one-line back-references — identified purely by content hash, so it catches duplicates even when the tool calls look different.

Pass 2 — information-bearing summaries, not placeholders

Old tool outputs become a typed one-liner that carries information, for example [terminal] ran `npm test` -> exit 0, 47 lines output or [search_files] content search for 'compress' in agent/ -> 12 matches. _summarize_tool_result has bespoke formatting for roughly 20 tool types and even regex-extracts the exit code or match count out of the raw result agent/context_compressor.py:66-185. The author explicitly contrasts this with “a generic placeholder that carries zero information.”

Pass 3 — argument truncation

A write_file with 50KB of content in its tool_call arguments would otherwise survive compression untouched, so large args outside the protected tail are clipped to ~200 chars agent/context_compressor.py:405-466.

The correctness gem: repairing orphaned tool pairs

After summarization you can end up with a tool result whose assistant tool_call was deleted, or vice-versa — both of which make the OpenAI/Anthropic API hard-reject the request (“No tool call found for function call output”). _sanitize_tool_pairs removes orphaned results and injects stub results for orphaned calls, so the message list is always well-formed agent/context_compressor.py:778-836.

Surprise. This is the subtle landmine most compactors miss: pruning messages can split a tool_call/tool_result pair, and the provider API will then 400 the entire request. Hermes repairs the pairing in both directions rather than just hoping the boundaries line up.

The summary itself is a structured checkpoint template (Active Task / Goal / Completed Actions / Active State / Blocked / Resolved vs Pending), framed for “a DIFFERENT assistant that continues the conversation” and told not to answer any questions in the transcript — a deliberate borrow from OpenCode/Codex framing agent/context_compressor.py:577-635. The summary budget scales with content size and model context (20% of compressed tokens, floored at 2000, capped at min(5% of context, 12000)) rather than a dead fixed cap agent/context_compressor.py:474-483.

Credential pool: OAuth refresh, soft leases, status-aware cooldowns

CredentialPool is a production-grade multi-key rotator, not a round-robin list. Four details stand out.

Status-aware cooldown TTLs

A 429 (rate-limited) cools a key down for 1 hour; other exhaustion uses a default TTL agent/credential_pool.py:192-196. Better still, it tries to compute an exact reset time from the provider: _normalize_error_context parses reset_at/resets_at/retry_until, and if those are absent, regex-extracts a retry after N seconds or quotaResetDelay from the error body, preferring that precise timestamp over the coarse TTL agent/credential_pool.py:229-275.

Cross-process token sync

For Anthropic claude_code and OpenAI Codex entries, before declaring a key exhausted it re-reads the on-disk credentials file — picking up tokens that the Claude Code CLI or another Hermes profile refreshed in a separate process agent/credential_pool.py:784-802.

Surprise. The pool shares OAuth tokens across processes by re-reading the credentials file at the last moment. So if the Claude Code CLI silently refreshed a token a minute ago, Hermes picks it up instead of marking a perfectly good key as dead. That’s the kind of safeguard you only add after getting burned by a stale token.

Soft leases for concurrency

acquire_lease picks the least-leased available credential (priority as tie-break) and, when every key is at the soft concurrency cap, still returns the least-loaded one instead of blocking agent/credential_pool.py:890-919. This spreads concurrent gateway sessions across keys without a hard semaphore. Selection strategy is pluggable — random, least-used, or round-robin, with round-robin re-ordering and persisting the entry list agent/credential_pool.py:837-858.

Rate-limit handling: killing retry amplification + jittered backoff

Two small files punch well above their weight. nous_rate_guard.py records a shared, atomically-written rate-limit state file so every session (CLI, gateway, cron, auxiliary) checks it before issuing a request.

Surprise. The comment quantifies the exact bug it kills: “Each 429 from Nous triggers up to 9 API calls per conversation turn (3 SDK retries x 3 Hermes retries), and every one counts against RPH” agent/nous_rate_guard.py:1-11. Recording the limit on the first 429 and short-circuiting the rest collapses a 9× amplification down to 1.

It parses the reset time in a clear priority order — hourly RPH header → per-minute RPM header → generic retry-after — and writes the state file via mkstemp + os.replace for atomicity agent/nous_rate_guard.py:38-67.

retry_utils.jittered_backoff then replaces fixed exponential backoff with decorrelated jitter so multiple sessions hitting the same provider don’t all retry on the same tick. It seeds the RNG from time_ns() ^ (counter * 0x9E3779B9) — the golden-ratio constant — behind a lock, so even a coarse clock produces distinct jitter per call agent/retry_utils.py:41-57. The companion rate_limit_tracker.py parses the full 12-header x-ratelimit-* schema into RPM/RPH/TPM/TPH buckets, with elapsed-time-adjusted remaining_seconds_now powering the /usage command agent/rate_limit_tracker.py:8-21.

Six terminal backends + serverless hibernation

BaseEnvironment abstracts six backends — local, Docker, Singularity, SSH, Modal, Daytona — behind one execute(). The non-obvious cleverness is how it fakes a persistent login shell on top of spawn-per-call remote sandboxes.

Faking a stateful shell

Session snapshot
Once at init it captures the login shell’s exported vars, functions, and aliases into a sourced file: export -p > snap; declare -f >> snap; alias -p >> snap tools/environments/base.py:315-336. Every later command sources that snapshot, then re-dumps env vars back into it (last-writer-wins), so an export FOO=bar in one call is visible in the next tools/environments/base.py:363-390.
CWD via stdout markers
Since each remote command is a fresh process, CWD can’t persist naturally. _wrap_command appends printf '\nMARKER%sMARKER\n' "$(pwd -P)"; the parent parses the marker out of stdout to track the working directory across calls tools/environments/base.py:363-390.
Surprise. Remote shells where each command is a brand-new process are made to behave like one persistent login shell — using a sourced env/function/alias snapshot plus in-band CWD markers smuggled through stdout. No daemon, no persistent connection required.

Serverless hibernation: snapshot on cleanup, restore next session

Cloud sandboxes auto-stop, so persistence is implemented as snapshot/restore rather than a long-lived box.

BackendPersistence mechanism
ModalOn cleanup() it calls sandbox.snapshot_filesystem(), stores the resulting image object_id keyed by task_id in a JSON store, then terminates; the next session restores from that snapshot id (with a legacy key-namespace migration) tools/environments/modal.py:402-433.
DaytonaPersistent sandboxes are stop()-ed (not deleted) on cleanup and start()-ed/resumed by name on the next creation, preserving the filesystem; auto_stop_interval=0 disables platform auto-stop so Hermes controls the lifecycle tools/environments/daytona.py:81-118.
Surprise. Filesystem persistence is faked on hibernating serverless sandboxes: snapshot the FS on cleanup, store the snapshot id against the task, and restore from it next time. The box dies between sessions; the work survives.

Transactional file sync

Underpinning the file-sync backends (SSH/Modal/Daytona) is FileSyncManager: mtime+size change detection, deletion tracking, 5s rate-limiting, and transactional commit with rollback — state is updated only if all uploads and deletes succeed, else it rolls back so the next cycle retries everything tools/environments/file_sync.py:101-168. Daytona’s bulk upload batches roughly 580 files into one multipart POST, cutting sync from about 5min to under 2s tools/environments/daytona.py:147-167. Docker and Singularity skip all of this — they bind-mount the live host filesystem.

Anthropic prompt caching: a rolling-window of breakpoints

A compact, correct implementation of the highest-leverage Anthropic cost optimization. apply_anthropic_cache_control places the 4 cache_control breakpoints (Anthropic’s maximum) as the system prompt — stable across every turn — plus the last 3 non-system messages as a rolling window agent/prompt_caching.py:41-71.

Key insight. The rolling tail means each new turn re-uses the cached prefix up to the previous breakpoint, so a multi-turn conversation gets roughly 75% input-token savings without ever managing cache state by hand.

_apply_cache_marker carefully handles every content shape — tool messages (marked only when native Anthropic), empty content, raw strings (promoted to a text block), and content lists (mark the last block) — and supports the 1h TTL marker agent/prompt_caching.py:15-38. It’s a pure function with no agent-state dependency, which makes it trivially testable.

Smart model routing + local-server fingerprinting

Two smaller-but-tasteful pieces. smart_model_routing.choose_cheap_model_route downshifts only truly trivial turns to a cheap model and is conservative by construction: it bails back to the primary model if the message exceeds char/word caps, has more than one newline, contains backticks or a URL, or matches any of ~40 complexity keywords (debug, refactor, traceback, pytest, docker, …) agent/smart_model_routing.py:11-46. Default thresholds are tight (160 chars / 28 words), and any runtime-resolution failure silently falls back to primary, returning a stable signature tuple used to detect whether the model actually changed agent/smart_model_routing.py:80-107.

model_metadata.detect_local_server_type fingerprints whatever local inference server is running by probing known endpoints in specificity order: LM Studio’s /api/v1/models first, then Ollama’s /api/tags (verifying the body actually contains models, because LM Studio returns 200 with an error body on that path), then llama.cpp’s /v1/props (with a /props fallback for old builds), then vLLM’s /version agent/model_metadata.py:308-364.

Graceful degradation. Each probe has a 2s timeout and swallows failures, so a misconfigured base_url degrades gracefully rather than hanging. The result feeds context-window detection, so a local model’s true context length is discovered rather than guessed.

Hooks, ACP adapter, and recursive toolset resolution

Three smaller systems round out the extensibility surface.

Filesystem-discovered hooks

Drop a directory with HOOK.yaml + handler.py into ~/.hermes/hooks/, declare lifecycle events, and the registry dynamically loads the module and registers handle() per event. The emit path supports wildcard fan-out (command:* fires for any command:…) and runs both sync and coroutine handlers, with every handler wrapped in try/except so “errors in hooks … never block the main pipeline” gateway/hooks.py:138-170. Built-in hooks like boot_md are registered separately so they’re always active gateway/hooks.py:54-67.

ACP adapter renders real diffs

The ACP adapter lets editors like Zed drive Hermes over the Agent Client Protocol. It maps every Hermes tool to an ACP ToolKind (read/edit/execute/fetch/think) and renders rich tool events: write_file and patch emit a proper diff content block via acp.tool_diff_content(old_text, new_text) so the editor shows a real inline diff, and terminal renders as $ command acp_adapter/tools.py:104-174. It also extracts file locations (path + line) from tool args so the editor can jump to them acp_adapter/tools.py:205-214.

Cycle-safe toolset resolution

Toolset resolution is recursive with composition (includes) and proper cycle/diamond handling: a shared visited set is threaded across sibling includes, so a diamond dependency resolves once and a true cycle silently returns [] rather than recursing forever; all/* expand to every toolset using fresh per-branch visited copies toolsets.py:447-497.
