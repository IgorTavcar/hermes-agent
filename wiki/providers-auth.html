Models, Providers & Authentication

Hermes routes inference through a single PROVIDER_REGISTRY of ~34 providers (hermes_cli/auth.py:167-442), each tagged with one of six auth types. Three of the headline questions users ask — "can I use my Claude Code / ChatGPT / Grok subscription instead of an API key?" — all resolve here. The short answers: Anthropic subscription OAuth works mechanically but violates Anthropic's ToS; an OpenAI ChatGPT subscription is a first-class, OpenAI-endorsed path for Codex models; and xAI/Grok now also ships a SuperGrok / Premium+ OAuth path (xai-oauth) alongside the plain API-key provider. This page maps the whole registry, then walks each provider's auth contract with verified verdicts.

PROVIDER_REGISTRY — full map

PROVIDER_REGISTRY is a Dict[str, ProviderConfig] defined at hermes_cli/auth.py:167. Each ProviderConfig (hermes_cli/auth.py:150-164) carries an id, name, auth_type, portal_base_url, inference_base_url, client_id, scope, an extra dict, api_key_env_vars (a priority-ordered tuple), and a base_url_env_var override. The registry is also auto-extended at import time with any api-key provider declared under providers/ (hermes_cli/auth.py:444-474).

Surprising design. The dataclass header comment lists four auth types (hermes_cli/auth.py:155: "oauth_device_code", "oauth_external", "oauth_minimax", or "api_key"), but the registry actually uses six: oauth_device_code, oauth_external, oauth_minimax (MiniMax), api_key, external_process (Copilot ACP), and aws_sdk (Bedrock). And two providers registered as api_key — Anthropic and Copilot — secretly carry full OAuth flows.

Anthropic — OAuth, CLAUDE_CODE_OAUTH_TOKEN & Claude Code spoofing

Partial Registered api_key, but Anthropic is the most elaborate auth path in Hermes. It accepts a regular Console key and a Claude Pro/Max subscription OAuth token, and it even runs its own native PKCE login.

Auth type
api_key (with full hidden OAuth machinery)
API key path
sk-ant-api… Console key → x-api-key header (clean, supported)
Subscription path
CLAUDE_CODE_OAUTH_TOKEN / ANTHROPIC_TOKEN / ~/.claude/.credentials.json / Hermes-native login → Authorization: Bearer with Claude Code identity spoofing
Env var order
ANTHROPIC_API_KEY → ANTHROPIC_TOKEN → CLAUDE_CODE_OAUTH_TOKEN (hermes_cli/auth.py:314)

How the token shape decides the header

get_anthropic_key() (hermes_cli/auth.py:483-498) walks the env-var tuple in order. At runtime the agent calls resolve_anthropic_token() (agent/anthropic_adapter.py:1159-1200), priority: (1) ANTHROPIC_TOKEN, (2) CLAUDE_CODE_OAUTH_TOKEN, (3) the Claude Code credentials — macOS Keychain or ~/.claude/.credentials.json (agent/anthropic_adapter.py:914-951), refreshed on expiry via _resolve_claude_code_token_from_credentials() (agent/anthropic_adapter.py:1122-1134), (4) ANTHROPIC_API_KEY. The token shape then chooses the header: _is_oauth_token() (agent/anthropic_adapter.py:386-411) returns True for sk-ant- (but NOT sk-ant-api), eyJ… JWTs, and cc- Claude Code tokens. build_anthropic_client() (agent/anthropic_adapter.py:700-817) sets auth_token= (Bearer) for OAuth tokens and api_key= (x-api-key) for regular keys.

Claude Code identity spoofing

For OAuth requests the client adds beta headers claude-code-20250219 + oauth-2025-04-20 (agent/anthropic_adapter.py:336-339), a spoofed user-agent: claude-cli/{version} (external, cli), and x-app: cli (set in build_anthropic_client's OAuth branch, agent/anthropic_adapter.py:800-810). build_anthropic_kwargs on the OAuth path (agent/anthropic_adapter.py:2327-2370) prepends the "You are Claude Code, Anthropic's official CLI for Claude." system prompt, rewrites brand strings (Hermes Agent→Claude Code, Nous Research→Anthropic), and mcp_-prefixes every tool name. Hermes' own comment is explicit: this is done "to avoid Anthropic's server-side content filters" (agent/anthropic_adapter.py:2338-2339).

Hermes-native PKCE login

Beyond consuming externally-minted tokens (and shelling out to claude setup-token via run_oauth_setup_token(), agent/anthropic_adapter.py:1203-1243), Hermes has its own flow: run_hermes_oauth_login_pure() (agent/anthropic_adapter.py:1270-1378) opens claude.ai/oauth/authorize with client_id 9d1c250a-e61b-44d9-88ed-5944d1962f5e, scopes org:create_api_key user:profile user:inference (agent/anthropic_adapter.py:1250-1253), exchanges the pasted code at console.anthropic.com/v1/oauth/token, and stores creds in ~/.hermes/.anthropic_oauth.json (agent/anthropic_adapter.py:1254). The prompt literally reads "Authorize Hermes with your Claude Pro/Max subscription" (agent/anthropic_adapter.py:1294). Refresh (_refresh_oauth_token, agent/anthropic_adapter.py:1033-1051) also write-back-merges scopes into ~/.claude/.credentials.json via _write_claude_code_credentials() to satisfy Claude Code ≥2.1.81's user:inference gate (agent/anthropic_adapter.py:1054-1119).

Verdict — Claude subscription: Works, but violates ToS. Technically yes, policy-wise no. Hermes accepts CLAUDE_CODE_OAUTH_TOKEN, setup-tokens, Claude Code credentials, and has its own login — and will make subscription-backed inference calls. But it only works by impersonating the first-party Claude Code client. Anthropic's Legal & Compliance doc states OAuth auth is "intended exclusively" for native Anthropic apps and "does not permit third-party developers to route requests through Free, Pro, or Max plan credentials." Since January 2026 Anthropic has been actively blocking exactly these spoofing harnesses (OpenCode, Roo, Goose, Cursor, Manus, Pi) and suspending accounts "without prior notice." A plain Bearer of an sk-ant-oat token without the Claude Code fingerprint returns 401 "OAuth authentication is currently not supported."
Key insight — the only legitimate Anthropic path. A pay-as-you-go Console API key (sk-ant-api…) under the Commercial Terms is the only unambiguously permitted option: export ANTHROPIC_API_KEY=sk-ant-api... routes through x-api-key with no spoofing. An API key is not the only credential Hermes will accept — but it is the only one Anthropic permits. The June 15 2026 Agent SDK subscription credit is also blessed, but it flows through the native Agent SDK, not a third-party harness.

OpenAI Codex — ChatGPT subscription OAuth

Yes You sign in with a ChatGPT subscription (Plus/Pro/Team/Business/Enterprise/Edu) to drive Codex models — entirely separate from any OpenAI API key. The access token is the credential; there is no API-key path for Codex models in Hermes.

Auth type
oauth_external (hermes_cli/auth.py:177-182)
Base URL
chatgpt.com/backend-api/codex — the same subscription-billed endpoint the official Codex CLI uses (hermes_cli/auth.py:80)
OAuth client
client_id app_EMoamEEZ73f0CkXaXp7hrann (hermes_cli/auth.py:96), token url auth.openai.com/oauth/token (hermes_cli/auth.py:97)
Billing
Counts against your ChatGPT plan's included Codex limits — not metered API billing

Device-code + PKCE login

_login_openai_codex() (hermes_cli/auth.py:6438-6511) first tries Hermes-stored creds, then optionally imports the Codex CLI's ~/.codex/auth.json via _import_codex_cli_tokens() (hermes_cli/auth.py:3676-3707), else runs _codex_device_code_login() (hermes_cli/auth.py:6925-7069): POST to auth.openai.com/api/accounts/deviceauth/usercode, show the user auth.openai.com/codex/device + a user code, poll for the authorization code, then PKCE-exchange it at auth.openai.com/oauth/token.

Independent session — no write-back to the Codex CLI

Hermes stores its own Codex session in ~/.hermes/auth.json under provider openai-codex with auth_mode="chatgpt" via _save_codex_tokens() (hermes_cli/auth.py:3499-3517), deliberately not in ~/.codex/. OpenAI rotates refresh tokens (single-use), so _refresh_codex_auth_tokens() (hermes_cli/auth.py:3655-3673) saves the new pair only to Hermes' store and the credential pool — it no longer writes back to ~/.codex/auth.json. The current design keeps the two sessions deliberately separate to avoid refresh-token rotation conflicts where one app's refresh invalidates the other's (hermes_cli/auth.py:3342-3346); Hermes still imports from ~/.codex/auth.json on first login, but does not sync changes back. Runtime: resolve_codex_runtime_credentials() (hermes_cli/auth.py:3710-3780) returns the access token as api_key, mapped to api_mode="codex_responses" (hermes_cli/runtime_provider.py:1413-1424), with a fall-back to the cross-process credential pool when the singleton store is empty. Model discovery hits chatgpt.com/backend-api/codex/models with a Bearer token via _fetch_models_from_api() (hermes_cli/codex_models.py:82-121).

Verdict — ChatGPT subscription drives Codex: Yes, supported & endorsed. This is the primary path for OpenAI's models in Hermes, not an afterthought. OpenAI publicly endorses personal reuse ("use Codex and your ChatGPT subscription wherever you like"), and the Codex CLI is Apache-2.0. How-to (Option A): run hermes auth / hermes login, pick "OpenAI Codex", open auth.openai.com/codex/device, sign in, enter the code. Option B: sign into the official Codex CLI so ~/.codex/auth.json exists — Hermes imports it automatically.
ToS & gaps. The backend-api/codex endpoint is undocumented/"semi-official" and can change without notice. OpenAI terms prohibit circumventing usage limits, pooling/transferring credentials, and reselling — honest single-user reuse is the tolerated zone; multi-account pooling or shared-service deployment is a ban risk. Update (post-merge): the earlier "no originator header" gap is now closed — the per-request default-header dispatch in run_agent.py:3843-3875 routes chatgpt.com traffic through _codex_cloudflare_headers() (agent/auxiliary_client.py:503-540), which pins originator: codex_cli_rs, a codex-rs-shaped User-Agent, and a ChatGPT-Account-ID extracted from the OAuth JWT's chatgpt_account_id claim — specifically to dodge Cloudflare 403 challenges on non-residential IPs. So Codex requests now advertise first-party Codex identity rather than a bare Bearer.

xAI / Grok — API key, plus new SuperGrok / Premium+ OAuth

Two paths now The plain xai provider is still an API-key backend, but the upstream merge added a separate xai-oauth provider that authenticates a SuperGrok / Premium+ subscription — so the earlier "API-key only, no subscription path" framing no longer holds.

The plain xai provider has no login dispatcher — xai resolves through the generic api-key resolver. But xai-oauth now does ship a login (_login_xai_oauth, hermes_cli/auth.py:6512) and runtime resolver (resolve_xai_oauth_runtime_credentials), and tools/xai_http.py grew beyond a bare User-Agent helper: alongside hermes_xai_user_agent() (tools/xai_http.py:66-72) it now carries resolve_xai_http_credentials() (tools/xai_http.py:75) that prefers Hermes-managed xAI OAuth creds before falling back to XAI_API_KEY. Aliases grok, x-ai, x.ai normalize to provider xai (hermes_cli/auth.py:1504); grok-oauth, x-ai-oauth etc. normalize to xai-oauth (hermes_cli/auth.py:1505-1506).

Surprising design. At runtime both xAI paths are routed through the Codex Responses API adapter — the generic api-key branch sets api_mode="codex_responses" for provider == "xai" (hermes_cli/runtime_provider.py:1669-1670), and the xai-oauth branch does the same (hermes_cli/runtime_provider.py:1433-1444). So Grok shares the Responses request format with OpenAI Codex; the api-key path still authenticates with a plain XAI_API_KEY bearer via the generic resolver resolve_api_key_provider_credentials() (hermes_cli/auth.py:5956).
Verdict — Grok subscription: Now possible via xai-oauth. A SuperGrok / X Premium+ subscription can now drive Grok through the dedicated xai-oauth provider (hermes auth add xai-oauth), in addition to the long-standing pay-per-token API-key path (console.x.ai → XAI_API_KEY) and OpenRouter. How-to (API key): create a key at console.x.ai, export XAI_API_KEY=xai-..., select a Grok model. How-to (subscription): run hermes auth add xai-oauth and complete the OAuth login.

GitHub Copilot & Copilot-ACP

Two distinct providers, two very different auth models.

copilot — hidden GitHub device-code OAuth

api_key, but OAuth under the hood Registered auth_type="api_key" (hermes_cli/auth.py:217-224), yet it ships a real GitHub device-code flow. The supported prefixes are gho_ (OAuth), github_pat_ (fine-grained PAT with Copilot Requests permission), and ghu_ (GitHub App) (hermes_cli/copilot_auth.py:36); validate_copilot_token (hermes_cli/copilot_auth.py:46-64) explicitly rejects classic ghp_ PATs. resolve_copilot_token() (hermes_cli/copilot_auth.py:67-95) checks COPILOT_GITHUB_TOKEN → GH_TOKEN → GITHUB_TOKEN (hermes_cli/copilot_auth.py:39), then falls back to gh auth token (_try_gh_cli_token, hermes_cli/copilot_auth.py:119-150). The interactive login copilot_device_code_login() (hermes_cli/copilot_auth.py:155-290) runs the GitHub OAuth device flow with client_id Ov23li8tweQw6odWQebz (the opencode/Copilot-CLI app id, hermes_cli/copilot_auth.py:33), scope read:user, polling github.com/login/oauth/access_token; the resulting token is saved via save_env_value("COPILOT_GITHUB_TOKEN", token) (hermes_cli/model_setup_flows.py:1539-1541). Requests carry editor-spoofing headers (Editor-Version: vscode/1.104.1, Copilot-Integration-Id: vscode-chat, hermes_cli/copilot_auth.py:383-385). The secret resolver special-cases copilot (hermes_cli/auth.py:567-578).

Verdict — GitHub Copilot subscription: Yes, via device-code OAuth. A Copilot subscription works as a model backend; the gho_ token from the GitHub device flow is the credential.

copilot-acp — external subprocess

external_process Base acp://copilot (hermes_cli/auth.py:225-231). This shells out to the Copilot CLI itself — there is no token. resolve_external_process_provider_credentials() (hermes_cli/auth.py:6001-6038) resolves the command (HERMES_COPILOT_ACP_COMMAND / COPILOT_CLI_PATH / copilot) and args (default --acp --stdio), returning a placeholder api_key="copilot-acp". Auth is delegated entirely to whatever the Copilot CLI process is logged into. CopilotACPClient (agent/copilot_acp_client.py:334) spawns copilot --acp --stdio per request and speaks JSON-RPC/ACP over stdio.

Qwen-OAuth, Gemini & Nous Portal

Qwen-OAuth — parasitic on the Qwen CLI

oauth_external Base portal.qwen.ai/v1 (hermes_cli/auth.py:197-202). Crucially, Hermes does not run its own Qwen device flow — it reads and refreshes the Qwen CLI's credential file ~/.qwen/oauth_creds.json via _read_qwen_cli_tokens() (hermes_cli/auth.py:1937-1947, path at hermes_cli/auth.py:1933-1934). If missing it errors "Run 'qwen auth qwen-oauth' first." Refresh (_refresh_qwen_cli_tokens, hermes_cli/auth.py:2001-2071) POSTs to chat.qwen.ai/api/v1/oauth2/token (hermes_cli/auth.py:108). resolve_qwen_runtime_credentials() (hermes_cli/auth.py:2092-2121) returns source="qwen-cli"; the dispatcher then tags it api_mode="chat_completions" (hermes_cli/runtime_provider.py:1451-1462).

Surprising design. Qwen "OAuth" mints no tokens of its own — it is effectively a parasitic session on the official Qwen CLI login. It is a subscription/OAuth provider, but only because the Qwen CLI did the logging-in.

Gemini — pure API key

api_key Base generativelanguage.googleapis.com/v1beta, env GOOGLE_API_KEY/GEMINI_API_KEY (hermes_cli/auth.py:232-239) — a Google AI Studio API key. Note: the merge also added a separate OAuth provider google-gemini-cli (hermes_cli/auth.py:203-208) for the Gemini CLI's Cloud Code path, so "no Google subscription login at all" no longer holds for the broader registry.

Nous Portal — the canonical subscription provider

oauth_device_code The flagship subscription provider (hermes_cli/auth.py:168-176): client_id hermes-cli (hermes_cli/auth.py:72), scope inference:invoke (hermes_cli/auth.py:73-74), portal portal.nousresearch.com (hermes_cli/auth.py:70). _nous_device_code_login() (hermes_cli/auth.py:7502-7630) opens the portal verification URL and obtains an OAuth access+refresh token. At runtime, resolve_nous_runtime_credentials() (hermes_cli/auth.py:5268-5494) reads provider state and refreshes the token via the standard /api/oauth/token refresh when its inference-scoped "invoke JWT" is expiring; the refreshed access token is the inference credential — _select_nous_invoke_jwt() (hermes_cli/auth.py:1893-1903) sets state["agent_key"] to that JWT and the resolver returns it with source="invoke_jwt" (hermes_cli/auth.py:5472-5494). (The earlier design that minted a separate short-lived key via POST {portal}/api/oauth/agent-key is gone — there is no agent-key mint endpoint in the current tree; the OAuth JWT itself carries the inference:invoke scope and hits the inference API directly.) A separate nous_subscription.py layer maps the subscription to managed tool features (web, image-gen, video-gen, TTS, STT, browser, modal), gated on NousSubscriptionFeatures (hermes_cli/nous_subscription.py:71-110).

Auth storage & runtime resolution

All Hermes-owned OAuth/credential state lives in ~/.hermes/auth.json (hermes_cli/auth.py:855-856), guarded by a reentrant cross-process advisory lock _auth_store_lock() (hermes_cli/auth.py:1023-1039) backed by _file_lock (fcntl/msvcrt, hermes_cli/auth.py:951-1021) with AUTH_LOCK_TIMEOUT_SECONDS=15 at hermes_cli/auth.py:67. The one exception is Anthropic's native OAuth, stored separately in ~/.hermes/.anthropic_oauth.json (agent/anthropic_adapter.py:1254). Per-provider OAuth tokens are additionally fanned out into a cross-process credential pool (agent/credential_pool.py) that the api-key and Codex/Nous resolvers fall back to.

Runtime dispatch

resolve_runtime_provider() (hermes_cli/runtime_provider.py:1254-1714) is the central dispatcher. After custom/Azure short-circuits and a credential-pool check, it branches per provider: Nous→invoke-JWT resolve (hermes_cli/runtime_provider.py:1391); Codex→codex_responses (hermes_cli/runtime_provider.py:1413); xai-oauth→codex_responses (1433); Qwen→chat_completions (1451); minimax-oauth→anthropic_messages (1469); google-gemini-cli (1483); copilot-acp→external process (1503); anthropic→resolve_anthropic_token + anthropic_messages (1517); bedrock→boto3 chain (1584); then the generic api_key branch for all remaining providers (hermes_cli/runtime_provider.py:1654-1706) with special api_mode handling (copilot, xai→codex_responses at 1669-1670, opencode, /anthropic-suffix auto-detect). Anything unmatched falls through to OpenRouter (hermes_cli/runtime_provider.py:1708-1714).

Auto-fallthrough. When the requested provider is "auto", OAuth providers that fail credential resolution log and fall through to the next provider — e.g. Codex→OpenRouter (hermes_cli/runtime_provider.py:1425-1431). The generic secret resolver _resolve_api_key_provider_secret (hermes_cli/auth.py:563-599) special-cases copilot to resolve_copilot_token(), otherwise scans api_key_env_vars and then the cross-process credential pool, filtering placeholder values via has_usable_secret (hermes_cli/auth.py:551-560).
