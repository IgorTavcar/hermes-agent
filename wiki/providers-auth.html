Models, Providers & Authentication

Hermes routes inference through a single PROVIDER_REGISTRY of ~24 providers (hermes_cli/auth.py:103-294), each tagged with one of five auth types. Three of the headline questions users ask — "can I use my Claude Code / ChatGPT / Grok subscription instead of an API key?" — all resolve here. The short answers: Anthropic subscription OAuth works mechanically but violates Anthropic's ToS; an OpenAI ChatGPT subscription is a first-class, OpenAI-endorsed path for Codex models; and xAI/Grok is API-key only with no subscription path at all. This page maps the whole registry, then walks each provider's auth contract with verified verdicts.

PROVIDER_REGISTRY — full map

PROVIDER_REGISTRY is a Dict[str, ProviderConfig] defined at hermes_cli/auth.py:103. Each ProviderConfig (hermes_cli/auth.py:86-100) carries an id, name, auth_type, portal_base_url, inference_base_url, client_id, scope, api_key_env_vars (a priority-ordered tuple), and a base_url_env_var override.

Surprising design. The dataclass header comment claims three auth types (hermes_cli/auth.py:91: "oauth_device_code", "oauth_external", or "api_key"), but the registry actually uses five: oauth_device_code, oauth_external, api_key, external_process (Copilot ACP), and aws_sdk (Bedrock). And two providers registered as api_key — Anthropic and Copilot — secretly carry full OAuth flows.

Anthropic — OAuth, CLAUDE_CODE_OAUTH_TOKEN & Claude Code spoofing

Partial Registered api_key, but Anthropic is the most elaborate auth path in Hermes. It accepts a regular Console key and a Claude Pro/Max subscription OAuth token, and it even runs its own native PKCE login.

Auth type
api_key (with full hidden OAuth machinery)
API key path
sk-ant-api… Console key → x-api-key header (clean, supported)
Subscription path
CLAUDE_CODE_OAUTH_TOKEN / ANTHROPIC_TOKEN / ~/.claude/.credentials.json / Hermes-native login → Authorization: Bearer with Claude Code identity spoofing
Env var order
ANTHROPIC_API_KEY → ANTHROPIC_TOKEN → CLAUDE_CODE_OAUTH_TOKEN (hermes_cli/auth.py:192)

How the token shape decides the header

get_anthropic_key() (hermes_cli/auth.py:301-316) walks the env-var tuple in order. At runtime the agent calls resolve_anthropic_token() (agent/anthropic_adapter.py:552-593), priority: (1) ANTHROPIC_TOKEN, (2) CLAUDE_CODE_OAUTH_TOKEN, (3) the Claude Code credential file ~/.claude/.credentials.json with auto-refresh (agent/anthropic_adapter.py:328-355), (4) ANTHROPIC_API_KEY. The token shape then chooses the header: _is_oauth_token() (agent/anthropic_adapter.py:165-186) returns True for sk-ant- (but NOT sk-ant-api) and for eyJ… JWTs. build_anthropic_client() (agent/anthropic_adapter.py:243-298) sets auth_token= (Bearer) for OAuth tokens and api_key= (x-api-key) for regular keys.

Claude Code identity spoofing

For OAuth requests the client adds beta headers claude-code-20250219 + oauth-2025-04-20, a spoofed user-agent: claude-cli/{version} (external, cli), and x-app: cli. build_anthropic_kwargs on the OAuth path (agent/anthropic_adapter.py:1281-1318) prepends the "You are Claude Code, Anthropic's official CLI for Claude." system prompt, rewrites brand strings (Hermes Agent→Claude Code, Nous Research→Anthropic), and mcp_-prefixes every tool name. Hermes' own comment is explicit: this is done "to avoid Anthropic's server-side content filters" (agent/anthropic_adapter.py:1291-1300).

Hermes-native PKCE login

Beyond consuming externally-minted tokens (and shelling out to claude setup-token via agent/anthropic_adapter.py:596-633), Hermes has its own flow: run_hermes_oauth_login_pure() (agent/anthropic_adapter.py:660-755) opens claude.ai/oauth/authorize with client_id 9d1c250a-e61b-44d9-88ed-5944d1962f5e, scopes org:create_api_key user:profile user:inference, exchanges the pasted code at console.anthropic.com/v1/oauth/token, and stores creds in ~/.hermes/.anthropic_oauth.json. The prompt literally reads "Authorize Hermes with your Claude Pro/Max subscription" (agent/anthropic_adapter.py:682). Refresh (agent/anthropic_adapter.py:387-448) also write-back-merges scopes into ~/.claude/.credentials.json to satisfy Claude Code ≥2.1.81's user:inference gate (agent/anthropic_adapter.py:472-512).

Verdict — Claude subscription: Works, but violates ToS. Technically yes, policy-wise no. Hermes accepts CLAUDE_CODE_OAUTH_TOKEN, setup-tokens, Claude Code credentials, and has its own login — and will make subscription-backed inference calls. But it only works by impersonating the first-party Claude Code client. Anthropic's Legal & Compliance doc states OAuth auth is "intended exclusively" for native Anthropic apps and "does not permit third-party developers to route requests through Free, Pro, or Max plan credentials." Since January 2026 Anthropic has been actively blocking exactly these spoofing harnesses (OpenCode, Roo, Goose, Cursor, Manus, Pi) and suspending accounts "without prior notice." A plain Bearer of an sk-ant-oat token without the Claude Code fingerprint returns 401 "OAuth authentication is currently not supported."
Key insight — the only legitimate Anthropic path. A pay-as-you-go Console API key (sk-ant-api…) under the Commercial Terms is the only unambiguously permitted option: export ANTHROPIC_API_KEY=sk-ant-api... routes through x-api-key with no spoofing. An API key is not the only credential Hermes will accept — but it is the only one Anthropic permits. The June 15 2026 Agent SDK subscription credit is also blessed, but it flows through the native Agent SDK, not a third-party harness.

OpenAI Codex — ChatGPT subscription OAuth

Yes You sign in with a ChatGPT subscription (Plus/Pro/Team/Business/Enterprise/Edu) to drive Codex models — entirely separate from any OpenAI API key. The access token is the credential; there is no API-key path for Codex models in Hermes.

Auth type
oauth_external (hermes_cli/auth.py:113-118)
Base URL
chatgpt.com/backend-api/codex — the same subscription-billed endpoint the official Codex CLI uses
OAuth client
client_id app_EMoamEEZ73f0CkXaXp7hrann, token url auth.openai.com/oauth/token (hermes_cli/auth.py:69-79)
Billing
Counts against your ChatGPT plan's included Codex limits — not metered API billing

Device-code + PKCE login

_login_openai_codex() (hermes_cli/auth.py:2845-2907) first tries Hermes-stored creds, then optionally imports the Codex CLI's ~/.codex/auth.json via _import_codex_cli_tokens() (hermes_cli/auth.py:1494-1525), else runs _codex_device_code_login() (hermes_cli/auth.py:2910-3052): POST to auth.openai.com/api/accounts/deviceauth/usercode, show the user auth.openai.com/codex/device + a user code, poll for the authorization code, then PKCE-exchange it at auth.openai.com/oauth/token.

Independent session, synced write-back

Hermes stores its own Codex session in ~/.hermes/auth.json under provider openai-codex with auth_mode="chatgpt" (hermes_cli/auth.py:1363-1374), deliberately not in ~/.codex/. OpenAI rotates refresh tokens (single-use), so _refresh_codex_auth_tokens() (hermes_cli/auth.py:1467-1491) writes the new pair both to Hermes' store and back to ~/.codex/auth.json to keep the Codex CLI in sync. Runtime: resolve_codex_runtime_credentials() (hermes_cli/auth.py:1528-1588) returns the access token as api_key, mapped to api_mode="codex_responses" (hermes_cli/runtime_provider.py:769-787). Model discovery hits chatgpt.com/backend-api/codex/models with a Bearer token (hermes_cli/codex_models.py:55-90).

Verdict — ChatGPT subscription drives Codex: Yes, supported & endorsed. This is the primary path for OpenAI's models in Hermes, not an afterthought. OpenAI publicly endorses personal reuse ("use Codex and your ChatGPT subscription wherever you like"), and the Codex CLI is Apache-2.0. How-to (Option A): run hermes auth / hermes login, pick "OpenAI Codex", open auth.openai.com/codex/device, sign in, enter the code. Option B: sign into the official Codex CLI so ~/.codex/auth.json exists — Hermes imports it automatically.
ToS & gaps. The backend-api/codex endpoint is undocumented/"semi-official" and can change without notice. OpenAI terms prohibit circumventing usage limits, pooling/transferring credentials, and reselling — honest single-user reuse is the tolerated zone; multi-account pooling or shared-service deployment is a ban risk. Verified gap: Hermes sets no originator (default codex_cli_rs) or chatgpt-account-id header — Codex requests go out as a bare Authorization: Bearer. Default headers in run_agent.py:958-1041 are only added for OpenRouter/Copilot/Kimi/Qwen, never Codex. If OpenAI enforces originator-based gating, Hermes' Codex calls could begin failing.

xAI / Grok — API-key only

No subscription path xAI/Grok is integrated, but strictly as a plain API-key provider. There is no xAI OAuth, no device-code/login flow, and no integration with xAI's own "Grok Build" CLI or SuperGrok subscription.

Auth type
api_key (hermes_cli/auth.py:218-225)
Base URL
api.x.ai/v1, override XAI_BASE_URL
Env var
XAI_API_KEY (the sole env var)
Console
console.x.ai — the pay-per-token developer API console (hermes_cli/config.py:849-857)
Default models
grok-4.20-reasoning, grok-4-1-fast-reasoning (hermes_cli/models.py:147-150)

No xAI-specific login dispatcher exists anywhere — xai never appears in any _login_* / device-code / OAuth path. tools/xai_http.py is a 13-line User-Agent helper (hermes_xai_user_agent(), tools/xai_http.py:6-12) with no auth logic. Aliases grok, x-ai, x.ai all normalize to provider xai (hermes_cli/auth.py:931).

Surprising design. At runtime xAI is routed through the Codex Responses API adapter — hermes_cli/runtime_provider.py:933-934 sets api_mode="codex_responses" for provider == "xai". So Grok shares the Responses request format with OpenAI Codex, yet still authenticates with a plain XAI_API_KEY bearer via the generic resolver (hermes_cli/auth.py:2488-2523). This is a request-format coupling, not an auth linkage.
Verdict — Grok subscription: Not possible. A consumer SuperGrok / X Premium+ subscription cannot be used as programmatic credentials — Hermes only accepts a console.x.ai pay-per-token XAI_API_KEY (or OpenRouter's grok-code-fast-1 via OPENROUTER_API_KEY). xAI's official "Grok Build" CLI is a separate first-party product Hermes does not wrap. How-to: create a key at console.x.ai, export XAI_API_KEY=xai-..., select a Grok model.

GitHub Copilot & Copilot-ACP

Two distinct providers, two very different auth models.

copilot — hidden GitHub device-code OAuth

api_key, but OAuth under the hood Registered auth_type="api_key" (hermes_cli/auth.py:125-132), yet it ships a real GitHub device-code flow. validate_copilot_token (hermes_cli/copilot_auth.py:46-64) accepts gho_ (OAuth), github_pat_ (fine-grained PAT with Copilot Requests permission), and ghu_ (GitHub App) prefixes — classic ghp_ PATs are rejected. resolve_copilot_token() (hermes_cli/copilot_auth.py:67-95) checks COPILOT_GITHUB_TOKEN → GH_TOKEN → GITHUB_TOKEN, then falls back to gh auth token (hermes_cli/copilot_auth.py:119-150). The interactive login copilot_device_code_login() (hermes_cli/copilot_auth.py:155-275) runs the GitHub OAuth device flow with client_id Ov23li8tweQw6odWQebz (the opencode/Copilot-CLI app id), scope read:user, polling github.com/login/oauth/access_token; the resulting token is saved via save_env_value("COPILOT_GITHUB_TOKEN", token) (hermes_cli/main.py:2122-2128). Requests carry editor-spoofing headers (Editor-Version: vscode/1.104.1, Copilot-Integration-Id: vscode-chat). The secret resolver special-cases copilot (hermes_cli/auth.py:375-386).

Verdict — GitHub Copilot subscription: Yes, via device-code OAuth. A Copilot subscription works as a model backend; the gho_ token from the GitHub device flow is the credential.

copilot-acp — external subprocess

external_process Base acp://copilot (hermes_cli/auth.py:133-139). This shells out to the Copilot CLI itself — there is no token. resolve_external_process_provider_credentials() (hermes_cli/auth.py:2526-2563) resolves the command (HERMES_COPILOT_ACP_COMMAND / COPILOT_CLI_PATH / copilot) and args (default --acp --stdio), returning a placeholder api_key="copilot-acp". Auth is delegated entirely to whatever the Copilot CLI process is logged into. CopilotACPClient (agent/copilot_acp_client.py:256-347) spawns copilot --acp --stdio per request and speaks JSON-RPC/ACP over stdio.

Qwen-OAuth, Gemini & Nous Portal

Qwen-OAuth — parasitic on the Qwen CLI

oauth_external Base portal.qwen.ai/v1 (hermes_cli/auth.py:119-124). Crucially, Hermes does not run its own Qwen device flow — it reads and refreshes the Qwen CLI's credential file ~/.qwen/oauth_creds.json (hermes_cli/auth.py:1084-1109). If missing it errors "Run 'qwen auth qwen-oauth' first." Refresh (hermes_cli/auth.py:1131-1200) POSTs to chat.qwen.ai/api/v1/oauth2/token and writes the rotated pair back to the Qwen CLI file. resolve_qwen_runtime_credentials() (hermes_cli/auth.py:1203-1232) returns source="qwen-cli", api_mode="chat_completions".

Surprising design. Qwen "OAuth" mints no tokens of its own — it is effectively a parasitic session on the official Qwen CLI login. It is a subscription/OAuth provider, but only because the Qwen CLI did the logging-in.

Gemini — pure API key

api_key OpenAI-compatible base generativelanguage.googleapis.com/v1beta/openai, env GOOGLE_API_KEY/GEMINI_API_KEY (hermes_cli/auth.py:140-147). No OAuth, no Google subscription login — a Google AI Studio API key only.

Nous Portal — the canonical subscription provider

oauth_device_code The flagship subscription provider (hermes_cli/auth.py:104-112): client_id hermes-cli, scope inference:mint_agent_key, portal portal.nousresearch.com. _nous_device_code_login() (hermes_cli/auth.py:3055) opens the portal verification URL and obtains an OAuth access+refresh token. At runtime, resolve_nous_runtime_credentials() reads provider state, refreshes if expiring, then mints a short-lived inference key via _mint_agent_key() (hermes_cli/auth.py:1749-1779) — POST {portal}/api/oauth/agent-key with the OAuth bearer and a min_ttl_seconds (default 1800s), caching it as state["agent_key"] and reusing until within TTL (hermes_cli/auth.py:1839-1843). The minted agent key (not the OAuth token) is what hits the inference API. A separate nous_subscription.py layer maps the subscription to managed tool features (web search, image-gen, TTS, browser, modal), gated on NousSubscriptionFeatures (hermes_cli/nous_subscription.py:41-71).

Auth storage & runtime resolution

All Hermes-owned OAuth/credential state lives in ~/.hermes/auth.json (hermes_cli/auth.py:571), guarded by a reentrant cross-process advisory lock (hermes_cli/auth.py:581-597, fcntl/msvcrt, AUTH_LOCK_TIMEOUT_SECONDS=15 at hermes_cli/auth.py:59). The one exception is Anthropic's native OAuth, stored separately in ~/.hermes/.anthropic_oauth.json (agent/anthropic_adapter.py:644).

Runtime dispatch

resolve_runtime_provider() (hermes_cli/runtime_provider.py:656-966) is the central dispatcher. It branches per provider: Nous→mint agent key (hermes_cli/runtime_provider.py:748); Codex→codex_responses (769); Qwen→chat_completions (789); copilot-acp→external process (807); anthropic→resolve_anthropic_token + anthropic_messages (821); bedrock→boto3 chain (847); then the generic api_key branch for all remaining providers (hermes_cli/runtime_provider.py:918-958) with special api_mode handling (copilot, xai→codex_responses, opencode, /anthropic-suffix auto-detect). Anything unmatched falls through to OpenRouter (hermes_cli/runtime_provider.py:960).

Auto-fallthrough. When the requested provider is "auto", OAuth providers that fail credential resolution log and fall through to the next provider — e.g. Codex→OpenRouter (hermes_cli/runtime_provider.py:781-787). The generic secret resolver _resolve_api_key_provider_secret (hermes_cli/auth.py:371-393) special-cases copilot to resolve_copilot_token() and otherwise scans api_key_env_vars, filtering placeholder values via has_usable_secret (hermes_cli/auth.py:359-368).
