Hermes Agent — Engineering Wiki

Hermes Agent is a self-improving, multi-platform AI agent harness from Nous Research (MIT-licensed) that drives a single user message to completion through one provider-agnostic turn loop, calls real tools over an RPC stub so a fifty-step pipeline costs one inference turn, and runs against roughly three dozen inference providers — including subscription-OAuth backends like ChatGPT Plus and Claude Pro/Max — while clinging to the two things that actually matter in production: the model's context window and its hourly rate quota.

What Hermes is

Hermes is the agent runtime that wraps a chat model in everything it needs to act in the world: a terminal, a filesystem, web search, code execution, memory, and a gateway onto messaging platforms. It is provider-agnostic by design. The same production turn loop, AIAgent.run_conversation() at run_agent.py:5144 (a thin forwarder into agent.conversation_loop.run_conversation), is used identically by the CLI and the gateway, and it speaks to every backend through the OpenAI ChatCompletion spec plus an Anthropic Messages transport, with adapters for Codex Responses and Bedrock Converse. Provider differences are quarantined inside _build_api_kwargs and per-provider adapter modules so the loop body stays uniform.

That loop is deliberately simple at its core — a synchronous, single-threaded while (api_call_count < agent.max_iterations and agent.iteration_budget.remaining > 0) at agent/conversation_loop.py:461 — and deliberately paranoid at its edges. Each iteration assembles per-call api_messages (an ephemeral system prompt plus memory and plugin injections plus KV-cache breakpoints), calls the model through a streaming-first interruptible transport, normalizes whatever the provider returns into a uniform OpenAI-style SimpleNamespace, and branches on tool-calls-versus-text. Tool calls dispatch through _execute_tool_calls() at run_agent.py:5043 — which routes to execute_tool_calls_concurrent on a ThreadPoolExecutor (up to 8 workers, agent/tool_executor.py:561) or to the sequential path — appends role:"tool" results, and continues; a plain text response with no tool calls becomes the final_response and breaks.

Key insight. There is effectively one production loop. The synchronous run_conversation (agent/conversation_loop.py:371) is shared verbatim by the CLI and the gateway — there is no second code path. (An earlier fork carried a separate async HermesAgentLoop for RL/eval environments, but the upstream merge removed the Atropos RL environments and that loop along with them, so the codebase now has a single turn loop plus its drivers.) The CLI and gateway differ only in how they feed and display that one loop, not in the loop body.

"Self-improving" is not a slogan here. Hermes closes a learning loop: trajectories are compressed and fed back, routines run on cron, and an auxiliary guardian LLM sits inside the approval gate to triage approve/deny/escalate before a human is ever bothered (_smart_approve at tools/approval.py:991, wired into the Smart-approval gate at tools/approval.py:1378), an idea borrowed from OpenAI Codex's Smart Approvals.

Highlights at a glance

The recurring theme across Hermes is that the non-obvious win is almost always about protecting the LLM's context window, surviving real-world rate limits, or making stateless cloud backends behave like stateful shells.

Surprising by design. Streaming is preferred always — even when no display or TTS consumer is attached — purely to gain the stale-stream and read-timeout health checks (90s stale-stream detection, 60s read timeout) the non-streaming path lacks (agent/conversation_loop.py:958). The streamed response is then repackaged into a non-streaming-shaped SimpleNamespace so the loop body never notices.
Cache-friendly by construction. Tool-call JSON is re-serialized with sort_keys=True and tight separators on every API call (agent/conversation_loop.py:728) to keep the prompt prefix byte-identical across turns, preserving KV-cache reuse on local inference servers like llama.cpp, vLLM, and Ollama.

How to read the codebase

If you are reading Hermes for the first time, walk these files in order — they form a spine from the turn loop out to the providers.

FileWhy it matters
run_agent.pyThe AIAgent class and its public surface (~5.4k lines). It exposes run_conversation() at run_agent.py:5144 and _execute_tool_calls() at run_agent.py:5043 as thin forwarders into the agent/ package, where the loop body now lives.
agent/conversation_loop.pyThe production turn loop itself: run_conversation() at agent/conversation_loop.py:371, the budget while loop at agent/conversation_loop.py:461, the cache-friendly sort_keys re-serialization at agent/conversation_loop.py:728, the always-streaming decision at agent/conversation_loop.py:958, and the empty/degenerate-response recovery (retry → fallback provider) around agent/conversation_loop.py:3994. A bird's-eye view of how a single message flows through the system:

graph TD;
  U[User message]-->RC[run_conversation conversation_loop.py:371];
  RC-->L{budget loop :461};
  L-->A[assemble api_messages + cache breakpoints];
  A-->T[streaming-first transport];
  T-->N[normalize to SimpleNamespace];
  N-->B{tool calls?};
  B-->|yes|D[_execute_tool_calls run_agent.py:5043];
  D-->L;
  B-->|no|F[final_response break];
  D-->EC[execute_code RPC stub];
  EC-->CP[context compactor];
Caveat. Subscription-OAuth providers route real consumer subscriptions through agent traffic (e.g. Claude Pro/Max via Bearer auth with Claude-Code identity, ChatGPT Plus driving Codex). Confirm such usage is within each provider's terms of service before relying on it in production; Hermes provides the transport, not the entitlement.
