Architecture: The Loops

Hermes is built around a single, synchronous turn loop — AIAgent.run_conversation() at run_agent.py:5144, a thin forwarder into the extracted loop body at agent/conversation_loop.py:371 — that drives one user message to completion. Almost everything else in the system is a driver wrapped around that loop: the CLI REPL, the multi-platform gateway, the cron/routines scheduler, the parallel batch runner, and the recursive delegation of subagents. After the upstream merge removed the Atropos RL/eval environments, there is effectively one production loop plus its drivers — no second async loop survives. This page dissects the main loop and its tool pipeline first, then maps each driver onto it and contrasts them in a single table.

Overview: One Loop, Many Drivers

The turn loop is AIAgent.run_conversation() — a public forwarder at run_agent.py:5144 whose body now lives in agent/conversation_loop.py:run_conversation (agent/conversation_loop.py:371). It is a synchronous function that returns a result dict containing final_response, messages, api_calls, completed, and token usage; that dict is assembled by the extracted finalize_turn helper (agent/turn_finalizer.py:326). Every driver in the system ultimately calls this exact function.

Key insight. The framing of "lighter CLI loop vs heavier gateway loop" is misleading. The inner loop is byte-identical run_conversation in every case — drivers differ only at the outer level (agent lifecycle, callback wiring, approval transport). The upstream merge (commit 5af672c75) deleted the Atropos RL/eval environments, so the old "second async HermesAgentLoop" is gone: there is one production loop, period.

The Main Agent Loop

Per-turn preamble

Before entering the loop, run_conversation delegates substantial per-turn setup to the extracted build_turn_context helper (agent/turn_context.py:64, called from agent/conversation_loop.py:407). That helper:

  • Sanitizes surrogate characters in the user message — lone surrogates crash json.dumps() inside the OpenAI SDK — via _sanitize_surrogates (agent/turn_context.py:114, agent/message_sanitization.py:31).
  • Resets a wall of per-turn retry counters — _invalid_tool_retries, _empty_content_retries, _thinking_prefill_retries, and others (agent/turn_context.py:132).
  • Builds or loads the system prompt once per session for prefix-cache stability: only when _cached_system_prompt is unset does it call restore_or_build_system_prompt, so continuing sessions replay the stored prompt and keep the Anthropic cache prefix bit-identical (agent/turn_context.py:232).
  • Runs preflight compression if the loaded history already exceeds the threshold, looping up to 3 passes (agent/turn_context.py:294).
  • Fires plugin pre_llm_call hooks whose returned context is injected into the user message — never the system prompt, to preserve the cache prefix (agent/turn_context.py:316).
  • Creates a fresh IterationBudget(agent.max_iterations) per call (agent/turn_context.py:164) and prefetches external memory once (agent/turn_context.py:367).

The user message is appended and its index recorded as current_turn_user_idx so ephemeral injections can target exactly that message at API-call time (agent/turn_context.py:222).

The loop body

The loop guard is while (api_call_count < agent.max_iterations and agent.iteration_budget.remaining > 0) or agent._budget_grace_call: at agent/conversation_loop.py:461. Each iteration runs five stages:

  1. Interrupt + budget gates — checks _interrupt_requested, increments api_call_count, consumes one iteration-budget unit with a one-shot _budget_grace_call (agent/conversation_loop.py:466).
  2. Assemble api_messages — copies messages, injects memory-prefetch and plugin context only into current_turn_user_idx, copies assistant reasoning to reasoning_content for providers that need it, strips internal fields, prepends the effective system message, inserts ephemeral prefills, applies Anthropic cache_control breakpoints when _use_prompt_caching is set (agent/prompt_caching.py:49), sanitizes orphaned tool results, and re-serializes tool-call JSON with sorted keys for KV-cache prefix stability (agent/conversation_loop.py:606).
  3. Inner retry loop — while retry_count < max_retries (agent/conversation_loop.py:811), builds kwargs via _build_api_kwargs, then always prefers streaming via _interruptible_streaming_api_call (agent/conversation_loop.py:1003). Invalid/empty responses trigger eager fallback activation and jittered exponential backoff (agent/conversation_loop.py:1156).
  4. finish_reason mapping per api_mode — Codex incomplete/length, Anthropic stop_reason via the transport's map_finish_reason, OpenAI/chat choices[0].finish_reason; suspicious Ollama/GLM stops are upgraded to length via _should_treat_stop_as_truncated (agent/conversation_loop.py:1279, run_agent.py:1350).
  5. Normalize the response via the active ProviderTransport.normalize_response into a uniform SimpleNamespace with .content, .tool_calls, .reasoning, and .finish_reason (agent/conversation_loop.py:3305).

The loop has two real exits: a tool-calling turn does continue (agent/conversation_loop.py:3828), and a text-only turn sets final_response and break (agent/conversation_loop.py:4164). A diagnostic _turn_exit_reason string is tracked throughout and logged in finalize_turn, escalating to WARNING when the last message is a pending tool result — the "agent just stopped" case (agent/turn_finalizer.py:179).

Stop conditions and the non-tool exit

The else branch (no tool calls, agent/conversation_loop.py:3830) is where a turn normally ends, but it is defensive about degenerate responses before committing final_response. It carries five distinct recovery strategies: partial-stream salvage (agent/conversation_loop.py:3848), housekeeping-only fallback (agent/conversation_loop.py:3877), a post-tool empty nudge (agent/conversation_loop.py:3922), thinking-only prefill continuation (≤2×, agent/conversation_loop.py:3975), and empty-response retry (≤3×, agent/conversation_loop.py:4010). Once a genuine text response is obtained, any buffered truncated_response_parts from prior length-continuations are prepended, <think> blocks are stripped for the user-facing string, and the loop breaks (agent/conversation_loop.py:4135).

Other terminators: interrupt at the top of the loop, budget exhaustion, all retries exhausted with no response, and an outer exception handler near max-iterations (agent/conversation_loop.py:4215). Post-loop finalization is delegated to finalize_turn (agent/turn_finalizer.py:30): if final_response is still None and the budget is spent, _handle_max_iterations makes one extra tools-stripped call asking the model to summarize (agent/turn_finalizer.py:70, implemented at agent/chat_completion_helpers.py:1305). It then saves the trajectory, cleans up task VM/browser, persists the session, fires post_llm_call/on_session_end hooks, optionally spawns a background memory/skill review, and returns the result dict (agent/turn_finalizer.py:326).

The Tool-Execution Pipeline

Registration: how tools appear

Tools self-register at import time. Each module calls registry.register(name, toolset, schema, handler, ...) (tools/registry.py:234), which populates a thread-safe ToolEntry map (tools/registry.py:77) and rejects shadowing of built-ins (only MCP-over-MCP overwrites are allowed, tools/registry.py:260). The agent builds agent.tools once via get_tool_definitions(enabled_toolsets, disabled_toolsets, quiet_mode) and derives agent.valid_tool_names — the set the loop validates every model tool call against (agent/agent_init.py:950, agent/agent_init.py:959).

get_tool_definitions (model_tools.py:272) resolves the requested toolsets to a name set, asks the registry only for tools whose check_fn passes (so missing API keys hide tools, model_tools.py:413), then dynamically rewrites schemas: execute_code's sandbox-tool list (model_tools.py:422) and browser_navigate's description (model_tools.py:464) are pruned to actually-available tools so the model cannot hallucinate absent tools. The four _AGENT_LOOP_TOOLS = {todo, memory, session_search, delegate_task} are short-circuited (model_tools.py:569) — they must be handled inside the loop with agent state, so a slip through to handle_function_call returns a stub error (model_tools.py:1018).

Note. toolset_distributions.py is orthogonal to the live loop: its DISTRIBUTIONS dict and sample_toolsets_from_distribution are used to randomly sample toolset combinations for training-data generation, not runtime dispatch (toolset_distributions.py:29, toolset_distributions.py:247).

Detection, repair, and dispatch

When the normalized assistant_message.tool_calls is truthy (agent/conversation_loop.py:3499), unknown names are run through _repair_tool_call (fuzzy correction, run_agent.py:3354); still-invalid names produce a self-correction error back to the model, capped at 3 retries (agent/conversation_loop.py:3509). The assistant message is appended, the streaming display closed, and _execute_tool_calls(...) runs (agent/conversation_loop.py:3731).

_execute_tool_calls is a thin dispatcher (run_agent.py:5043) that chooses concurrency via _should_parallelize_tool_batch (agent/tool_dispatch_helpers.py:103) — both the parallelism predicate and the concurrent/sequential executors were extracted from run_agent.py into dedicated modules in the merge. A batch larger than one runs concurrently only if no tool is in _NEVER_PARALLEL_TOOLS ({clarify}, agent/tool_dispatch_helpers.py:41) and every tool is either in the read-only _PARALLEL_SAFE_TOOLS set (read_file, search_files, session_search, skill_view, skills_list, vision_analyze, web_extract, web_search, HA reads — agent/tool_dispatch_helpers.py:44) or is a path-scoped file tool whose target paths do not overlap (agent/tool_dispatch_helpers.py:132). The concurrent path (agent/tool_executor.py:243) uses a ThreadPoolExecutor with max_workers=min(len(runnable_calls), 8) (_MAX_TOOL_WORKERS=8 at agent/tool_executor.py:52) and a 5-second-poll wait loop (agent/tool_executor.py:579) emitting 30-second heartbeats (agent/tool_executor.py:608) and cancelling pending futures on interrupt (agent/tool_executor.py:599).

Per-tool execution routes agent-level tools (todo, memory, session_search, clarify, delegate_task, plus memory-manager tools) directly with agent state inside the executor (agent/tool_executor.py:964); everything else goes to handle_function_call (model_tools.py:876, called at agent/tool_executor.py:1200) which calls registry.dispatch(name, args, ...) (tools/registry.py:390), bridging async handlers and wrapping all exceptions as {"error": ...}. Pre/post pre_tool_call/post_tool_call plugin hooks fire around dispatch, and handle_function_call receives the resolved enabled_tools=list(agent.valid_tool_names) so subagents cannot widen the sandbox (agent/tool_executor.py:1206).

Approval gate

Approval is not invoked from the turn loop directly — it lives inside the tools (e.g. the terminal tool imports the helpers at tools/terminal_tool.py:255). The central gate is check_all_command_guards(command, env_type, ...) (tools/approval.py:1273):

  1. Hardline/sudo-stdin floors block catastrophic commands unconditionally; then container env types and --yolo/HERMES_YOLO_MODE/approvals.mode=off bypass everything (tools/approval.py:1283, tools/approval.py:1309); non-CLI/gateway/ask contexts no-op (tools/approval.py:1318).
  2. Two detectors run — tirith security (check_command_security, tools/approval.py:1344) and the regex detect_dangerous_command (tools/approval.py:594); already session-approved findings are skipped (tools/approval.py:1367).
  3. In smart mode an auxiliary LLM assesses risk via _smart_approve (tools/approval.py:990, invoked at tools/approval.py:1382), itself calling call_llm(task='approval') against the auxiliary client (tools/approval.py:1016, agent/auxiliary_client.py:5046). Verdicts: approve auto-session-approves, deny hard-blocks, escalate prompts the human.
  4. Manual prompts differ by driver: the CLI returns once/session/always/deny via prompt_dangerous_approval (tools/approval.py:822, called at tools/approval.py:1524); the gateway blocks the agent thread on an async /approve//deny via _await_gateway_decision (tools/approval.py:1172), wired by register_gateway_notify (tools/approval.py:641).

Result re-injection

Each result string passes through maybe_persist_tool_result (offloading oversized results to disk-backed references, tools/tool_result_storage.py:122), gains subdirectory hints, then becomes a {"role":"tool", "content":..., "tool_call_id":...} message appended to messages (agent/tool_executor.py:748). After the batch, enforce_turn_budget caps the aggregate result size (tools/tool_result_storage.py:181, called at agent/tool_executor.py:759). On interrupt mid-batch, remaining calls receive synthetic "skipped" tool messages so every tool_call_id is answered (agent/tool_executor.py:780). Back in the loop, compression is checked against real API token counts and the loop continues (agent/conversation_loop.py:3812).

Provider Transport & Normalization

agent.api_mode is resolved once at agent init to one of chat_completions, anthropic_messages, codex_responses, bedrock_converse, or codex_app_server from explicit config, provider name, or base-URL heuristics (agent/agent_init.py:314). The merge extracted the per-provider divergence into a ProviderTransport hierarchy under agent/transports/ — the agent fetches the active one via _get_transport() (run_agent.py:4391) and the loop body calls only its uniform validate_response / map_finish_reason / normalize_response methods. Divergence is concentrated in two places:

  1. Request build — _build_api_kwargs forwards to build_api_kwargs (agent/chat_completion_helpers.py:555): anthropic_messages delegates to build_anthropic_kwargs (agent/anthropic_adapter.py:2253) plus convert_messages_to_anthropic (agent/anthropic_adapter.py:2189); bedrock_converse builds a Converse payload; codex_responses builds a Responses-API payload (input, instructions, reasoning.effort, prompt_cache_key); otherwise a plain chat-completions dict.
  2. Transport call — _interruptible_api_call forwards to interruptible_api_call (agent/chat_completion_helpers.py:125), dispatching to Codex stream, client.messages.create, boto3 converse, or client.chat.completions.create. The streaming variant interruptible_streaming_api_call (agent/chat_completion_helpers.py:1567) mirrors this with client.messages.stream() (agent/chat_completion_helpers.py:2153), chat SSE, or bedrock converse_stream — all returning a SimpleNamespace that mimics the non-streaming shape so the loop is unchanged.

Responses are funneled into a single shape by the transport normalizers. AnthropicTransport.normalize_response (agent/transports/anthropic.py:80) maps Anthropic content blocks (text/thinking/tool_use) and stop_reason into the OpenAI-style .content/.tool_calls[].function.{name,arguments}/.reasoning + finish_reason that the rest of the loop consumes verbatim; the chat-completions, Codex, and Bedrock transports do the same for their providers.

Note. auxiliary_client.py is a parallel transport, not part of the main turn. get_text_auxiliary_client(task) (agent/auxiliary_client.py:3990) returns an OpenAI-compatible client + model for secondary tasks (smart approval, web_extract, compression, title generation, MoA), wrapping non-OpenAI providers behind OpenAI-shaped shims — e.g. the Codex-to-chat adapter (agent/auxiliary_client.py:640) and the Anthropic-to-chat adapter (agent/auxiliary_client.py:991) — so callers always use .chat.completions.create regardless of the main agent's api_mode.

Context-Window Management

The loop holds one ContextCompressor as agent.context_compressor, a ContextEngine subclass (agent/context_engine.py:32, agent/context_compressor.py:563). It exposes only two loop touchpoints:

  • Preflight (before the loop, in build_turn_context): if the loaded history estimate meets the threshold, compress up to 3 passes, resetting retry counters and clearing conversation_history so all compressed messages flush to a new session (agent/turn_context.py:294).
  • Per tool-turn (inside the loop): after _execute_tool_calls, should_compress(_real_tokens) is checked using the real last_prompt_tokens reported by the API (rough estimate fallback when usage is zero), and _compress_context rewrites messages + active_system_prompt when it fires (agent/conversation_loop.py:3812).

Initialization sets threshold_tokens = max(context_length * threshold_percent, MINIMUM_CONTEXT_LENGTH) with protect_first_n=3 and protect_last_n=20 defaults (agent/context_compressor.py:629, agent/context_compressor.py:645). should_compress simply compares tokens to threshold_tokens (agent/context_compressor.py:785); usage is fed via update_from_response (agent/context_compressor.py:741). The deep summarization mechanics live in context_compressor.compress (agent/context_compressor.py:1984) and trajectory_compressor.py, but from the loop's perspective compression is just two hooks that swap state and may start a new session.

The Drivers

Sourcing note. The details below were reconstructed directly from the codebase (cron, gateway, batch_runner, delegate_tool) and the verified main-loop findings. The Atropos RL/eval environment driver (environments/agent_loop.py, HermesAgentLoop) was deleted by upstream commit 5af672c75 and no longer exists, so it is not listed here. Citations point at the live source.

Gateway loop (driver, not a new loop)

The gateway is a long-lived process managing all configured platform adapters. Per inbound message it resolves a per-turn route, then reuses a session-keyed cached AIAgent when the config signature matches (preserving the frozen system prompt and tool schemas for cache hits), else builds a fresh one (gateway/run.py:13999, signature at gateway/run.py:12223). It rebinds callbacks (tool_progress_callback, step_callback, stream_delta_callback, status_callback, gateway/run.py:14068) and calls agent.run_conversation(...) via the async _run_agent() (gateway/run.py:13034, call site at gateway/run.py:10119). Approval flips from synchronous input() to an async /approve transport. So the gateway is one outer driver around the same inner loop, differing in agent lifecycle (session cache vs CLI's singleton, whose turn runs at cli.py:10192), callback wiring, and approval transport.

Cron / routines loop

This is a genuinely separate outer loop, but it still drives run_conversation. A background ticker thread runs while not stop_event.is_set(), calling cron_tick at a fixed interval (default 60s) inside the gateway process so cronjobs fire without a separate daemon (gateway/run.py:15691, ticker started at gateway/run.py:15666). tick() takes a cross-platform file lock so only one tick runs at a time, fetches get_due_jobs(), and for each job calls advance_next_run(job["id"]) before execution (so a mid-run crash will not re-fire the job) then run_job(job) (cron/scheduler.py:1970, due-jobs at cron/scheduler.py:2003, advance at cron/scheduler.py:2018, dispatch at cron/scheduler.py:2050). Schedules are parsed into once/interval/cron kinds — the latter via croniter (cron/jobs.py:28, kinds documented at cron/jobs.py:211).

run_job (cron/scheduler.py:1306) constructs a headless AIAgent (disabled toolsets cronjob/messaging/clarify at cron/scheduler.py:74, platform="cron" at cron/scheduler.py:1754), then submits agent.run_conversation to a single-worker ThreadPoolExecutor guarded by an inactivity-timeout poll loop (HERMES_CRON_TIMEOUT, default 600s, at cron/scheduler.py:1767; pool at cron/scheduler.py:1781). A [SILENT] sentinel at the start of the response suppresses delivery while still saving output for audit (cron/scheduler.py:157). The prompt is prefixed with a [IMPORTANT: ...scheduled cron job...] hint so the agent knows its execution context (cron/scheduler.py:1134).

Batch (data-generation) loop

batch_runner.py is a multiprocessing driver for parallel data generation: the dataset is chunked into batches and dispatched across a process Pool(processes=num_workers) via pool.imap_unordered(_process_batch_worker, tasks) (batch_runner.py:918, batch_runner.py:959). Inside each worker, _process_batch_worker (batch_runner.py:400) iterates the batch's prompts and, per prompt, builds an AIAgent (skip_memory=True at batch_runner.py:345) and calls agent.run_conversation(prompt, task_id=task_id) (batch_runner.py:349). So batch parallelism is process-level fan-out over many independent invocations of the same inner loop; --resume skips already-completed prompts by content-matching per-batch JSONL output (batch_runner.py:821).

Removed in the merge. Earlier revisions of this wiki described a second, structurally distinct async loop — HermesAgentLoop.run() in environments/agent_loop.py — used by Atropos RL/eval environments against a pluggable inference server, including a raw <tool_call>-tag fallback parser. Upstream commit 5af672c75 deleted the entire Atropos/tinker integration: environments/agent_loop.py and the HermesAgentLoop class no longer exist anywhere in the tree, and the root environments/ package is gone (only tools/environments/, the terminal backends, remains). There is no second loop to dissect — every driver listed here funnels into the one synchronous run_conversation.

Delegation / subagents loop

The delegate_task tool (tools/delegate_tool.py:1970) recursively spawns child AIAgent instances, each running the same run_conversation loop. It normalizes input to a task list, rejecting batches larger than delegation.max_concurrent_children (tools/delegate_tool.py:2062). Children are built with care taken to save and restore the global _last_resolved_tool_names that get_tool_definitions mutates (tools/delegate_tool.py:1394, restored at tools/delegate_tool.py:1921). A single task runs directly with no thread-pool overhead (tools/delegate_tool.py:2145); a batch runs in a ThreadPoolExecutor(max_workers=max_children) (tools/delegate_tool.py:2154) with a wait(timeout=0.5, FIRST_COMPLETED) poll loop that bails on parent interrupt instead of blocking forever on a stuck child (tools/delegate_tool.py:2216). Each child eventually calls child.run_conversation(user_message=goal) in _run_single_child (tools/delegate_tool.py:1373, tools/delegate_tool.py:1559).

Caveat: budgets do not nest. Each agent — parent or subagent — gets its own independent IterationBudget, capped via delegation.max_iterations from config (tools/delegate_tool.py:1036, resolved at tools/delegate_tool.py:2041). Total iterations across parent plus subagents can therefore exceed the parent's cap. The parent also truncates excess concurrent delegate_task calls via _cap_delegate_task_calls to enforce max_concurrent_children (run_agent.py:3306), and propagates interrupts down to running children (run_agent.py:2335). Children cannot widen their sandbox: child toolsets are intersected with the parent's and blocked tools are stripped via _strip_blocked_tools (tools/delegate_tool.py:706, tools/delegate_tool.py:989).

Key insight. All five drivers are the same inner loop wrapped in different outer machinery — there is no longer any structurally distinct second loop (the RL/eval async loop was removed in the merge). Surprising Design Choices

Streaming is preferred always. Even when no display or TTS consumer is attached, the loop uses the streaming transport purely to gain stale-connection and read-timeout health checks the non-streaming path lacks (agent/conversation_loop.py:958). The streamed response is repackaged into a non-streaming-shaped SimpleNamespace so the loop body is none the wiser.
Tool-call JSON is re-serialized with sorted keys on every call. This keeps the prompt prefix byte-identical across turns for KV-cache reuse on local inference servers (llama.cpp/vLLM/Ollama) (agent/conversation_loop.py:714).
execute_code-only turns get an iteration refund. Programmatic "RPC-style" tool calling via the sandbox is treated as free so it does not eat the turn budget (agent/conversation_loop.py:3773).
Smart approval embeds a mini LLM guardian inside the gate. A side LLM call decides approve/deny/escalate before bothering the human (tools/approval.py:990), inspired by OpenAI Codex's Smart Approvals (tools/approval.py:996).
Parallel file edits are path-aware. read_file/write_file/patch run concurrently only after a path-overlap check (_paths_overlap compares path-prefix tuples), so disjoint subtrees parallelize while same-subtree edits serialize (agent/tool_dispatch_helpers.py:166).
Five recovery strategies guard every text exit. Partial-stream salvage, housekeeping-only fallback, post-tool empty nudge, thinking-only prefill continuation, and empty-response retry all run before a text turn is allowed to terminate (agent/conversation_loop.py:3830).
