Architecture: The Loops

Hermes is built around a single, synchronous turn loop — AIAgent.run_conversation() at run_agent.py:8169 — that drives one user message to completion. Almost everything else in the system is a driver wrapped around that loop: the CLI REPL, the multi-platform gateway, the cron/routines scheduler, the parallel batch runner, and the recursive delegation of subagents. There is exactly one genuinely separate loop — the async HermesAgentLoop.run() used only by RL/eval environments. This page dissects the main loop and its tool pipeline first, then maps each of the other loops onto it and contrasts them in a single table.

Overview: One Loop, Many Drivers

The seed anchor at run_agent.py:7516 is a red herring — it is the while True future-wait inside _execute_tool_calls_concurrent, not the turn loop. The real turn loop is AIAgent.run_conversation(), a synchronous method that returns a result dict containing final_response, messages, api_calls, completed, and token usage (run_agent.py:11213). Every loop in the system, except the RL/eval one, ultimately calls this exact method.

Key insight. The framing of "lighter CLI loop vs heavier gateway loop" is misleading. The inner loop is byte-identical run_conversation in both cases — they differ only at the driver level (agent lifecycle, callback wiring, approval transport). The single genuinely distinct second loop is HermesAgentLoop.run() (environments/agent_loop.py:175), an async loop used only by RL/eval environments against a pluggable inference server.

The Main Agent Loop

Per-turn preamble

Before entering the loop, run_conversation performs substantial per-turn setup (run_agent.py:8197):

  • Sanitizes surrogate characters and strips leaked <memory-context> blocks from the user message (run_agent.py:8214).
  • Resets a wall of per-turn retry counters — _invalid_tool_retries, _empty_content_retries, _thinking_prefill_retries, and others (run_agent.py:8238).
  • Builds or loads the system prompt once per session for prefix-cache stability: continuing sessions reload the stored prompt from SQLite rather than rebuilding, keeping the Anthropic cache prefix bit-identical (run_agent.py:8336).
  • Runs preflight compression if the loaded history already exceeds the threshold, looping up to 3 passes (run_agent.py:8384).
  • Fires plugin pre_llm_call hooks whose returned context is injected into the user message — never the system prompt, to preserve the cache prefix (run_agent.py:8445).
  • Creates a fresh IterationBudget(self.max_iterations) per call (run_agent.py:8272) and prefetches external memory once (run_agent.py:8523).

The user message is appended and its index recorded as current_turn_user_idx so ephemeral injections can target exactly that message at API-call time (run_agent.py:8317).

The loop body

The loop guard is while (api_call_count < self.max_iterations and self.iteration_budget.remaining > 0) or self._budget_grace_call: at run_agent.py:8531. Each iteration runs five stages:

  1. Interrupt + budget gates — checks _interrupt_requested, increments api_call_count, consumes one iteration-budget unit with a one-shot _budget_grace_call (run_agent.py:8536).
  2. Assemble api_messages — copies messages, injects memory-prefetch and plugin context only into current_turn_user_idx, copies assistant reasoning to reasoning_content for providers that need it, strips internal fields, prepends the effective system message, inserts ephemeral prefills, applies Anthropic cache_control breakpoints when _use_prompt_caching is set, sanitizes orphaned tool results, and re-serializes tool-call JSON with sorted keys for KV-cache prefix stability (run_agent.py:8596).
  3. Inner retry loop — while retry_count < max_retries (max 3), builds kwargs via _build_api_kwargs, then always prefers streaming via _interruptible_streaming_api_call (run_agent.py:8877). Invalid/empty responses trigger eager fallback activation and jittered exponential backoff (run_agent.py:8961).
  4. finish_reason mapping per api_mode — Codex incomplete/length, Anthropic stop_reason to stop/tool_calls/length, OpenAI choices[0].finish_reason; suspicious Ollama/GLM stops are upgraded to length (run_agent.py:9096).
  5. Normalize the response into a uniform SimpleNamespace with .content, .tool_calls, and .reasoning (run_agent.py:10296).

The loop has two real exits: a tool-calling turn does continue (run_agent.py:10755), and a text-only turn sets final_response and break (run_agent.py:11059). A diagnostic _turn_exit_reason string is tracked throughout and logged at the end, escalating to WARNING when the last message is a pending tool result — the "agent just stopped" case (run_agent.py:11165).

Stop conditions and the non-tool exit

The else branch (no tool calls, run_agent.py:10757) is where a turn normally ends, but it is defensive about degenerate responses before committing final_response. It carries five distinct recovery strategies: partial-stream salvage (run_agent.py:10775), housekeeping-only fallback (run_agent.py:10804), a post-tool empty nudge (run_agent.py:10837), thinking-only prefill continuation (≤2×), and empty-response retry (≤3×) (run_agent.py:10884). Once a genuine text response is obtained, any truncated_response_prefix from prior length-continuations is prepended, <think> blocks are stripped for the user-facing string, and the loop breaks (run_agent.py:11033).

Other terminators: interrupt at the top of the loop, budget exhaustion, all retries exhausted with no response, and an outer exception handler near max-iterations. After the loop, if final_response is still None and the budget is spent, _handle_max_iterations makes one extra tools-stripped call asking the model to summarize (run_agent.py:11111). The method then saves the trajectory, cleans up task VM/browser, persists the session, fires post_llm_call/on_session_end hooks, optionally spawns a background memory/skill review, and returns the result dict (run_agent.py:11130).

The Tool-Execution Pipeline

Registration: how tools appear

Tools self-register at import time. Each module calls registry.register(name, toolset, schema, handler, ...) (tools/registry.py:176), which populates a thread-safe ToolEntry map and rejects shadowing of built-ins (only MCP-over-MCP overwrites are allowed). AIAgent.__init__ builds self.tools once via get_tool_definitions(enabled_toolsets, disabled_toolsets, quiet_mode) and derives self.valid_tool_names — the set the loop validates every model tool call against (run_agent.py:1086).

get_tool_definitions resolves the requested toolsets to a name set, asks the registry only for tools whose check_fn passes (so missing API keys hide tools), then dynamically rewrites schemas: execute_code's sandbox-tool list and browser_navigate's description are pruned to actually-available tools so the model cannot hallucinate absent tools (model_tools.py:196). The four _AGENT_LOOP_TOOLS = {todo, memory, session_search, delegate_task} are short-circuited — they must be handled inside the loop with agent state, so direct registry dispatch returns a stub error (model_tools.py:326).

Note. toolset_distributions.py is orthogonal to the live loop: its DISTRIBUTIONS dict and sample_toolsets_from_distribution are used to randomly sample toolset combinations for training-data generation, not runtime dispatch (toolset_distributions.py:29, toolset_distributions.py:247).

Detection, repair, and dispatch

When the normalized assistant_message.tool_calls is truthy (run_agent.py:10464), unknown names are run through _repair_tool_call (fuzzy correction); still-invalid names produce a self-correction error back to the model, capped at 3 retries. The assistant message is appended, the streaming display closed, and _execute_tool_calls(...) runs (run_agent.py:10678).

The dispatcher _execute_tool_calls (run_agent.py:7235) chooses concurrency via _should_parallelize_tool_batch (run_agent.py:267). A batch larger than one runs concurrently only if no tool is in _NEVER_PARALLEL_TOOLS ({clarify}) and every tool is either in the read-only _PARALLEL_SAFE_TOOLS set (read_file, web_search, search_files, web_extract, session_search, vision_analyze, skill_view, HA reads…) or is a path-scoped file tool whose target paths do not overlap (run_agent.py:216). The concurrent path uses a ThreadPoolExecutor with max_workers=min(num_tools, 8) (_MAX_TOOL_WORKERS=8 at run_agent.py:237) and a 5-second-poll wait loop emitting 30-second heartbeats and cancelling pending futures on interrupt — the seed anchor (run_agent.py:7516).

Per-tool execution routes agent-level tools (todo, memory, session_search, clarify, delegate_task, plus memory-manager tools) directly with agent state; everything else goes to handle_function_call (model_tools.py:421) which calls registry.dispatch(name, args, ...) (tools/registry.py:292), bridging async handlers and wrapping all exceptions as {"error": ...}. Pre/post pre_tool_call/post_tool_call plugin hooks fire around dispatch, and execute_code receives the resolved enabled_tools so subagents cannot widen the sandbox (run_agent.py:7258).

Approval gate

Approval is not invoked from the turn loop directly — it lives inside the tools (e.g. the terminal tool imports the helpers at tools/terminal_tool.py:139). The central gate is check_all_command_guards(command, env_type, ...) (tools/approval.py:693):

  1. Container env types and --yolo/HERMES_YOLO_MODE/approvals.mode=off bypass everything; non-CLI/gateway/ask contexts no-op (tools/approval.py:703).
  2. Two detectors run — tirith security (check_command_security) and the regex detect_dangerous_command; already session-approved findings are skipped (tools/approval.py:725).
  3. In smart mode an auxiliary LLM assesses risk via _smart_approve (tools/approval.py:766), itself calling get_text_auxiliary_client(task='approval') (tools/approval.py:546). Verdicts: approve auto-session-approves, deny hard-blocks, escalate prompts the human.
  4. Manual prompts differ by driver: the CLI returns once/session/always/deny via a prompt_toolkit callback or raw input() with denial-on-timeout (tools/approval.py:409); the gateway blocks the agent thread on an async /approve//deny wired by register_gateway_notify (tools/approval.py:233).

Result re-injection

Each result string passes through maybe_persist_tool_result (offloading oversized results to disk-backed references), gains subdirectory hints, then becomes a {"role":"tool", "content":..., "tool_call_id":...} message appended to messages (run_agent.py:7968). After the batch, enforce_turn_budget caps the aggregate result size (run_agent.py:8011). On interrupt mid-batch, remaining calls receive synthetic "skipped" tool messages so every tool_call_id is answered (run_agent.py:7995). Then compression is checked against real API token counts and the loop continues (run_agent.py:10729).

Provider Transport & Normalization

self.api_mode is resolved once in __init__ to one of chat_completions, anthropic_messages, codex_responses, or bedrock_converse from explicit config, provider name, or base-URL heuristics (run_agent.py:683). The loop body never branches on provider beyond a few api_mode == checks; divergence is concentrated in two places:

  1. Request build — _build_api_kwargs (run_agent.py:6429): anthropic_messages delegates to build_anthropic_kwargs plus convert_messages_to_anthropic (agent/anthropic_adapter.py:1214); bedrock_converse builds a Converse payload; codex_responses builds a Responses-API payload (input, instructions, reasoning.effort, prompt_cache_key); otherwise a plain chat-completions dict.
  2. Transport call — _interruptible_api_call (run_agent.py:5010) dispatches to Codex stream, client.messages.create, boto3 converse, or client.chat.completions.create. The streaming variant _interruptible_streaming_api_call (run_agent.py:5259) mirrors this with client.messages.stream() (run_agent.py:5587), chat SSE, or bedrock converse_stream — all returning a SimpleNamespace that mimics the non-streaming shape so the loop is unchanged.

Responses are funneled into a single shape by the normalizers. normalize_anthropic_response (agent/anthropic_adapter.py:1380) maps Anthropic content blocks (text/thinking/tool_use) and stop_reason into the OpenAI-style .content/.tool_calls[].function.{name,arguments}/.reasoning + finish_reason that the rest of the loop consumes verbatim.

Note. auxiliary_client.py is a parallel transport, not part of the main turn. get_text_auxiliary_client(task) (agent/auxiliary_client.py:1673) returns an OpenAI-compatible client + model for secondary tasks (smart approval, web_extract, compression, title generation, MoA), wrapping non-OpenAI providers behind OpenAI-shaped shims (agent/auxiliary_client.py:265) so callers always use .chat.completions.create regardless of the main agent's api_mode.

Context-Window Management

The loop holds one ContextCompressor as self.context_compressor, a ContextEngine subclass (agent/context_engine.py:32, agent/context_compressor.py:188). It exposes only two loop touchpoints:

  • Preflight (before the loop): if the loaded history estimate meets the threshold, compress up to 3 passes, resetting retry counters and clearing conversation_history so all compressed messages flush to a new session (run_agent.py:8384).
  • Per tool-turn (inside the loop): after _execute_tool_calls, should_compress(_real_tokens) is checked using the real last_prompt_tokens + last_completion_tokens reported by the API (rough estimate fallback when usage is zero), and _compress_context rewrites messages + active_system_prompt when it fires (run_agent.py:10729).

Initialization sets threshold_tokens = max(context_length * threshold_percent, MINIMUM_CONTEXT_LENGTH) with protect_first_n=3 and protect_last_n=20 defaults (agent/context_compressor.py:268). should_compress simply compares tokens to threshold_tokens (agent/context_compressor.py:307); usage is fed via update_from_response (agent/context_engine.py:66). The deep summarization mechanics live in context_compressor.compress (agent/context_compressor.py:999) and trajectory_compressor.py, but from the loop's perspective compression is just two hooks that swap state and may start a new session.

The Other Loops

Sourcing note. The dedicated "other loops" findings pass returned empty, so the details below were reconstructed directly from the codebase (cron, gateway, batch_runner, delegate_tool, environments) and the verified main-loop findings. Citations point at the live source.

Gateway loop (driver, not a new loop)

The gateway is a long-lived process managing all configured platform adapters. Per inbound message it resolves a per-turn route, then reuses a session-keyed cached AIAgent when the config signature matches (preserving the frozen system prompt and tool schemas for cache hits), else builds a fresh one (gateway/run.py:8598). It rebinds callbacks (tool_progress_callback, step_callback, stream_delta_callback, status_callback) and calls agent.run_conversation(message, conversation_history=agent_history, task_id=session_id) via _run_agent() (gateway/run.py:8111, gateway/run.py:8886). Approval flips from synchronous input() to an async /approve transport. So the gateway is one outer driver around the same inner loop, differing in agent lifecycle (session cache vs CLI's singleton at cli.py:7704), callback wiring, and approval transport.

Cron / routines loop

This is a genuinely separate outer loop, but it still drives run_conversation. A background ticker thread runs while not stop_event.is_set(), calling cron_tick at a fixed interval (default 60s) inside the gateway process so cronjobs fire without a separate daemon (gateway/run.py:9571). tick() takes a cross-platform file lock so only one tick runs at a time, fetches get_due_jobs(), and for each job calls advance_next_run(job["id"]) before execution (so a mid-run crash will not re-fire the job) then run_job(job) (cron/scheduler.py:909). Schedules are parsed into once/interval/cron kinds — the latter via croniter (cron/jobs.py:117).

run_job constructs a headless AIAgent (disabled toolsets cronjob/messaging/clarify, no context files, platform="cron"), then submits agent.run_conversation to a single-worker ThreadPoolExecutor guarded by an inactivity-timeout poll loop (HERMES_CRON_TIMEOUT, default 600s) (cron/scheduler.py:773). A [SILENT] sentinel at the start of the response suppresses delivery while still saving output for audit (cron/scheduler.py:54). The prompt is prefixed with a [SYSTEM: ...scheduled cron job...] hint so the agent knows its execution context (cron/scheduler.py:523).

Batch / RL data-generation loop

batch_runner.py is a multiprocessing driver for parallel data generation: the dataset is chunked into batches and dispatched across a process Pool(processes=num_workers) via pool.imap_unordered(_process_batch_worker, tasks) (batch_runner.py:880, batch_runner.py:921). Inside each worker, _process_batch_worker iterates the batch's prompts and, per prompt, builds an AIAgent (skip_memory=True) and calls agent.run_conversation(prompt, task_id=task_id) (batch_runner.py:337). So batch parallelism is process-level fan-out over many independent invocations of the same inner loop; --resume skips already-completed prompts by reading per-batch JSONL output.

The RL/eval loop is the one true exception. HermesAgentLoop.run() is async (environments/agent_loop.py:175) and differs structurally from run_conversation:

  • Talks to a pluggable self.server.chat_completion(**chat_kwargs) (a ManagedServer/vLLM wrapper) rather than provider SDK clients (environments/agent_loop.py:230).
  • Plain for turn in range(self.max_turns) with no IterationBudget, no compression, no fallback chain, no memory or plugins (environments/agent_loop.py:204).
  • Includes a raw <tool_call>-tag fallback parser (get_parser('hermes')) for servers whose ToolCallTranslator cannot structure tool calls — something production never needs because the SDK returns structured tool_calls (environments/agent_loop.py:268).
  • Still dispatches through the same handle_function_call registry path and returns a structured AgentResult dataclass (environments/agent_loop.py:411, environments/agent_loop.py:64).

Delegation / subagents loop

The delegate_task tool (tools/delegate_tool.py:623) recursively spawns child AIAgent instances, each running the same run_conversation loop. It normalizes input to a task list, rejecting batches larger than delegation.max_concurrent_children (tools/delegate_tool.py:671). All children are built on the main thread first — thread-safe construction — with care taken to save and restore the global _last_resolved_tool_names that get_tool_definitions mutates (tools/delegate_tool.py:705). A single task runs directly with no thread-pool overhead; a batch runs in a ThreadPoolExecutor(max_workers=max_children) with a wait(timeout=0.5, FIRST_COMPLETED) poll loop that bails on parent interrupt instead of blocking forever on a stuck child (tools/delegate_tool.py:741). Each child eventually calls child.run_conversation(user_message=goal) in _run_single_child (tools/delegate_tool.py:399, tools/delegate_tool.py:472).

Caveat: budgets do not nest. Each agent — parent or subagent — gets its own independent IterationBudget, capped via delegation.max_iterations (run_agent.py:173). Total iterations across parent plus subagents can therefore exceed the parent's cap. The parent also truncates excess concurrent delegate_task calls via _cap_delegate_task_calls to enforce max_concurrent_children (run_agent.py:3583), and propagates interrupts down to running children (run_agent.py:3124). Children cannot widen their sandbox: child toolsets are intersected with the parent's, and blocked tools are stripped (tools/delegate_tool.py:285).

Key insight. Five of the six loops are the same inner loop with different outer drivers; only the RL/eval loop is structurally distinct. Yet even it converges on the shared tool surface — handle_function_call to registry.dispatch — so tool behavior is identical across the entire system regardless of which loop invoked it.

Surprising Design Choices

Streaming is preferred always. Even when no display or TTS consumer is attached, the loop uses the streaming transport purely to gain stale-connection and read-timeout health checks the non-streaming path lacks (run_agent.py:8844). The streamed response is repackaged into a non-streaming-shaped SimpleNamespace so the loop body is none the wiser.
Tool-call JSON is re-serialized with sorted keys on every call. This keeps the prompt prefix byte-identical across turns for KV-cache reuse on local inference servers (llama.cpp/vLLM/Ollama) (run_agent.py:8696).
execute_code-only turns get an iteration refund. Programmatic "RPC-style" tool calling via the sandbox is treated as free so it does not eat the turn budget (run_agent.py:10712).
Smart approval embeds a mini LLM guardian inside the gate. A side LLM call decides approve/deny/escalate before bothering the human (tools/approval.py:766), inspired by Codex-style smart approvals.
Parallel file edits are path-aware. read_file/write_file/patch run concurrently only after a path-overlap check (_paths_overlap compares path-prefix tuples), so disjoint subtrees parallelize while same-subtree edits serialize (run_agent.py:296).
Five recovery strategies guard every text exit. Partial-stream salvage, housekeeping-only fallback, post-tool empty nudge, thinking-only prefill continuation, and empty-response retry all run before a text turn is allowed to terminate (run_agent.py:10757).
